# TwinVM Stage 1 报错修复报告（v0.2.7 → v0.2.8）

> 现场：真机自检「运行 STAGE 1 自检（BIONIC GUEST）」→ 控制台在 `trap#16 nr=57`（closedir）
> 之后直接 `[TwinVM] guest 槽位退出: code=-31（异常）`；logcat 同步记录
> `TwinVM : stage0 guest slot exit=-31`（时间戳 1791805829.774）。
> `code=-31` = `WTERMSIG==31` = **死于 SIGSYS**。

---

## 0. 一句话结论

**seccomp 过滤器与用户态内核判决表不一致，导致"直发内核"的 syscall 在 SIGSYS handler
内部被自己的过滤器二次 TRAP**：`exit(93)`（bionic `__exit()` 线程退出）被过滤器判为
TRAP，而 `vm_handle_syscall()` 把它当 `VM_PT3`（handler 里裸 `svc` 直发）——
裸 `svc` 又落回同一个过滤器，此刻 SIGSYS 处于阻塞态，内核**不执行**该 syscall、只把
SIGSYS 挂起；等 guest（bionic）自己恢复掩码时才"迟到"投递，ucontext 已不是系统调用
现场，寄存器是别处的垃圾 → 用垃圾参数执行一次完全无关的 syscall / handler 自递归。

bionic 的 `pthread_create` 恰好在 `clone` 前后 `sigfillset()+rt_sigprocmask(SIG_SETMASK)`
**屏蔽全部信号**，而线程入口 `__start_thread` 的第一件事就是 `gettid`、线程结束走
`__exit`(exit) —— 三者正落在这个窗口里。这就是"trap#16 之后再也不打 trap#N，直接
SIGSYS 退出"的原因，也是自检*pthread 一步必崩*的原因。

修复：把 `exit`、`gettid` 加入 BPF 放行清单（线程退出/线程入口直达内核），并给
handler 加上"直发集合 ⊆ 放行清单"的启动自检 + 迟到 TRAP 防护。

## 1. 取证链（全部可复核）

### 1.1 退出码 → 信号

`android/jni/twinvm_jni.c`：

```c
int code = WIFEXITED(st) ? WEXITSTATUS(st) : -WTERMSIG(st);
```

`-31` ⇒ `SIGSYS`。控制台最后两行是 `trap#16 nr=57` → `guest 槽位退出: code=-31`，
说明第 17 次 TRAP **从未进入 handler**（handler 第一件事就是打印 `trap#N`，
`n_count<48` 时必定打印）。

### 1.2 真机 guest 二进制反汇编（来自设备上安装的 APK/ROM，entry=0x2173c0，与截图一致）

从设备取出 `assets/demo.rom`（`/data/data/dev.twinbox.vm/files/demo.rom`）解包得到
`/bin/guest`（2156512 B，AArch64 ET_EXEC，entry 0x2173c0）。binutils 反汇编：

```
0000000000260d00 <__exit>:          ; bionic 线程退出
  260d04: mov x8, #0x5d             ; 93 = exit        ← 我们的过滤器判 TRAP
  260d08: svc #0
0000000000260cc0 <_Exit>:
  260cc4: mov x8, #0x5e             ; 94 = exit_group  ← 放行
0000000000247080 <__bionic_clone>:
  247088: mov x8, #0xdc             ; 220 = clone      ← 放行
00000000002304dc <__start_thread>:  ; 新线程入口
  230510: mov w0, #0xb2             ; 178 = gettid     ← 我们的过滤器判 TRAP
  230514: bl syscall
  230524: bl __exit                 ; 线程结束 → exit(93)
000000000022f5 90 <pthread_create>:
  22f7f0: bl sigfillset64
  22f804: bl __rt_sigprocmask       ; SIG_SETMASK ← 屏蔽全部信号（含 SIGSYS）
  22f82c: bl clone
  22f844: bl __rt_sigprocmask       ; 父线程恢复
000000000022fb08 <__pthread_start>: ; 子线程
  22fb74: bl __rt_sigprocmask       ; ← 子线程在这里才恢复掩码：迟到投递点
```

要点：
* `exit(93)` 是 **bionic 的线程退出**（不是 `exit_group`），Stage 1 guest 里
  `pthread_create` 之后必然走到它；
* 新线程出生时**继承父线程"全屏蔽"的掩码**，第一条 `gettid` 与最后的 `exit`
  都发生在 SIGSYS 被屏蔽的窗口内；
* `__pthread_start` 直到 `22fb74` 才 `rt_sigprocmask(SIG_SETMASK, …)` 恢复掩码 ——
  被挂起的 SIGSYS 就是在这里"迟到"投递的，此时 ucontext 早已不是系统调用现场。

### 1.3 离线 BPF 仿真（`core/tests/bpf_sim.py`，不需要 seccomp）

用生成的 `bpf_gen.h` 逐条解释执行过滤器：

```
── aarch64: 过滤器 57 条指令, 判决表直发 26 项
   !! 直发 exit                 nr= 93 -> 0x30000     ← SECCOMP_RET_TRAP
   !! 直发 gettid               nr=178 -> 0x30000
   ...
FAIL:
  - aarch64: 判决表直发 exit(93) 未被 BPF 放行（0x00030000）—— handler 内裸 svc 会二次 TRAP
  - aarch64: 判决表直发 gettid(178) 未被 BPF 放行（0x00030000）
  - x86_64 : 判决表直发 exit(60) / gettid(186) / prctl(157) 未被 BPF 放行
```

即：**判决表里 26 个 `VM_PT*` 直发 syscall 中，有 2 个（arm64）不在放行清单里**；
x86_64 上 `prctl` 连清单都没进（`gen_bpf.py` 的 X86 表漏了 `'prctl': 157`）。
这正是本 bug 的机械证据，也可以当作回归测试（修复前 FAIL、修复后 PASS）。

### 1.4 机制（为什么不是普通的 ENOSYS，而是 SIGSYS 退出）

1. guest 线程在"全信号屏蔽"窗口里执行 `exit(93)` → 过滤器 TRAP → 内核
   `syscall_rollback` + `force_sig_info(SIGSYS)`；因为 SIGSYS 被屏蔽，**信号挂起、
   handler 不运行、该 syscall 不执行**（这是内核 seccomp-TRAP 的既定行为）。
2. handler 侧：正常情况下（掩码没屏蔽）handler 会用裸 `svc` 直发 `exit(93)`，
   而裸 `svc` 同样受本过滤器管辖 → 在 handler 内二次 TRAP（SIGSYS 必然处于阻塞
   态）→ 再次挂起 → handler 返回 → 立刻再次投递 → **handler 自递归**。
3. 迟到投递：`__pthread_start` 恢复掩码时投递挂起的 SIGSYS，ucontext 指向
   `rt_sigprocmask` 返回处，`r[8]`/`r[0..5]` 都不是系统调用参数 —— 原实现
   `long nr = (long)r[8];` 会**用垃圾当 syscall 号**（可能命中 `openat`/`write`
   分支去解引用垃圾指针），也可能形成"直发→二次 TRAP→再直发"的活锁。
   三个后果（自递归爆栈 / 垃圾参数乱判决 / 空转）最终都以进程被 SIGSYS 干掉收场，
   而且全程不会再打 `trap#N`（信号一直没进 handler）。

### 1.5 容器内 A/B 复现（同架构、同 BPF、同一份真机 guest）

本机容器（aarch64 Ubuntu + proot）用与 JNI 同构的宿主程序
（`core/tests/a64_selftest.c`）加载真机 ROM：

```
===== 原版引擎 =====
[TwinVM] 拦截就绪，装载 guest entry=0x2173c0（原生 aarch64 代码）
[TwinVM] guest 槽位退出: code=-4（异常）
[TwinVM] 死于信号 4 (Illegal instruction)      ← 线程退出路径失控（proot 吞掉 SIGSYS，故表现为 SIGILL）
===== 修复版引擎 =====
[TwinVM] 拦截就绪，装载 guest entry=0x2173c0（原生 aarch64 代码）
[TwinVM] guest 槽位退出: code=0（正常关机）     ← 关键修复点行为正确
```

（容器是 proot，SIGSYS 会被 proot 吞掉，所以真机上的 SIGSYS 在容器里表现为
SIGILL/挂死 —— 但"在 guest 的 pthread 一步失控"这件事两边完全一致。）

## 2. 修复内容（逐文件）

| 文件 | 改动 |
|---|---|
| `core/gen_bpf.py` | `ALWAYS` 放行清单加入 `exit`、`gettid`；补齐 X86 表漏掉的 `prctl:157`；额外生成机器可读放行清单 `VM_BPF_ALLOW_NRS`；输出改到 `core/src/bpf_gen.h`；把"直发必须放行"写成铁律注释 |
| `core/src/bpf_gen.h` | 重新生成：arm64 61 条指令 / 26 项放行，x86_64 63 条 / 27 项放行（跳转偏移由生成器重算） |
| `core/src/vm_backend_sigsys.c` | ① syscall 号一律取内核给的 `si->si_syscall`（不再信 `r[8]`）；② **迟到投递防护**：`si_call_addr != ucontext PC` ⇒ 判定为"挂起后才投递的 TRAP"，只告警不判决；③ **启动自检** `vm_filter_check_passthrough()`（内置微型 BPF 解释器，把 26/27 个直发 syscall 逐个喂进过滤器，发现不是 ALLOW 就大声告警）；④ `sys/reg.h` 只在 x86_64 包含（顺带让 glibc-aarch64 宿主可编译） |
| `core/src/vm_core.c` | 新增显式直发清单 `vm_passthrough_nrs[]`（判决表的不变量）；`case VM_NR_exit` 兜底改为**退化为 `exit_group` + 告警**（万一过滤器又漏放行，也绝不会在 handler 里二次 TRAP） |
| `core/include/vm_core.h` | 导出直发清单与自检函数声明 |
| `core/tests/bpf_sim.py` | 新增/重写：BPF 判决仿真 + **铁律回归**（直发集合 ⊆ 放行清单、两架构清单一致、write(console) 直通、架构不匹配 KILL） |
| `core/tests/a64_selftest.c` | 新增：aarch64 自检宿主（与 Android JNI `stage0` 同构；glibc 静态，可在 Termux 直接跑真机 A/B） |
| `core/Makefile` | 新增 `test`（离线回归）/ `bpf`（重生成过滤器）/ `selftest_a64` 目标 |
| `android/jni/twinvm_jni.c` | 诊断增强：退出码附信号名与提示（SIGSYS → 指向判决表/放行清单）；修正 `GUEST FAULT` 里把 `regs[31]/regs[32]` 当 sp/pc 的越界读（arm64 `regs[]` 只有 x0..x30，sp/pc 是 `sigcontext` 独立字段） |
| `rom/rompack.py` | 修 `unpack()` 两个既有 bug：头部结构体是 7 字段却只解 6 个（ValueError）；`name` 未按首个 NUL 截断导致 `embedded null byte` |
| `android/AndroidManifest.xml` | 版本号 0.2.7 → **0.2.8**，versionCode 9 → 10 |

## 4. 尚未做 / 已知风险（诚实清单）

1. **真机运行验证由你执行**（你选择自行编译）：1.5 的容器 A/B 与 3.1 的离线回归我都跑了，
   真机（非 proot）这一环没有由我复跑。
2. "guest 自己屏蔽 SIGSYS 的窗口里发生的其他 TRAP"仍然会被内核**丢弃**（内核行为，
   无法在 handler 里补救，因为信号到达时参数已经没了）。现在引擎会打印
   `迟到 TRAP nr=…` 而不是拿垃圾参数乱判决 —— 这是"不再崩"，但不是"完全正确"。
   Stage 2 建议：像 VMOS 那样引入**不带过滤器的 broker 槽位**（fork 早于过滤器安装）
   来代发这类 syscall，或直接把直发集合全部改成放行清单成员。
3. `gettid` 现在透传（返回真实 tid），而 `getpid` 仍按设计伪造为 1。此时 guest 若用
   `pthread_kill`/`tgkill(getpid(), tid, sig)`，`tgid` 会是 1（内核以 EPERM 拒绝，
   无副作用但不正确）。Stage 2 建议把 `kill/tgkill/getpid` 族一起虚拟化。
4. 过滤器放行清单加入了 `exit`：语义上"guest 线程退出"会真的让宿主线程退出 ——
   对本项目（guest 就是宿主进程本身）正是想要的；但如果以后做"多 guest 共享进程"的
   槽位池，需要重新评估（每个槽位应独占一个进程）。
5. `gen_bpf.py` 生成的跳转偏移是自动回填的，改动放行清单后**必须重跑** `make bpf`
   （否则 `bpf_gen.h` 与实际清单脱节）；新加的启动自检会当场告警这种情况。
