## 1. 本轮两个独立 bug

### bug 1（真凶）：`android/build.sh` 只把 fixture 的 `system/` 打进 ROM，`apex/` 被丢掉

你的 fixture 里其实**已经有** javalib：
`rom/fixture/android_root/apex/com.android.art/javalib/{core-oj,core-libart,okhttp,bouncycastle,apache-xml,service-art}.jar`
（6 个 jar 我逐个 md5 与设备 `/apex/com.android.art/javalib/` 核对：**全部一致 ✔**）。

但 build.sh 第 2 步只有：

```bash
cp -r ../rom/fixture/android_root/system "$OUT/romroot/system"
```

→ `/apex/**` 从来没进过 ROM（45 inode 里一个 `/apex` 都没有）。
而 guest 的 `BOOTCLASSPATH` 指向 `/apex/com.android.art/javalib/*.jar` —— 路径指到空处。

**反汇编取证**（用 ROM 里的 `libartbase.so`）：那句 CHECK 的位置是

```
art::GetDefaultBootImageLocation(const std::string&, bool, bool)
   └─ 调 art::GetDefaultBootImageLocationSafe(...)
      file_utils.cc:609  CHECK(!location.empty())
      << "BOOTCLASSPATH and DEX2OATBOOTCLASSPATH must not be empty"
```

即：**ART 用 boot classpath 第一项 jar 的目录去推默认启动镜像位置**，classpath 为空 → location 为空 → FATAL。
（旁证：`libartbase.so` 里还有 `%s!%s/%s:/nonx/%s-framework.art!%s/%s`、`etc/boot-image.prof`、
`dalvik.vm.boot-image` —— 和我们下面要放镜像的位置完全对得上。）

> 顺带排除了"环境变量没传进去"这条嫌疑：我新写了 `core/tests/envtest.c` 直接调
> `vm_loader_exec_dyn` 构造 exec 栈再按 ABI 解析，**envp 每条字符串逐字节完好、
> BOOTCLASSPATH 非空**（长度 266）→ 环境是能到 guest 的，问题在 ROM。

### bug 2（潜在崩溃）：exec 栈的字符串区没预留，写穿栈顶

`vm_loader.c` 里 `strs` 只算了 `execfn/platform/AT_RANDOM`，但 argv/envp 字符串却从 auxv
结束处**往上**写、没有预留空间：

* 真机 `BOOTCLASSPATH` 266B + 其它变量 ≈ 353B，刚好落在旧代码的"渣余量"里（靠 `32*2*8`
  的 auxv 预留多出来的空间侥幸没炸），但会**盖掉 AT_RANDOM/AT_EXECFN/AT_PLATFORM**；
* 环境再大一点就**越过 1MB 栈映射**。A/B 实测（`tests/envtest.c`，8 条 500B 环境变量）：

| loader | 结果 |
|---|---|
| 旧（你的 0.7.36） | **Segmentation fault，退出码 139** |
| 新（v0.7.37） | PASS（字符串整条都在映射内，AT_RANDOM/EXECFN/PLATFORM 完好） |

## 2. 修复

### 2.1 `android/build.sh`：`android_root/` 的**所有**顶层目录整体进 ROM

```bash
for d in ../rom/fixture/android_root/*; do
    b=$(basename "$d")
    case "$b" in bin|rom) continue ;; esac      # 这两个由脚本自己产出
    cp -r "$d" "$OUT/romroot/$b"
done
```

### 2.2 `vm_loader.c`：字符串区先算够再写（与内核同布局）

`strbytes = 16(AT_RANDOM) + execfn + platform + Σargv + Σenvp`（16 对齐），
布局改成 `AT_RANDOM | execfn | platform | argv... | envp...` 全部落在预留区内，
auxv 里的 `AT_RANDOM/AT_EXECFN/AT_PLATFORM` 指向这些新位置。

### 2.3 `guest_stage42.c`：补齐 ART 要的环境

* `BOOTCLASSPATH` 顺序对齐设备 `/apex/com.android.art/etc/classpaths/bootclasspath.pb`
  （core-oj, core-libart, okhttp, bouncycastle, apache-xml；**service-art 不进 boot**）；
* 补 `DEX2OATBOOTCLASSPATH`（libartbase 里明写 "DEX2OATBOOTCLASSPATH must be a prefix of BOOTCLASSPATH"）；
* 补 `ANDROID_ASSETS/ANDROID_STORAGE/LD_LIBRARY_PATH/PATH/TMPDIR`。

### 2.4 ROM：把 javalib + classpaths + **启动镜像**一起放进去（59 inode / 46.9 MB）

| 新增 | 来源 | 说明 |
|---|---|---|
| `/apex/com.android.art/javalib/*.jar`（6 个，9.3MB） | fixture（= 设备 APEX，md5 全对） | ART 的 boot classpath |
| `/apex/com.android.art/etc/classpaths/{bootclasspath,systemserverclasspath}.pb` | 设备 APEX | 设备用它描述 classpath |
| `/apex/com.android.art/etc/{boot-image.prof,dirty-image-objects}` | 设备 APEX | ART 会去读 |
| `/apex/com.android.art/javalib/boot.{art,oat,vdex}`（共 5.2MB） | 设备 `/system/framework/arm64/` | **ART 默认推算的镜像位置**就是"第一个 boot jar 的目录/boot.art" |

### 2.5 工具：把这两类事故变成机器可查

* `rom/checkrom.py` 新增**启动类路径完整性**检查：
  「ROM 里有 dalvikvm，却没有任何 `/apex/.../javalib/*.jar`」直接 FAIL 并指向 build.sh；
  同时校验 `classpaths/*.pb` 里列的每个 jar 都在 ROM 内。对你这版 ROM 的输出：
  ```
  !! ROM 里有 dalvikvm，却没有任何 /apex/com.android.art/javalib/*.jar
  FAIL: 启动类路径不完整 1 项（ART 起不来）
  ```
* `rom/syncrom.py`：加**同名路径兜底**（`/apex/...` 这类路径设备上就是同名路径）、
  boot 镜像映射（`apex/com.android.art/javalib/boot.*` ← `/system/framework/<isa>/boot.*`）、
  以及 `--as-root`（直接产出 build.sh 要的 fixture）。
  实测 `--as-root` 从设备重建的 fixture 与树里的**逐字节一致**（54 项全对，只剩 `.keep` 保留原样）。
* `core/tests/envtest.c`（新）：exec 栈 argv/envp 回归，已挂进 `make test`。

## 4. 下一层可能卡哪（都给了对应弹药）

1. **启动镜像映射**：镜像里记录了首选加载地址，而 guest 的 linker/exe 已经占了
   `0x71eee…/0x7302d…`。ART 会尝试重定位（可能变慢/报 "Failed to mmap boot image"）。
   日志里会出现 `openat("/apex/com.android.art/javalib/boot.art") -> fd=…`：
   只要能看到它打开成功，就说明位置对了，剩下是映射问题。
2. **`/proc/self/maps`**：本轮日志里 ART 的 `Runtime aborting` 之后
   `native: (Unwind failed for thread 29861: Failed to parse maps)` ——
   目前 ROM 没有合成 `/proc/self/maps`。合成一份（按 guest 自己的映射表）能让崩溃
   堆栈可读，也是 ART 某些路径会读的文件。
3. **属性区 `/dev/__properties__`**：仍 ENOENT（`__system_property_get` 全空）。
   `libartbase.so` 里有 `dalvik.vm.boot-image` 这个属性名 —— 空属性时会退回
   "从 boot classpath 推默认镜像位置"，也就是本轮修好的那条路；真要设属性就得把
   property area 也虚拟化（或让 engine 对若干关键属性直接答值）。
4. 其它已见但暂不致命的：`ENOSYS nr=282(userfaultfd) / nr=240(mq_open)`、
   `/sys/kernel/tracing/trace_marker -> -EACCES`（ART 只是警告）。

## 5. 诚实说明

* 我在容器里跑不了 ART（proot 吞 SIGSYS），本轮证据 = 单元测试（含 A/B）+ 真机日志 +
  对 ROM 内 `libartbase.so` 的反汇编定位 + 设备文件 md5 比对；
* 启动镜像虽然按 ART 的推算位置放好了，但**能否在 guest 地址空间里映射成功要以真机日志为准**；
* 我改的 `guest_stage42.c` 需要你重跑 `bash build.sh`（它会重编 guest）才生效；
  ROM 本身已经用你现成的 guest 重打过，即使不重编 guest，classpath/镜像这层也已经能过
  （BOOTCLASSPATH 是旧 guest 就有的）。
