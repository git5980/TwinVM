# TwinVM Stage 4.2 修复报告（第六轮：ART 那句 CHECK 的真身 = android_root 为空）v0.7.37 → v0.7.38

> 本轮我自己完成了闭环：**自己取日志 → 自己定位 → 自己修 → 自己打包 APK**，不需要你贴日志。
> 取日志路径（App 自己落的盘）：
> `/storage/emulated/0/Android/data/dev.twinbox.vm/files/twinvm-<时间戳>.log`
> 本轮现场：`twinvm-20261013-223507.log`（用我上一版 APK 跑的：`ROM 59 inodes` ✔）。

## 1. 上一版（v0.7.37）之后仍然报同一个 CHECK —— 说明病根不只在 ROM 的 jar

```
dalvikvm file_utils.cc:609] Check failed: !location.empty()
                BOOTCLASSPATH and DEX2OATBOOTCLASSPATH must not be empty
dalvikvm runtime.cc:719] Runtime aborting...     → code=127
```
关键观察：**日志里一次 `/apex/...` 的 openat 都没有** —— 也就是说 ART 根本没走到"打开 jar"，
是在更早的地方就判定了"boot classpath 为空"。所以我又拆了一层。

## 2. 反汇编定位（用 ROM 里的 `libartbase.so` / `libart.so`，都是带符号的）

1. `file_utils.cc:609` 的 CHECK 在 `art::GetDefaultBootImageLocation(const std::string&, bool, bool)`
   → 转发到 `GetDefaultBootImageLocationSafe(...)`，**它检查的是第一个参数（一个 std::string）是否为空**。
2. 在 `libart.so` 里找到唯一调用点（`ParsedOptions::DoParse` 内）：
   ```
   63a1cc: stp xzr,xzr,[sp,#24] ; str xzr,[sp,#40]   ← 初始化结果 string
   63a1d4: mov x8, sp
   63a1d8: bl  art::GetAndroidRoot()                 ← 取 /system 这类根
   63a1dc: bl  art::IsZygoteOcomp()
   63a1e8: mov x0, sp                                ← 第一参数 = GetAndroidRoot() 的返回值!
   63a1f4: bl  GetDefaultBootImageLocation
   ```
   ⇒ **CHECK 触发是因为 `GetAndroidRoot()` 返回了空字符串**，那句 "BOOTCLASSPATH … must not be empty"
   是这条路径上的（容易误导人的）文案。
3. `GetAndroidRoot()` → `GetAndroidRootSafe()`：读 `ANDROID_ROOT`，拿不到就失败 →
   `art::GetAndroidRoot()` 里那句 `Check failed: !ret.empty()`。

**顺带修正了上一轮我的一个推测**：boot 镜像不是放在"第一个 boot jar 的目录"，而是
**`<android_root>/framework/<isa>/boot.art`**（设备就是 `/system/framework/arm64/boot.{art,oat,vdex}`）。

### 我把整条环境链路在容器里逐段测了（都是新写的回归）

| 链路 | 测试 | 结果 |
|---|---|---|

所以"环境没传进 guest"这条**在本地测不出来**，必须让真机自己说 —— 于是我加了一个探针。

## 3. 本轮修复

### 3.1 新增 `/bin/probe`（**动态 PIE**，和 dalvikvm 同款装载路径）

guest 现在 exec `/bin/probe`，探针做四件事（然后原样透传 argv/env 继续 exec dalvikvm）：

1. 打印 `argc/argv`；
2. 打印完整 `environ` 条数 + 四个关键变量（`BOOTCLASSPATH` / `DEX2OATBOOTCLASSPATH` / `ANDROID_ROOT` / `ANDROID_DATA`）；
3. 逐个 `open()` ART 要用的 ROM 路径，打印拿到的 fd（**≥10000 就是 ROM 虚拟 fd**）：
   `/apex/com.android.art/javalib/{core-oj.jar,boot.art,boot.oat,boot.vdex}`、`etc/classpaths/bootclasspath.pb`、
   `/system/framework/arm64/boot.{art,oat,vdex}`、`/system/lib64/libart.so`、`/system/bin/dalvikvm`；
4. 用**裸 `svc 221`**（不是 `execveat` —— 引擎只实现了 `execve`）继续引导。

一次运行就能判定：是环境没到 ART，还是 `GetAndroidRoot()`/路径推算的问题，并且顺手验证 ROM 布局。

### 3.2 ROM 布局修正（63 inode / 53.3 MB）

* 把设备启动镜像**放到 ART 真正会推算的位置**：`/system/framework/arm64/boot.{art,oat,vdex}`（1.1MB+3.8MB+0.11MB）；
* 上一版放在 `/apex/com.android.art/javalib/` 的那份**保留**（两条路径都在，谁对都能中）；
* 6 个 boot jar + `etc/classpaths/*.pb` + `boot-image.prof` 继续保留（`checkrom --strict` PASS）。

### 3.3 引擎与 guest 都重新编译了（这次我这边有工具链了）

容器里原本没有 NDK（x86_64 的 NDK 在 aarch64 容器里跑不起来），我改成：
**Ubuntu clang 18 + NDK r26d 的 sysroot（bionic 头/库，与宿主架构无关）+ lld**，
等价于你 `build.sh` 里 clang 的用法（`--target=aarch64-linux-android24`）。
于是本轮 APK 里：

* `lib/arm64-v8a/libtwinvm.so` = **你自己源码 + 我这轮的 `vm_loader.c` 字符串区修复**重新编译（不再是沿用旧 .so）；
* ROM 里的 `/bin/guest` = 我用你的 `guest_stage42.c`（含我补的 `DEX2OATBOOTCLASSPATH/PATH/TMPDIR` 等）+ 探针跳转重新编译。

### 3.4 顺手修掉的真 bug（`vm_loader.c`）

exec 栈的字符串区旧写法只把 `execfn/platform/AT_RANDOM` 算进预留，argv/envp 字符串却从 auxv
后面往上写 → **会盖掉 AT_RANDOM/AT_EXECFN/AT_PLATFORM，环境一大就直接越过 1MB 栈映射**。
A/B：旧代码 + 8×500B 环境 = `SIGSEGV(139)`；新代码 = PASS。已在 `make test` 里常驻。

## 6. 诚实说明

* 我**没能**在容器里跑通 ART（缺 `/linkerconfig/ld.config.txt`，而设备根目录按策略只读，不能造；
  连用设备自己的 `/apex/com.android.art/bin/dalvikvm` 在容器里跑也是同样的 "Failed to initialize JNI invocation API"，
  证明这是容器环境限制，不是 ROM 的问题）。
* 因此本轮结论建立在：反汇编（ART 侧 CHECK 的真实输入）+ 三个自建回归（引擎侧全绿）+ 探针（下一份日志）。
* 探针是诊断脚手架：等定位清楚后把 `guest_stage42.c` 里那行换回 `/system/bin/dalvikvm`，
  `/bin/probe` 就可以从 ROM 里去掉。
