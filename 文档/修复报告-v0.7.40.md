# TwinVM Stage 4.2 修复报告（第八轮：卡死可见化 + 排除新引入变量）v0.7.39 → v0.7.40

> 我这轮没能拿到卡死现场 —— 因为**卡死时本来就没有日志**（App 是 native 返回后才落盘的），
> UI 又一直停在"运行中"。所以这一轮的主要工作是**把卡死变成可诊断的**，顺带排掉我自己引入的变量。

## 1. 现场勘查（我自己做的）

| 检查 | 结果 |
|---|---|
| 日志目录 | 最新仍是 `twinvm-20261014-065541.log`（06:55，v0.7.38 那次的）→ **v0.7.39 那次没落盘** |
| 应用进程 | pid 24788 仍在（06:59:16 启动，S 态、0 CPU） |
| 它的 20 个线程 | 全是 App 自己的 ART 线程（Jit/HeapTaskDaemon/binder/RenderThread…），**没有 `twinvm-selftest` 工作线程** |
| 它的子进程 | **没有**（`ps -ef` 里 PPID=24788 一个都没有） |
| 屏幕截图 / UI dump | 设备侧 `SCREEN_TARGET_UNAVAILABLE`（DSHA 截屏目标当前不可用，读不到 UI 文字） |

结论：**"运行中"卡住时，native 调用没有返回、也没有崩溃日志**，而这套实现是"读管道攒完再返回"，
所以卡死 = 零证据。这是设计缺陷，必须补。

## 2. 本轮改动

### 2.1 卡死可见化（`android/jni/twinvm_jni.c`）

* **实时日志**：控制台每读到一段就立刻追加写 `twinvm-live.log`（外部私有目录，8MB 上限）——
  **卡死也会留下最后现场**；
* **看门狗**：`poll()` + 超时判定 —— 连续 **60 秒**无任何控制台输出，或总时长超 **300 秒**，
  即判定卡死：把"最后现场"交回 UI、`SIGKILL` 槽位、结束本次运行。
  这样 UI **不会再永远停在"运行中"**，而且会明确告诉你"是卡死（被强杀）而不是崩溃"；
* Java 侧同步改：`Native.stage0(romPath, liveLogPath)`（`MainActivity` 传
  `getExternalFilesDir(null)/twinvm-live.log`）。

### 2.2 排掉上一轮我自己引入的变量

* **撤掉 `/linkerconfig/ld.config.txt`**：那是我 v0.7.39 加的（只为消掉 linker 的一句 warning），
  但它改变了 linker 读配置的路径 —— 在找卡死原因期间不该同时动多个变量，先退回 v0.7.38 的行为
  （linker 走 `/system/etc/ld.config.txt`，也就是你们原来那套）；
* v0.7.39 里真正**必要**的那条修复保持不变：`DEX2OATBOOTCLASSPATH` 是 `BOOTCLASSPATH` 的**真前缀**
  （`core-oj:core-libart`），因为上一轮已由日志实证过（`No mainline framework library found` 消失意味着 ART 走得更深了）。

### 2.3 版本与产物

* 版本 **0.7.39 → 0.7.40**（versionCode 62 → 63）；
* ROM **64 inode / 53.3MB**，`checkrom --strict` PASS，仍含：
  6 个 boot jar、`etc/classpaths/*.pb`、`/apex/.../javalib/boot.{art,oat,vdex}` 与
  `/system/framework/arm64/boot.{art,oat,vdex}`、`/bin/{guest,probe}`；
* `lib/arm64-v8a/libtwinvm.so` 用你源码 + 我的 loader 修复 + 本轮 JNI 重编（60,600 B）。

## 3. 你这边只需要做一件事

装 **v0.7.40**（与上一版同签名，可直接覆盖）→ 点一次「运行」。

* 如果**正常跑完**：日志照旧落在 `twinvm-<时间戳>.log`，我下一轮自己取；
* 如果**又卡住**：等约 60 秒 → UI 会自动解冻并显示"**被看门狗强杀 = 卡死**"，
  同时 `twinvm-live.log` 里保留了卡住前的**最后几十行**（引擎的 TRAP/openat 行会直接指到具体位置）。
  **我不需要你贴任何东西** —— 下一轮我自己去读那个 live 文件。

## 4. 已知的卡死嫌疑（下一份日志直接判定）

| 嫌疑 | 依据 | 判定方式 |
|---|---|---|
| **启动镜像映射** | v0.7.38 死在 mainline CHECK（没走到镜像），v0.7.39 修好后**第一次真正走到**加载 `boot.art/oat/vdex` | live 日志最后若停在 `openat(.../boot.art)` / `mmap` 附近 → 就是它；对策：换基址、或先不放镜像看 ART 是否给出干净错误 |
| linker 配置路径 | 我上一轮加的 `/linkerconfig/ld.config.txt` | 已撤回，本轮若仍卡则可排除 |
| ART 内部线程等待 | `/proc` 里槽位进程已消失、App 无线程阻塞 —— 说明卡在**子进程**里且管道未…… | live 日志能看到它卡前最后做的事 |

## 5. 诚实说明

* 我**没能在容器里复现**这次卡死：设备侧截屏/UI 目标当前不可用（`SCREEN_TARGET_UNAVAILABLE`），
  而卡死本身不留日志；App 进程虽在，但工作线程与槽位子进程都已消失，`/proc` 只能看到 App 自己的 ART 线程。
* 因此本轮交付的是"**让下一次卡死自己说话**"的能力（live 日志 + 看门狗 + UI 不再假死），
  而不是一个已确认修好的卡死根因。
* 探针（`/bin/probe`）仍留在引导链里 —— 它在这两轮都是最有价值的信息源，等这层稳定后再摘掉。
