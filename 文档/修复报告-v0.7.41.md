# TwinVM Stage 4.2 修复报告（第九轮：卡死真因 = msync 无限重试）v0.7.40 → v0.7.41

> 这一轮的现场来自 **v0.7.40 的实时日志**（我上轮加的能力），**不需要你贴任何东西**：
> `/sdcard/Android/data/dev.twinbox.vm/files/twinvm-live.log` —— 8,388,608 B（正好打满我设的 8MB 上限）。
> 这本身就是结论：卡死不是"没输出"，而是**输出暴走**。

## 1. 破案：8MB 日志里 99.5% 是同一行

```
[TwinVM] ENOSYS nr=227(0xe3) — Stage1 未实现 (x8758849)
```
* 归一化统计：131,140 行里 **130,487 行**都是这条（引擎每 64 次打一行 → 实际调用 **约 875 万次**）；
* arm64 **nr=227 = `msync`**；
* 整份日志里缺失的 syscall 只有两个：`msync`(227) 8.7M 次、`userfaultfd`(282) **1 次** ——
  也就是说 ART 其余部分都已经被满足了。

**结论**：ART 走到"加载启动镜像/对映射做 flush"之后，对 `msync` 拿到 `ENOSYS` 就**无限重试**
（它把这个错误当成"稍后重试"），于是槽位进程永远不退出 → 父进程一直读管道 → UI 永久"运行中"。
上一轮 live 日志里那句话（`ART 越走越深 → 卡住`）现在有了确切答案。

## 2. 修复

### 2.1 引擎：实现 `msync`（`core/src/vm_core.c`）

```c
/* v0.7.41：msync（arm64 227 / x86_64 26）直接成功。
 * 真机实锤（2026-10-14 07:12 twinvm-live.log）：ART 对映射调 msync，
 * 拿到 ENOSYS 就无限重试（8.7M 次）。VM 里没有需要真实回写的对象
 * （ROM 只读、映射都是 MAP_PRIVATE），返回 0 语义上安全。 */
case VM_NR_msync:   return 0;
```
* 回归测试进了 `make test`：`vm_memtest` 断言 `msync` 返回 0（不能是 ENOSYS）；
* 顺手确认 `userfaultfd`(282) 只被调 1 次、走默认 ENOSYS 无害（ART 会降级）。

### 2.2 JNI：把"暴走"也纳入卡死判定（`android/jni/twinvm_jni.c`）

上一轮的看门狗只判"**静默** 60 秒"，这次是**持续刷屏**，所以它没触发（只能等总时长上限）。
现在补上：

* **控制台累计超过 6MB → 直接判定"日志暴走（极可能某 syscall 无限重试）"**，强杀槽位、立刻交回 UI；
  正常一整轮自检的输出约 0.5MB，6MB 是安全阈值；
* 总时长上限 300s → **120s**；
* live 日志上限 8MB → 4MB（够定位，又省空间）。

⇒ 以后无论"静默卡死"还是"刷屏暴走"，UI 都会在 1~2 分钟内解冻并给出判定，不会再有假死。

### 2.3 版本与产物

* 版本 **0.7.40 → 0.7.41**（versionCode 63 → 64）；
* `lib/arm64-v8a/libtwinvm.so` = 你的源码 + 全部历史修复（直发护栏/connect/loader 字符串区/execve env/msync）
  + 本轮的暴走判定，60,600 B；
* ROM 不变（64 inode / 53.3MB，`checkrom --strict` PASS）：6 个 boot jar、classpaths、两处 boot 镜像、guest、probe；
* `make -C core test` 全绿（含本轮的 msync 回归）。

## 4. 下一批候选（按可能性）

| 候选 | 说明 |
|---|---|
| 启动镜像映射/重定位 | 这是 msync 之前 ART 正在做的事；如果镜像首选基址与 linker/exe 冲突，ART 会重定位或报 mmap 失败 |
| `/proc/self/maps` | 仍 ENOENT；Art 崩溃时的 `Unwind failed: Failed to parse maps` 靠它 |
| `/dev/__properties__` | 仍 ENOENT；`dalvik.vm.*` 属性全空，ART 会退回推算路径（已铺好） |
| `userfaultfd` 之类单次调用 | 走默认 ENOSYS 即可，除非后续日志显示有重试行为 |
