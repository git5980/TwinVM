# TwinVM Stage 4.2 修复报告（第十轮：ART 已进 Runtime 初始化；补 userfaultfd / proc-stat / 镜像真路径）v0.7.41 → v0.7.42

> 现场仍是我自己取的：`twinvm-live.log`（v0.7.41 那次，58,049 B —— **没有再暴走**）。
> 你只需要"装+点一次运行"，其它我来。

## 1. v0.7.41 的效果：msync 死循环消失，ART 一步跨到 Runtime 初始化

上一轮 8MB 全是 `ENOSYS nr=227(msync)`；这一轮整份日志只有 **2 次** ENOSYS
（`nr=282 userfaultfd` 1 次、`nr=240 mq_open` 1 次），而且 ART 打出了这些：

```
dalvikvm Using CollectorTypeCC GC.
dalvikvm Could not create image space with image file
         '/system/framework/boot.art!/apex/com.android.art/etc/boot-image.prof:
          /system/framework/boot-framework.art!/system/etc/boot-image.prof'
dalvikvm Could not reserve sentinel fault page
dalvikvm FaultHandler: MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED failed: 38
couldn't open /proc/self/stat: No such file or directory
ENOSYS nr=240(0xf0)   ← 之后静默（这次是"静默卡死"，看门狗 30s 会兜住）
```

**三条金信息**：

1. **启动镜像的真路径是 `/system/framework/boot.art`** —— 既不是 `/system/framework/arm64/`，
   也不是 `/apex/com.android.art/javalib/`。为什么没有 `arm64/` 这一层？
   因为**属性区缺失**（`/dev/__properties__` ENOENT），ART 拿不到 `ro.product.cpu.abi`，
   只能退回 isa-less 路径。日志直接把答案写在脸上了。
2. `userfaultfd` 被调了一次就 ENOSYS —— ART 的 **CC GC / FaultHandler** 正需要它；
   而 `MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED failed: 38` 说明这条 membarrier
   命令连内核都不支持（membarrier 本来就在放行清单里，不是我们的问题）。
3. `couldn't open /proc/self/stat` —— ART 初始化时要读它做 CPU/线程统计。

## 2. 本轮修复（v0.7.42）

| # | 改动 | 说明 |
|---|---|---|
| 1 | **`userfaultfd` 进 BPF 放行清单** | arm64 282 / x86_64 323（`gen_bpf.py` 的 `ALWAYS` + 号表；放行清单 41 项）。ART 用 `UFFD_USER_MODE_ONLY`，非特权也能成功 → CC GC/FaultHandler 有机会正常起来 |
| 2 | **合成 `/proc/self/stat`** | 按 proc(5) 格式生成一行（pid/comm/state/…），ART 不再报 "couldn't open" |
| 3 | **补上镜像真路径** | ROM 里同时放 `/system/framework/boot.{art,oat,vdex}`（日志实证的路径）＋ 原 `/system/framework/arm64/` ＋ `/apex/.../javalib/` 三份，谁对都能中 |
| 4 | JNI 看门狗静默阈值 60s → **30s** | 这次是"静默卡死"，30 秒无输出就判死、强杀、交回 UI |

RM 现状：**67 inode / 58.3 MB**，`checkrom --strict` PASS。

## 4. 下一步

装 **v0.7.42**（同签名覆盖）→ 点「运行」。看门狗 30s 内会给结果，live 日志我下轮自己取。

预期/候选：
* `userfaultfd` 通了之后，`Could not reserve sentinel fault page` 那条应该不再致命（sentinel 页是
  userfaultfd 不可用时的**退路**；而这台机器的 app 地址空间被 ART 自己占着，退路本来就很难成）；
* 若还卡在 image space：那就要面对"**镜像映射进 guest 地址空间**"这个硬骨头
  （镜像有首选基址，而 guest 与宿主 App 共用一个地址空间）——对策是给 ART 传 `-Ximage:` 明确位置，
  或把镜像映射改成引擎侧代劳；
* `/dev/__properties__` 缺失导致 ART 各种"猜默认值"（比如本次的 isa-less 镜像路径）。
  如果后面被属性卡住，可以考虑给引擎加一个**最小属性区**（只答 ART 实际会读的那几个：
  `ro.product.cpu.abi` / `ro.build.version.sdk` / `dalvik.vm.*`）。
