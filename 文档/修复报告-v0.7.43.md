> 现场仍是我自己读的 `twinvm-live.log`（v0.7.42 那次，58,172 B —— 依旧没有暴走）。

## 1. v0.7.42 的效果（两条修复都生效了）

```
MMAP_TRYLOCK is not supported in uffd addr:0x7302ed5000 page-size:4096
Using CollectorTypeCMC GC.            ← 上一轮是 CollectorTypeCC；userfaultfd 通了，ART 换用 CMC GC
Could not reserve sentinel fault page  ← 仍有，但它只是 uffd 的退路，不再致命
Could not create image space with image file '/system/framework/boot.art!…'  ← 镜像在，但"创建 image space"失败
FaultHandler: MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED failed: 38          ← 内核不支持该命令（无害）
openat("/proc/self/stat") -> fd=10060 [合成 168B]                          ← ✅ /proc/self/stat 合成生效
openat("/proc/self/maps") -> ENOENT                                        ← ❌ 新缺口
couldn't open /proc/self/maps: No such file or directory
ENOSYS nr=240(0xf0)  ×1                                                    ← 之后静默卡死
```

* ✅ **userfaultfd 放行生效**：ART 的 GC 从 `CollectorTypeCC` 切到 `CollectorTypeCMC`，`ENOSYS nr=282` 消失；
* ✅ **`/proc/self/stat` 合成生效**：`fd=10060 [合成 168B]`，那句 "couldn't open" 消失；
* ❌ **新瓶颈 = `/proc/self/maps`**：ART 的 unwinder 要靠它把 PC 映射到具体文件，
  bionic 的 `pthread_getattr_np` 要靠它找线程栈边界；打不开就静默卡住。

## 2. 本轮修复：合成 `/proc/self/maps`（v0.7.43）

引擎里"替 guest 干的映射活"本来就是它最清楚的，现在全部登记下来并渲染成 Linux maps 文本：

| 登记点 | 内容 |
|---|---|
| `vm_loader_exec_dyn` | exe（`/system/bin/dalvikvm`）、linker（`/system/bin/linker64`）、新栈 `[stack]` |
| ROM 虚拟 fd 的 `mmap` 分支 | 每个 .so 的真实映射（路径取自 VFS 里的 guest 路径，如 `/system/lib64/libart.so`） |
| 匿名 `mmap` 透传后 | 按返回值登记（ART 自己的堆/线程栈等） |

渲染格式与 Linux 一致（`addr-perm offset dev inode path`），按地址排序，上限 128 条。
打开 `/proc/self/maps` 时走既有的"合成 fd"通道（与 cmdline/stat 同一机制）。

**回归**：新增 `core/tests/maptest.c` 并挂进 `make test` —— 用真实 ROM 跑
`openat(/proc/self/maps)` → `read()`，断言：能打开、有内容、含已登记的 `libart.so`、
含 `[stack]`、权限字段格式正确。实测输出：

```
100000-104000 r-x- 00000000 00:00 0 /system/lib64/libart.so
7f0000000000-7f0000100000 rw-- 00000000 00:00 0 [stack]
```

## 4. 下一轮看点

* `/proc/self/maps` 打开后，ART 的 unwinder/线程信息应当能正常取到 → 有望继续往下走；
  如果它开始**依赖 maps 的内容**（比如要求某段地址确实可执行/可读），
  那么后面可能要给引擎加"映射登记与真实布局一致性"校验（我会按日志里它读到的行来对）；
* `Could not create image space with image file '/system/framework/boot.art!…'`：
  镜像文件是在 ROM 里了，失败发生在**创建 image space**（映射/基址）阶段 ——
  这与"guest 和宿主 App 共用地址空间"有关（镜像有首选基址）。如果后面卡在这里，
  对策是给 ART 传 `-Ximage:` 明确位置，或由引擎代劳映射；日志里会先出现它 open 镜像的行，能直接分辨；
* `/dev/__properties__` 仍缺（ART 因此走了 isa-less 的镜像路径、以及一堆默认值）：
  真被属性卡住时，可给引擎加**最小属性区**（只答 `ro.product.cpu.abi` / `ro.build.version.sdk` / `dalvik.vm.*`）。
