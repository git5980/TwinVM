# TwinVM Stage 4.2 修复报告（第十二轮：maps 里必须有"当前线程的栈"）v0.7.43 → v0.7.44

> 现场：`twinvm-20261014-074726.log`（v0.7.43 那次，**完整落盘** —— 因为看门狗按设计把它结束了）。

## 1. v0.7.43 的效果

```

stack not found in /proc/self/maps                              ← ❌ 新错误（来自 guest 的 libc）
ENOSYS nr=240 ×1
[TwinVM] !! 看门狗：30 秒无任何控制台输出（累计 30 秒）——判定卡死，已强杀槽位。
[TwinVM] guest 槽位退出: code=127（被看门狗强杀 = 卡死，不是崩溃）   ← 看门狗也按设计工作了 ✅
```

**新瓶颈**：`bionic` 的 `pthread_getattr_np()` 要在 `/proc/self/maps` 里找
**"包含当前线程栈指针的那条映射"** 来推线程栈边界；找不到就报
`stack not found in /proc/self/maps`，ART 随即静默卡死。

而我上一版登记的映射表**只有 128 条并被填满**，淘汰策略是最旧的先走 ——
于是 exe/linker/[stack] 这些"命根子"被 ART 后来创建的大量匿名映射挤掉了。

## 2. 本轮修复（v0.7.44）

1. **`VmCpu.guest_sp`**：引擎每次进 SIGSYS handler 都记下 guest 的 SP；
2. **maps 表扩到 256 条 + "只淘汰匿名项"**：有名项（exe / linker / `[stack]` / 各 `.so`）不再被挤掉；
3. **渲染时按需兜底**：若当前 SP 不被任何已登记映射覆盖，就补一条 3MB 的匿名 `[stack]` 区
   —— 保证 `pthread_getattr_np` 一定能找到栈。
4. 回归：`core/tests/maptest.c` 增加两条断言（maps 里出现 `[stack]`；确有映射覆盖设定的 SP），已挂进 `make test`。

## 4. 下一轮看点

* 栈边界拿到后，ART 的线程/异常处理应当能继续；如果 `Could not create image space` 变成阻塞点，
  就轮到"镜像映射进 guest 地址空间"这块（对策：传 `-Ximage:` 或引擎代劳映射）；
* `/dev/__properties__` 仍缺 —— 必要时给引擎加**最小属性区**（只答
  `ro.product.cpu.abi` / `ro.build.version.sdk` / `dalvik.vm.*`）。
