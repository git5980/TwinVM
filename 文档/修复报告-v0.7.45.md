# TwinVM Stage 4.2 修复报告（第十三轮：/proc/self/stat 的 startstack —— "stack not found" 真因）v0.7.44 → v0.7.45

> 现场：`twinvm-20261014-075658.log`（v0.7.44）。maps 已经能出 256 条（18,391B），但 bionic 依旧
> `stack not found in /proc/self/maps`。于是这回我直接反汇编 guest 的 libc 找判据。

## 1. 反汇编 libc：bionic 根本不"直接扫 maps"

`__find_main_stack_limits(uintptr_t*, uintptr_t*)`（libc.so:0x9a618）干的是：

1. `fopen("/proc/self/maps")` 之前，先 `fopen("/proc/self/stat")` 并用**固定格式**解析：
   ```
   " %*c %*d %*d %*d %*d %*d %*u %*u %*u %*u %*u %*u %*u %*d %*d %*d %*d %*d %*d
     %*u %*u %*d %*u %*u %*u %lu"
   ```
   抓的是**第 28 字段 `startstack`（主线程栈起点）**（proc(5) 字段序：… 26 startcode, 27 endcode, **28 startstack**）；
2. 再打开 `/proc/self/maps`，找**包含 startstack 的那个区间**当栈边界；
3. 找不到才报 `stack not found in /proc/self/maps`（字符串在 libc.so:0x1eece）。

也就是说：**我上一版合成的 `/proc/self/stat` 把第 28 字段写成了 0** →
startstack=0 → maps 里不可能有区间包含 0 → 永远报"找不到栈"→ ART 静默卡死。

（这也是为什么"SP 兜底"没用：bionic 压根没走"找包含 SP 的映射"这条路。）

## 2. 本轮修复（v0.7.45）

1. 引擎记录 **guest 主线程栈基址**：`vm_loader_exec_dyn` 建新栈时调用
   `vm_set_guest_stack(stk, 1MB)`（同时仍登记 `[stack]` 映射）；
2. `/proc/self/stat` 合成改为**严格按 proc(5) 字段序**输出 55 个字段，
   其中 **第 28 字段 = 主栈基址**（没有记录时退回"当前 guest SP 页对齐"）；
   日志里能看到 `startstack=0x...`；
3. 回归（`core/tests/maptest.c`）**完整复刻 bionic 的解析流程**：
   读 stat → 用它那条 sscanf 取 startstack → 到 maps 找包含它的区间。实测：
   ```
   [TwinVM] openat("/proc/self/stat") -> fd=10062 [synth 163B, startstack=0x7f2000000000]
   bionic 式解析: 返回 1, startstack=0x7f2000000000（期望 0x7f2000000000）
   [ OK ] 第 28 字段 startstack == guest 主栈基址
   [ OK ] maps 里存在包含 startstack 的区间（bionic 找栈边界成功）
   ```
   同时保留上一轮的 SP 兜底与"只淘汰匿名项"策略。
