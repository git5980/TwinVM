# TwinVM Stage 4.2 修复报告（第十四轮：静默 SIGSYS 死亡 → 加黑匣子）v0.7.45 → v0.7.46

> 现场：`twinvm-20261014-080516.log`（v0.7.45）。

## 1. v0.7.45 的效果：栈问题彻底解决

```
openat("/proc/self/stat") -> fd=10060 [synth 257B, startstack=0x71ecb64000]   ← ✅ 字段对了
openat("/proc/self/maps") -> fd=10060 [synth 18386B, 256 maps]                ← ✅
stack not found in /proc/self/maps  →  出现 0 次                              ← ✅ 彻底消失
ENOSYS                              →  0 次                                   ← ✅
```
ART 还多打了一条 **性能类**警告（不是错误）：
```
dalvikvm Bump pointer space is not aligned to 2048KB. This can lead to longer
         stop-the-world pauses for compaction
```
—— 说明它已经在**建堆/分配空间**了（地址空间对齐受限，VM 里正常）。

## 2. 新情况：静默死亡 / 静默卡死，且日志看不到现场

* 本次是 `code=-31`（**SIGSYS**），而且是在"完全静默"的窗口里死的；
* 查日志发现：**引擎的 TRAP 探针打印上限是 512 条**，而日志最后一条正好是 `TRAP#512`
  —— **512 之后的 syscall 全被吞掉了**，死亡现场自然无从查起；
* logcat 里也没有任何 seccomp / SIGSYS / tombstone 痕迹（子进程死于 SIGSYS 不会留 tombstone）。

## 3. 本轮修复（v0.7.46）：两个"黑匣子"

1. **TRAP 探针上限 512 → 4096**：不再有"死亡恰好发生在 512 之后就看不着"的盲区；
2. **卡死/静默期黑匣子**（JNI）：轮询超时后每 2 秒把**槽位子进程此刻在干什么**抄进日志与 live 文件：
   * `/proc/<pid>/syscall` —— 它正阻塞在哪个系统调用、参数是什么（被过滤器丢弃的 syscall 会显示成 `-1` 挂起态）；
   * `/proc/<pid>/wchan` —— 内核等待点（`futex_wait` / `do_wait` / `pipe_read` …）；
   * `/proc/<pid>/status` 的 `State` / `SigPnd` / `SigBlk` —— **挂起信号里有没有未投递的 SIGSYS**、以及屏蔽位。
   这正好覆盖"SIGSYS 死亡时 handler 根本没跑、引擎无法自述"这种最盲的情形。

## 4. 验证与产物

* `make -C core test` 5 条全绿；`checkrom --strict` PASS；
* `.so` 里确认含黑匣子字符串（`blackbox`），APK 内 `libtwinvm.so` 同样含（3 处）；
* 版本 **0.7.45 → 0.7.46（69）**；ROM 内容不变（67 inode / 58.3MB）。

（说明：本轮我先打出了一个**编译失败仍带旧 .so** 的 APK，已经在导出目录里就地识别并替换成重编后的正确包 —— 现在 `TwinVM/apk/TwinVM-Stage4-v0.7.46-fixed.apk` 里是含黑匣子的 .so。）

## 5. 下一轮

装 v0.7.46 跑一次即可。两种结果都能定位：

* 若再出现 **SIGSYS 静默死亡** → 黑匣子会给出它死前最后的 syscall 号与阻塞点；
* 若 **静默卡死** → `/proc/<pid>/syscall` + `wchan` + `SigPnd` 会直接指出它在等什么
  （例如等一个被丢弃的 syscall 的返回、或在 futex 上等一个永远不来的唤醒）。
