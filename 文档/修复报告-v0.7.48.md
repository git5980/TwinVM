# TwinVM Stage 4.2 修复报告（第十六轮：SIGSYS 是被"内核直接杀" —— 加策略 KILL 探针）v0.7.47 → v0.7.48

> 现场：`twinvm-20261014-081610.log`（94KB，TRAP 打到 #867）＋ 黑匣子输出。**没有新 tombstone**（v0.7.47 的闪退已修好）。

## 1. 黑匣子给出了关键证据

```
[TwinVM] [blackbox] child State:   Z (zombie)          ← 子进程早就死了，父进程却在空等
[TwinVM] [blackbox] child SigPnd:  0000000000000000
[TwinVM] [blackbox] child SigBlk:  7ffffe00bffbfeff    ← 注意：SIGSYS(bit30) 仍处于“被屏蔽”
[TwinVM] [blackbox] child wchan:   0
...
[TwinVM] guest 槽位退出: code=-31（被看门狗强杀 = 卡死，不是崩溃）
```

* 死亡前的最后动作：`openat("/proc/self/maps")` → `fstat` → `read`×2（fd 10060 合成 fd）→ `close` → **然后直接没了**；
* 整份日志 **ENOSYS = 0、迟到 TRAP = 0**，而**死亡那一刻没有任何 TRAP 行**。

**推论**：我们的 SIGSYS handler 根本没被调用，而且当时 SIGSYS 还是被屏蔽的 —— 这两点同时成立，
只有一种可能：**内核用 `SECCOMP_RET_KILL_PROCESS` 直接杀了进程**
（KILL 绕过 handler、也绕过屏蔽位）。而我们的 BPF 里唯一的 KILL 是"架构不匹配"，不可能是它
—— 那就是 **Android App 自己的 seccomp 策略里有 KILL 条目**，而 guest 调到了某个被它 KILL、
却被我们 BPF 放行的 syscall。

## 2. 本轮修复（v0.7.48）

1. **策略 KILL 探针**（`vm_policy_probe()`，在 App 进程里、fork 槽位之前运行）：
   逐个 `fork` 子进程去调用 29 个可疑 syscall（userfaultfd / membarrier / rseq /
   process_vm_readv·writev / msync / mlock / mincore / mbind / perf_event_open / bpf /
   keyctl / splice / clone3 / openat2 / statx / …），**被信号杀掉的就是 App 策略 KILL 名单里的**
   —— 参数随意即可（seccomp 在参数校验之前就判）。结果写 logcat（tag `TwinVM`）+ live 日志。
   只杀子进程，对 App 安全。
2. **父进程处理 `POLLHUP/POLLERR`**：子进程一死立刻收尾（不再空等 30 秒看门狗），
   并且能正确报出"死于信号 X"。
3. **黑匣子补 `SigCgt`**：以后能直接看出"我们的 SIGSYS handler 是不是被换掉了"。

## 4. 下一轮怎么用

装 v0.7.48 → 点「运行」。日志开头会出现一段：

```
[TwinVM] [policy] App 策略 KILL 探针：逐个 syscall fork 子进程试调
[TwinVM] [policy]    userfaultfd(282) -> 安全
[TwinVM] [policy] !! xxx(123) -> 死于信号 31（App 策略 KILL）
[TwinVM] [policy] 共 N 条被 App 策略 KILL（这些 syscall 绝不能让 guest 直接调）
```

拿到这份名单后，**把命中的 syscall 从我们的 BPF 放行清单里摘掉、改成引擎自己处理**
（能伪造的伪造，不能的返回 ENOSYS），guest 就不会再踩到内核那一刀。
