# TwinVM Stage 4.2 修复报告（第十七轮：真凶 = rseq —— App 策略 KILL 名单实测）v0.7.48 → v0.7.49

> 现场：`twinvm-20261014-082224.log`（378KB）＋ 策略探针结果。**没有 tombstone**（不是闪退）。

## 1. 探针一击命中：App 策略 KILL 名单（11 条）

v0.7.48 的策略探针在 App 进程里逐个 fork 子进程试调，结果（logcat tag `TwinVM` / live 日志开头）：

```
[TwinVM] [policy] App 策略 KILL 探针：逐个 syscall fork 子进程试调
[TwinVM] [policy]    userfaultfd(282) -> 安全
[TwinVM] [policy]    membarrier(283) -> 安全
[TwinVM] [policy] !! rseq(293) -> 死于信号 31（App 策略 KILL）        ← ★ 它在我们的放行清单里
[TwinVM] [policy]    process_vm_readv(270) -> 安全
[TwinVM] [policy]    process_vm_writev(271) -> 安全
[TwinVM] [policy]    msync(227) -> 安全
[TwinVM] [policy]    mlock(228) / mlock2(284) / mincore(232) / perf_event_open(241) / bpf(280) -> 安全
[TwinVM] [policy] !! mbind(235) get_mempolicy(236) set_mempolicy(237) migrate_pages(238)
                      move_pages(239) keyctl(250) add_key(248) request_key(249)
                      openat2(437) faccessat2(439) -> 死于信号 31
[TwinVM] [policy] 共 11 条被 App 策略 KILL（这些 syscall 绝不能让 guest 直接调）
```

**这 11 条里，只有 `rseq` 曾被我们的 BPF 放行**（其它 10 条本来就会 TRAP → 引擎回 -ENOSYS）。

**于是死因完全解释得通**：
* `rseq` 是 bionic **每个新线程**都会调用的（`__init_tls`/线程注册）；
* 我们放行 → 它直达内核 → **App 的策略用 `SECCOMP_RET_KILL_PROCESS` 直接杀** →
  绕过我们的 SIGSYS handler（所以**没有任何 TRAP 行**）、也绕过屏蔽位（blackbox 显示 SIGSYS 仍被屏蔽）；
* 表现就是：`openat(/proc/self/maps)` 之后突然 `code=-31`，日志戛然而止。

## 2. 修复（v0.7.49）

1. **`rseq` 从 BPF 放行清单里摘掉**（`core/gen_bpf.py` 的 ALWAYS）；
   之后它会 TRAP → 引擎回 `-ENOSYS` → bionic 按"内核不支持 rseq"正常退化（这是标准路径）；
2. 在生成器里写下**铁律**并列出这 11 条 KILL 名单（任何人都不能再加回去）；
3. **新增权威回归**（`core/tests/bpf_sim.py`）：解析 `VM_BPF_ALLOW_NRS`，
   断言这 11 条 App-KILL syscall **一条都不在放行清单里**。
   * 反向验证：故意把 `rseq` 放回去 → 测试立刻 FAIL 且**只报 rseq**；恢复 → PASS；
   * （顺带踩了两个小坑：注释行里也含这个名字、头文件里有两份名单要按架构挑；
     还有个"局部变量遮蔽了同名函数"的 Python 版遮蔽 —— 都已修正。）
