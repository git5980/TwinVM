# TwinVM Stage 4.2 修复报告（第十八轮：造一个"内核杀不死"的黑匣子）v0.7.49 → v0.7.50

> 现场：`twinvm-20261014-082855.log`（381KB，TRAP 打到上限 **4096**）。

## 1. v0.7.49 之后：还是 `code=-31`，但日志被"噪声"塞满了

```
[TwinVM] [4.2dbg] TRAP#4089 nr=227 pc=0x70e3769a4c a0=0x3e524000 a1=0x1000 a2=0x0 stale=0
[TwinVM] [4.2dbg] TRAP#4090 nr=227 ... a0=0x3e525000 ...
...                                        ← 连续 30+ 条全是 nr=227(msync)，地址每页 +0x1000
[TwinVM] [4.2dbg] TRAP#4096 nr=227 ... a0=0x3e52b000 ...
[TwinVM] guest 槽位退出: code=-31（死于信号 31 = SIGSYS）
```

* ART 在**逐页 flush 一大片内存**（msync，4KB 一页），把 4096 条 TRAP 上限刷满；
* 真正的致命 syscall 落在 **4096 条之后 → 被日志上限吞掉**；
* 而且 App 策略的 KILL **绕过一切 handler**，子进程连遗言都留不下。

## 2. 本轮修复（v0.7.50）：共享内存黑匣子 + 降噪

1. **共享黑匣子**（`VmBlackBox`）：父进程在 `fork()` **之前**用
   `mmap(MAP_SHARED|MAP_ANONYMOUS)` 建一页，子进程 attach 后**每次 syscall** 都往里写
   `(nr, arg0, pc)`（环形 32 条）+ 序号；父进程收尸时把最后 32 次 syscall 倒进日志。
   **内核 KILL_PROCESS 抹不掉共享内存** —— 下一轮无论怎么死，都能看到它死前在调什么。
2. **msync 降噪**：探针打印跳过 `nr=227`（那次逐页 flush 刷了几千行），
   把日志带宽留给真正的现场。
3. 回归：`maptest` 增加黑匣子断言（连做 read/write/execve 后，能从黑匣子尾部读到
   `nr=221 a0=0x33`）——已进 `make test`。

## 4. 下一轮

装 v0.7.50 → 点「运行」。这次日志末尾会多出：

```
[TwinVM] [bb] 子进程最后的 syscall（seq=N，最新在后）:
[TwinVM] [bb]   nr=63   a0=0x...       pc=0x...
[TwinVM] [bb]   nr=227  a0=0x...       pc=0x...
[TwinVM] [bb]   nr=XX   a0=0x...       pc=0x...   ← 这一条就是被 App 策略 KILL 的那个
```

拿到那个号，就能像修 `rseq` 一样处理：**从放行清单摘掉 → 引擎自己回 ENOSYS/伪造**。
（如果号落在我们已放行的集合里，说明还有别的 KILL 条目 —— 我会把策略探针扩到**全量放行清单**，
一次性把交集清空。）

## 5. 这一轮顺带确认的事

* `rseq` 的修复**生效了**：整份日志里 `nr=293` 出现 **0 次** —— 说明 bionic 已经按
  "内核不支持 rseq" 正常退化，它不再触碰那一刀；
* ART 已经走到**逐页 flush 内存**这一步（msync 循环），说明它在做镜像/缓存相关的实际工作，
  比前几轮又深入了一层。
