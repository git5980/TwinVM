# TwinVM Stage 4.2 修复报告（第二十轮：真凶第二条 —— set_robust_list）v0.7.51 → v0.7.52

> 现场：`twinvm-20261014-084402.log` + live 日志开头的**全量放行清单审计**。

## 1. 全量审计把最后一条也抓出来了

```
[TwinVM] [policy] 审计放行清单（40 条）：逐条 fork 子进程实测
[TwinVM] [policy]    futex(98) -> 安全          ...（38 条安全）
[TwinVM] [policy] !! set_robust_list(99) -> SIGSYS — App 策略 KILL！必须从放行清单摘掉
[TwinVM] [policy] 放行清单里有 1 条会被 App 策略 KILL
```

**放行清单 40 条里，恰好只有一条会被 App 策略 KILL：`set_robust_list(99)`。**

它为什么致命：**bionic 每个线程初始化都会调用 `set_robust_list`**（告诉内核 robust futex
链表位置）。我们放行 → 直达内核 → App 策略 `KILL_PROCESS` 直接杀 —— 正好解释了
前几轮"日志停在 `/proc/self/maps` 之后、无任何 TRAP 行、`code=-31`"的现象
（那时 ART 正在建新线程）。

## 2. 修复（v0.7.52）

1. **`set_robust_list` 从 BPF 放行清单摘除**（`gen_bpf.py` ALWAYS）；
2. **引擎自己处理它**：新增 `case VM_NR_set_robust_list: return 0;`（x86 273 / arm64 99）——
   它只是"告诉内核 robust futex 链表在哪"，伪造成功即可（bionic 不校验返回值，我们也不需要
   robust futex），比返回 ENOSYS 更稳；
3. **回归名单补上它**：`bpf_sim.py` 的 App-KILL 名单从 11 条扩到 **12 条**
   （rseq / set_robust_list / mbind / … / faccessat2），以后谁再把它加回放行清单，
   `make test` 立刻报错；
4. 顺带修：`VM_NR_set_robust_list` 的编号要定义在 `vm_core.c`（这个文件里放编号表，
   不是头文件）—— 第一次加错了位置，编译期直接报出来。

## 3. 验证

$ 生成器：x86_64 41 项 / arm64 39 项（set_robust_list 已摘除）

版本 **0.7.51 → 0.7.52（75）**；ROM 不变（67 inode / 58.3MB）。

## 4. 意义：这一类故障可以判定为"清零"

审计是**全量**的（40 条一条不漏），现在的结果是：

* 放行清单里 **0 条**会被 App 策略 KILL；
* 已知的 12 条 KILL syscall 全部有回归保护；
* 引擎对 `rseq`、`set_robust_list` 这类"内核要杀但我们用不着"的调用改成自己伪造/退化。

也就是说：**"无痕 SIGSYS（code=-31）"这一类故障，至此应当消失**。
下一轮如果还出现 `code=-31`，黑匣子（共享内存版）会直接把死前 syscall 序列摆出来，
而且不会再出现"放行清单里的漏网之鱼"这种情形。
