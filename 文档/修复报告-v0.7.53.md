# TwinVM Stage 4.2 修复报告（第二十一轮：让引擎能自查 handler，并补审"参数化放行")v0.7.52 → v0.7.53

> 现场：`twinvm-20261014-084718.log`（92KB）。

## 1. v0.7.52 之后：还是 `code=-31`，黑匣子尾部一模一样

```
[bb]   nr=56 openat(AT_FDCWD) → nr=80 fstat → nr=63 read → nr=57 close
[bb]   nr=56 / 80 / 63 / 63 / 57          ← 第二次（maps）
[bb]   nr=57  close  a0=0x274c            ← 最后一条，之后进程消失
guest 槽位退出: code=-31
```

也就是说：致命 syscall **仍然被我们的过滤器放行**（放行=原生执行=引擎看不到）。

但 v0.7.51 的全量审计只覆盖了 `VM_BPF_ALLOW_NRS`（无条件放行清单，39 条）。
我们的 BPF 还有一类**按参数放行**的规则 —— 它们同样"原生执行、不经引擎"，
审计没覆盖到：

| 规则 | 放行条件 |
|---|---|
| `write` / `read` / `close` / `ioctl` | fd 是真实内核 fd（3..9999），或 write 写 console |
| `socket` | family == AF_UNIX(1) |
| `connect` | fd 在 3..9999 |
| `pread64` | fd < 10000 |
| `mmap` | 匿名 / fd 不在虚拟区间 |
| `rt_sigaction` | sig != SIGSYS(31) |

## 2. 本轮（v0.7.53）做了两件事

### (a) 让引擎能**自查 SIGSYS handler 是否还在**

致命 syscall 没有 TRAP 行，只有两种可能：**内核直接 KILL**，或**我们的 handler 被换掉**
（处置权落到 SIG_DFL 或别人手里）。后者可以自证 —— 但以前做不到，因为
`rt_sigaction(sig=31)` 被 BPF **无条件** TRAP（这是 v0.7.6 保护 handler 的设计）。

现在把规则细化：**sig==31 且 `act==NULL`（纯查询）→ 放行；只有"安装企图"才 TRAP**。
于是引擎每 8 次 TRAP 就向内核问一次当前 SIGSYS 处置，一旦发现不是我们的 handler：

```
[TwinVM] !! SIGSYS handler 被替换：当前=0x... 我们=0x... —— 下一个 TRAP 必死（这就是 code=-31 的真因）
```

这一条会**决定性**地区分"handler 被换"与"内核直接杀"，不用再猜。

### (b) 审计补上"参数化放行"名单

`write(64) writev(66) read(63) close(57) ioctl(29) socket(198) connect(203)
 pread64(67) mmap(222) rt_sigaction(134) fstat(80) openat(56)`
——逐条 fork 子进程实测，命中 SIGSYS 就标明"App 策略 KILL"。

$ 生成器：BPF 指令数 arm64 145（+4：rt_sigaction 查询分支）；条数 39 项

## 4. 下一轮怎么读结果

装 v0.7.53 → 点「运行」，日志里会出现：

* 若 **handler 被替换** → 直接打出"当前=… 我们=…"，那就是真因，对策是：
  让 BPF 彻底堵死 SIGSYS 处置被更改的所有路径（含 `sigaction` 的 *查询+安装* 组合、
  `clone(CLONE_CLEAR_SIGHAND)`、`execve` 之后重装 handler 等）；
* 若 handler **一直在** → 那 `code=-31` 必然是**内核直接 KILL**，
  这时看审计里有没有新的 `!!`（参数化名单），有就直接摘掉/接管它；
* 两条线索合起来，就能把 `code=-31` 这条线彻底钉死。
