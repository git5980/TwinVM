# TwinVM Stage 4.2 修复报告（第二十二轮：我上一轮把 SIGSYS 保护改漏了 —— 已修并离线钉死）v0.7.53 → v0.7.54

> 现场：`twinvm-20261014-085217.log` —— **只有 3KB**（上一轮 92KB），槽位在第 14 个 syscall 就死。

## 1. v0.7.53 引入的回归（我的错）

为了让引擎能自查"handler 是否还在"，我把 BPF 里 `rt_sigaction` 的规则细化了：

```
LD nr ; JEQ rt_sigaction → 顺序
LD 16 (sig) ; JEQ 31 → 继续查 act ; 否则 → RET ALLOW
LD 24 (act) ; JEQ 0 → ALLOW（纯查询）; RET TRAP（安装企图）
```

**跳转偏移算错一位**：`JEQ 31` 的"不相等"分支我按 `jf = skip_to - (i+1)` 算，
而 `skip_to` 就是紧邻的下一条 `RET ALLOW` → 结果是 **`jf = 0`，等于"直接落到下一条"，
也就是 `sig==31` 也落进了 `RET ALLOW`** —— **任何程序都能把我们 SIGSYS handler 换掉**。

后果与真机现象完全吻合：

```
[TwinVM] [bb] 子进程最后的 syscall（seq=13，最新在后）:
[bb]  ... nr=48 sigaltstack / 120 gettimeofday / 79 newfstatat / 56 openat / 64 write×4
[bb]  ... nr=48 / 120 / 79 / 56        ← 正是**链接器**启动阶段
guest 槽位退出: code=-31               ← 链接器把自己 handler 装上后，下一个 TRAP 就要了命
```

## 2. 修复与"离线钉死"（v0.7.54）

1. **修正跳转**：`sig==31` 必须**跳过**那条 `RET ALLOW`（`jt = skip_to+1-(i+1)`），
   `sig!=31` 直接落下命中 `RET ALLOW`；
2. **把这条铁律写进离线回归**（`core/tests/bpf_sim.py`），两种架构 × 四种组合全查：

```
OK rt_sigaction(sig=31,act=NULL) -> ALLOW      （纯查询放行，引擎可自查）
OK rt_sigaction(sig=31,act=ptr ) -> TRAP       （安装企图必须拦截 ← 这次漏的就是它）
OK rt_sigaction(sig=11,act=ptr ) -> ALLOW
OK rt_sigaction(sig=11,act=NULL) -> ALLOW
```

   顺带给模拟器补上 `args[1]`（offset 24）/`args[2]`（offset 32）的读取支持 ——
   以前它遇到未知偏移直接抛错，所以这类改动**离线根本测不到**，这才是漏网的根本原因。

3. **移除 v0.7.53 那个 in-handler `sigaction()` 自查**：信号处理器里调 `sigaction`
   不是异步信号安全的，而且它只能证明"此刻"，证明不了"死的那一刻"。
   改用**父进程读 `/proc/<pid>/status` 的 `SigCgt`**（blackbox 已经在打）——
   僵尸进程该字段仍然保留，直接就能看出 SIGSYS 是否还在"被捕获"位里。

## 4. 教训（写进流程）

**BPF 的任何改动都必须在 `bpf_sim` 里补上对应用例**，而且模拟器要支持新用到的
`seccomp_data` 偏移。上一轮我只在真机上试，结果一个偏移错误就把 VM 的命根子
（SIGSYS 保护）打开了 —— 这类问题离线几秒就能发现。现在 sigaction 四组合已成回归。
