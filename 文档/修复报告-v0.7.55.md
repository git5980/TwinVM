# TwinVM Stage 4.2 修复报告（第二十三轮：SIGSYS 线彻底结束，转到 SIGILL —— 补 i-cache flush）v0.7.54 → v0.7.55

> 现场：`twinvm-20261014-085742.log`（92KB，回到正常体量）。

## 1. 好消息：`code=-31` 那条线**彻底结束**

```
[TwinVM] guest 槽位退出: code=-4（死于信号 4 = SIGILL）      ← 不再是 -31（SIGSYS）
```

结合前几轮的结论（App 策略 KILL 名单里 `rseq` 与 `set_robust_list` 都被摘掉、审计确认
放行清单与 KILL 名单**零交集**），现在**没有"无痕 SIGSYS"了** ——
两轮辛苦的审计确实把那类故障清零了。

## 2. 新瓶颈：SIGILL（非法指令）

* 死亡点仍在 `openat("/proc/self/maps")` 之后；黑匣子尾部同样以 `close(fd=10060)` 收尾
  —— 但 SIGILL **不需要 syscall**，所以黑匣子看不到它是正常的；
* 我们的 `GUEST FAULT` 诊断没打印 —— 因为 **ART 自己会安装 SIGILL 处理器**（它的
  FaultHandler 就是干这个的），把我们的诊断顶掉了。所以只能靠推理 + 实验定位。

**推理**：SIGILL 出现在"ART 刚进 Runtime、第一次大量执行新映射的 ROM 代码"时。
而引擎里映射 ROM 段的路径是：

```c
memcpy((void*)at, ino->map + off, n);      // 写代码
mprotect(at, len, prot);                   // 收紧权限
```

**ARM64 上写完代码必须清 i-cache 才能执行**（否则取指可能命中陈旧字节 → SIGILL）。
引擎里**一处 flush 都没有** —— 这是货真价实的 bug，而且症状完全对得上
（也解释了为什么它是"偶发/靠后"出现：只有某页恰好被取指到陈旧内容才炸）。

## 3. 修复（v0.7.55）

在**所有"写代码"的地方**补 `__builtin___clear_cache`（编译为 `dc cvau` / `ic ivau`）：

| 位置 | 说明 |
|---|---|
| `vm_core.c` ROM 虚拟 fd 的 `mmap` | 每个 `.so` 段映射后：**先 flush → 再 mprotect 收紧 → 再 flush**（标准做法） |
| `vm_loader.c` 静态 exec 段拷贝 | 每个 `PT_LOAD` 段拷贝后 flush |
| `vm_loader.c` 动态 exec（exe/linker） | 同上，覆盖 exe 与 linker64 |

顺带核对了 `AT_HWCAP`：loader 用的是 `getauxval(AT_HWCAP)`（同一颗 CPU 的真实特性），
所以不是"guest 以为支持某指令"的问题 —— 排除法后 flush 是主因。
