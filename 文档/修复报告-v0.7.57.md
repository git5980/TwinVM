# TwinVM Stage 4.2 修复报告（第八轮：v0.7.56 回归真因 = 我构建用了陈旧 ROM）v0.7.56 → v0.7.57

## 1. v0.7.56 真机判读：引擎无罪，ROM 有罪

10:05 的 .log 死得比 v0.7.55 更早（TRAP#11 就没了，v0.7.55 走到 #865）：

```
[guest] execve(/bin/probe -> /system/bin/dalvikvm)...
TRAP#9 nr=221 execve a0=0x202efd
[guest] !! execve 失败 → exit(98)
```

关键线索：**"ROM 66 inodes 就绪"（v0.7.55 是 67）**。

## 2. 根因（逐 inode 对比实锤）

| ROM | inodes | /bin/probe | /bin/guest |
|---|---|---|---|
| 源码包 assets/demo.rom（6e52fb9c） | 66 | **无** | 旧版 2.1MB |
| v0.7.55-fixed APK 内 ROM（fa88cc28） | **67** | **有**（10056 B） | 新版 3.5MB |

**源码 zip 与 -fixed APK 不同步**：DeepSeek 打 -fixed APK 时树里已加上 /bin/probe
和新 guest，但源码 zip 里的 `rom/fixture`、`build_guest64`、build.sh（无 probe 构建步）
都是旧状态。我用源码树构建 v0.7.56 → ROM 缺 /bin/probe → guest 第一个 execve
直接 ENOENT——**与语音盒修改无关**（BPF/ENOSYS 改动本轮在真机上也无事可做，
因为根本没跑到未知 syscall 那一步）。

## 3. 修复（v0.7.57 = 0.7.56 引擎 + 真 ROM）

* `android/assets/demo.rom` ← **fa88cc28**（-fixed APK 内的 67-inode ROM 原样采用）；
* `rom/fixture/android_root` 挪为 `.stale-bak`——防 build.sh 重打覆盖（沿用已有 ROM，
  正是 ROM-使用方法.md 的方案 C）；
* 引擎代码与 v0.7.56 完全一致（BPF 末位 TRAP + ENOSYS 全参数日志 + 铁律 5）；
* 版本 0.7.56 → **0.7.57（80）**（versionCode 递增确保可覆盖安装）。

## 4. 验证

```
$ APK 内 assets/demo.rom md5 = fa88cc28 ✓（与 -fixed APK 逐字节一致）
$ checkrom --strict → PASS（67 inode；6 jar + classpaths/*.pb 全命中）
$ make -C core test → PASS ×5（41/41 [ OK ]）
$ aapt：versionCode=80 versionName=0.7.57 ✓
```
