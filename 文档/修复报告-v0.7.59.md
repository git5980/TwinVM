# TwinVM 修复报告（第十轮：示踪器握手修复 + 扫雷首份地雷图）v0.7.58 → v0.7.59

## 1. v0.7.58 真机判读

**扫雷（部分）立功**——0..181 就炸出 **28 个 App 策略 KILL 号**：
```
18 39 40 42 51 58 89 99 100 104 105 106 112 116 142 143 144 145 146
149 151 152 159 161 162 170 171 180 （死于 31；扫到 181 用尽 25s 预算）
```
关键认知：**未分配的 syscall 号（18/39/40/42/51/58/89…arm64 上根本不存在）也被杀**
→ App 策略是**允许清单制**（不在清单 = 默认 KILL_PROCESS），不是黑名单制。
这解释了整个死因链：任何不在 App 清单里的 syscall，无论我们的过滤器怎么判 TRAP，
多层过滤取最严判决，App 的 KILL 永远赢 → guest 无声死。

同时重大发现：**扫雷的 (0,0,0) 参数会过报**——策略里带参数条件的规则（如
set_robust_list(head, 24) 合法调用 vs (0,0,0) 试探）在 0 参数下落入默认 KILL。
证据：v0.7.52 曾实测 set_robust_list(99) "KILL"，但 guest 活过了 867 次 TRAP
（真参数调用被允许 → 我们的 TRAP 生效 → ENOSYS → bionic 退化）。
**真凶只能靠示踪器的现场（真实参数）点名，扫雷图只是上界。**

**示踪器哑火**——0 个事件、0 控制台输出、bb seq=0、30 秒看门狗击杀。
子进程从未恢复运行：嫌疑锁定在 SIGSTOP **群停点（group-stop）**的重启怪癖
+ ART 进程可能的 SIGCHLD 处理器把阻塞的 waitpid 打成 EINTR（握手没收到停点
就继续，重启命令作用在未停的 tracee 上静默失败）。

## 2. v0.7.59 修复（三处，全在握手链）

| 改动 | 说明 |
|---|---|
| SIGSTOP → `raise(SIGTRAP)` | SIGTRAP 是干净的**信号投递停点**（无群停点重启怪癖） |
| fork 前 `pthread_sigmask` 屏蔽 SIGCHLD | ART 的 ProcessManager 处理器不再能 EINTR 握手/抢收；示踪线程继承屏蔽掩码 |
| 握手全链路落日志 | `[trace] 握手: 停点信号=? setoptions=? 重启=?`——若再失败，日志直接说出哪一步断的 |

扫雷同步提速：单探针超时 3s→1.2s、预算 25s→50s（目标 0..500 跑完全程）、
结果行注明过报警示。waitpid 全部 EINTR 安全重试。

- **语义绕行**：handler 里用允许的等价 syscall 合成该功能。
