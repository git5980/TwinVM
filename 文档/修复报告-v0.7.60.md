# TwinVM 修复报告（第十一轮：示踪器线程模型重构）v0.7.59 → v0.7.60

## 1. v0.7.59 真机判读：握手满分，示踪器零事件——ptrace 的线程铁律

```
[trace] 握手: 停点信号=5 setoptions=0 重启=0 (pid=1473)   ← 三项全对
[sweep] KILL 名单（死于 31）共 104 个（扫到 nr=313，预算用尽）
```

- 握手链（SIGTRAP 停点→SETOPTIONS→PTRACE_SYSCALL）**全部成功**——v0.7.59 的
  停点/信号修复生效；
- 但示踪器依然 0 事件、0 控制台输出、bb seq=0、30s 看门狗击杀——**子进程还是冻死**；
- 扫雷到 313 已 **104 个 KILL 号**（允许清单制进一步坐实；28→104）。

## 2. 根因：ptrace 停点只能被"追踪者任务本人"wait

v0.7.59 的线程布局是"主线程 fork+吞掉握手停点，示踪线程 waitpid(-1) 收事件"。
真机行为证明了两条内核规则同时成立：

1. **ptrace 停点事件只投递给追踪者任务（即执行 fork 的那个线程）**——
   子进程恢复后的第一个 syscall 入口停点，只有主线程能收到；
2. **其它线程的 waitpid(-1) 立刻 ECHILD 返回**（children 是 per-thread 的）——
   示踪线程根本等不到任何事件，直接退出。

于是：子进程停在第一个 syscall 入口 → 示踪线程已经退出 → 没人发
PTRACE_SYSCALL 恢复它 → 冻死 → 看门狗击杀。join 不挂死恰是因为示踪线程
早已 ECHILD 返回——全部现象吻合，无一例外。

## 3. v0.7.60 修复：fork 权移交示踪线程（线程模型重构）

**fork / 握手 / waitpid 等待循环全部收进示踪线程内闭环：**

```
主线程：pipe → 屏蔽 SIGCHLD → 启动示踪线程（带 rom/bb/管道参数）→ sem_wait 等 fork 完成
示踪线程：fork（子进程：关读端→恢复空信号掩码→TRACEME→raise(SIGTRAP)
                     →bb 挂载→guest 开跑）
          ├ 父侧：关写端（唯一一份）→ g_t_pid 就绪 → sem_post → 握手 → 事件循环
```

配套加固：
- TRACEME 失败保护（attach 失败直接 _exit(98)，防 raise(SIGTRAP) 真杀进程）；
- 子进程恢复空信号掩码（去掉继承的 SIGCHLD 屏蔽，guest 看到正常世界）；
- 事件循环收尾非阻塞排空残留 clone 线程事件（防僵尸泄漏）；
- 信号量单次初始化（重复点「运行」安全）；
- 看门狗放宽：静默 30→90s、总时长 120→240s（示踪版每 syscall 两次停点，
  guest 显著变慢——这是诊断版的必要代价）。
