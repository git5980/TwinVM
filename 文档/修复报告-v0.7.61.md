# TwinVM 修复报告（第十二轮：真凶落网——哨兵页与 maps 破坏性渲染）v0.7.60 → v0.7.61

## 1. v0.7.60 真机判读：三大突破

**突破一：老无声死点已越过。** guest 跑过 v0.7.55/57 的死点（close(maps) 之后
又活了 30+ 条 TRAP，深入到 nativeloader）——ptrace 示踪版跑通。

**突破二：死因变成 ART 自 abort（code=127）**，且 abort 消息完整可见：
`runtime.cc:719] Runtime aborting...` + 全线程 dump。真凶（追溯四个版本的共同死因）：

> **"Could not reserve sentinel fault page"（runtime.cc:1852，PLOG FATAL）**

**突破三：语音盒开箱**——`ENOSYS nr=141`（getpriority）与 `ENOSYS nr=240`
（rt_tgsigqueueinfo，ART abort 的 SIGABRT 发送）都被日志点名。

## 2. 反汇编定位（ROM 内带符号 libart/libartbase 实锤）

sentinel 的调用链（libart.so `Runtime::Init` → libartbase.so `MemMap::MapAnonymous`）：

```
MapAnonymous("sentinel fault page",
             expected_ptr = (-count) & 0xEBAD6070,   ← AOSP 著名毒地址！
             count = 一页, prot = PROT_NONE,
             flags = 0x22 = MAP_PRIVATE|MAP_ANONYMOUS，**无 MAP_FIXED**)
```

- `0xebad6070` 就是 tombstone 里常见的 ART 毒地址；页对齐后 = **0xebad6000**；
- **这是 hint mmap，必须拿到精确地址**——而 fork 继承的地址空间里，
  **宿主 App 自己的 ART 早已把 0xebad6000 保留为它自己的哨兵页**；
- 内核于是给了别的地址 → `Failed to mmap at expected address` → MemMap 无效 →
  PLOG(FATAL) → abort → `rt_tgsigqueueinfo(self, SIGABRT)`（nr=240）→
  我们的 handler 回 ENOSYS → ART 走 exit(127) 兜底。

v0.7.55/57 的"close 后无声死"就是同一 abort 链的另一种死法（abort 早期路径
被 App 策略 KILL）；v0.7.60 示踪器让它现形。**四个版本一个凶手。**

## 3. 顺手破的第二个案子：maps 合成 52B 劣化

`vm_render_maps` 用 **len=0 当"已输出"标记**（惰性选择排序）→ 渲染一次就把
整张 256 条的 map 表抹掉 → 第二次 openat("/proc/self/maps") 只剩兜底 [stack]
一行 52B（v0.7.60 日志：18379B → 52B → 52B 实锤）→ abort 的 unwinder
"Failed to parse maps"。任何第二次读 maps 的组件都会拿到残废数据。

## 4. 修复（v0.7.61，三处）

| 改动 | 位置 | 说明 |
|---|---|---|
| **释放哨兵页** | 子进程 fork 后 `munmap(0xebad6000, 0x1000)` | fork 地址空间独立，只影响本槽位，宿主无感。guest 的 hint mmap 从此能拿到精确地址 |
| **maps 非破坏性渲染** | `vm_render_maps` 用 `done[]` 位图替代 len=0 标记 | 第二次及以后读 maps 拿到完整 256 条 |
| **getpriority(141)** | handler 新 case，返回 0（nice 0） | ART 线程 dump 用 |
| stat 格式串 UB 修复 | /proc/self/stat 合成 55 转换符对齐 55 实参 | v0.7.58 遗留警告清零 |
