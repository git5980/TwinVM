# TwinVM 修复报告（第十三轮：fcntl 虚拟 fd 路由——jar 读废真因）v0.7.61 → v0.7.62

## 1. v0.7.61 真机判读：哨兵页已灭，新卡点=fcntl EBADF

v0.7.60 的修复**全部生效**：

| 修复 | 验证 |
|---|---|
| 哨兵页释放 | "Could not reserve sentinel fault page" **消失**（0 次出现，v0.7.60 为 1） |
| maps 非破坏渲染 | 两次读都是 18398B/256 条（v0.7.60 第二次只剩 52B） |
| getpriority(141) | 线程 dump 的 nice 读取正常服务 |

guest 走得比任何版本都深：Runtime::Init 后段（isSwordfish 属性检查、
nativeloader 初始化都过了）。但依然 abort（code=127），且这次 abort 原因
没有走任何可见通道（fd3/logd 只收到了两条早期 linker 警告）。

## 2. 从消息链拼出真凶：fcntl(10000, F_GETFD) → EBADF ×5

语音盒（writev 正文解码）完整消息链：

```
MMAP_TRYLOCK uffd 警告（非致命）
Using CollectorTypeCMC GC（堆初始化 ✓）
Could not create image space ... Image component
  /system/framework/boot-framework.art does not match a boot class path component
fcntl(10000, F_GETFD) failed: Bad file descriptor ×5   ← ★ 新卡点
isSwordfishLaunchAppEnabled_ 0 ...
Failed to read /system/etc/public.libraries.txt（非致命）
→ 线程 dump（sched_getscheduler/getparam/getpriority 全部正常服务）
→ Runtime aborting... → exit(127)
```

因果链：**fcntl 在 BPF 放行清单 → 原生直发内核 → 内核不认识虚拟 fd 10000 →
EBADF → libziparchive 打不开 boot classpath 的 5 个 jar → "Image component
does not match"（校验和读不出来=不匹配）→ imageless 回退 → 后续 ClassLinker
真需要 jar 内容时 CHECK 失败 → abort**。

消息出处定位：`fcntl(%d, F_GETFD) failed` 字符串在 ROM 的 libartbase.so 里。

## 3. 修复（v0.7.62）

| 层 | 改动 |
|---|---|
| **BPF**（gen_bpf.py） | fcntl 从 ALWAYS 放行清单除名 → **fd 参数化**：真 fd（3..9999 含 console）→ ALLOW 原生；虚拟 fd（≥10000）→ TRAP；stdio（0/1/2）→ TRAP |
| **handler**（vm_core.c） | 三层路由：虚拟 fd → **伪造成功**（F_GETFD/F_SETFD/F_GETFL/F_SETFL/锁全 0；F_DUPFD(_CLOEXEC) → 真 VFS dup 槽位复制）；stdio → 伪造（绝不直发=防二次 TRAP 铁律）；真 fd → VM_PT4 直发 |
| 直发表 | fcntl 移出 vm_passthrough_nrs（改由 auto-scan fd=5 路径验证） |

安全语义不变：虚拟 fd 的 fcntl 从"交给内核（EBADF）"变成"handler 全权应答"，
防逃逸不降级。
