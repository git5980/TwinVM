# TwinVM 修复报告（第十四轮：maps perms 严格解析 + 示踪器 0x80 停点）v0.7.62 → v0.7.63

## 1. v0.7.62 真机判读：fcntl 修复生效，但 abort 原因不可见

**fcntl 三层路由完全生效**：5 个 boot classpath jar 被完整读取
（lseek/read/fstat/pread64/mmap 循环 + fcntl(F_GETFD/F_SETFD) 全部成功，
v0.7.61 的 "fcntl(10000) failed: Bad file descriptor ×5" 彻底消失）。

guest 走到**历史最深**：Runtime::Init 后段 → imageless 回退 → **5 个 jar
的 ClassLinker 加载**（TRAP#878-970 完整 dex 读取循环）→ isSwordfish 二次
检查 → nativeloader 初始化 → **abort（code=127）**。

## 2. abort 原因的追查（全渠道扑空）

- writev(fd83/logd)：10 条全列出（CMC GC → image space → bump pointer →
  membarrier → isSwordfish×2 → nativeloader → Runtime aborting dump）——
  **CHECK 理由行不在其中**；
- write(fd2/stderr)：15 条全列出（linker 警告×8 + public.libraries 警告）——
  **也不在**；
- 反汇编确认 GOT 符号：`android::base::StderrLogger` 被注册为 logger
  （Runtime::Init 745f60 SetLogger），理论上 CHECK 理由应走 fprintf(stderr)
  → 但 bionic stderr 每条都是 write(2) TRAP——没出现；
- 结论：abort 是"裸 abort"（无消息或消息进了不可见通道），**必须靠
  native 栈指认凶手**。

## 3. 两把新刀（v0.7.63）

### 刀一：maps perms 第 4 位 'p'——让 abort dump 能 unwind

abort dump 里的 "Unwind failed for thread 8316: **Failed to parse maps**"
是本轮最大线索：unwinder 读到了完整 18398B maps 却解析失败。
对比真内核 maps 发现我们的缺陷：

```
真内核：722f000000-722f001000 rw-p 00000000 00:00 0 [anon:.bss]
我  们：100000-104000        r-x- 00000000 00:00 0 /system/lib64/libart.so
                                      ↑ 第 4 位：真内核只有 'p'/'s'，我们写 '-'
```

Android 16 的 libunwindstack 已 **Rust 化**（.so 里带 rustlib 路径实锤），
严格解析器对 perms 第 4 位非法字符直接判整个 maps 解析失败。
修复：`perm[3] = 'p'`（我们所有映射都是 MAP_PRIVATE）+ 空 path 不写尾随空格。

**修好后 abort dump 将打出带函数名的 native 栈——CHECK 原因就算不打印，
栈帧（函数名+file:line）也会直接指认凶手。**

### 刀二：示踪器 0x80 停点修复——完整 syscall 流水

v0.7.62 的示踪器握手 5/0/0 成功却 0 事件。根因（ptrace 规则）：
**syscall-entry/exit 停点的 wait 状态是 `(SIGTRAP|0x80)<<8`，WSTOPSIG 返回
0x85 而非 5**。旧代码 `sig == SIGTRAP` 漏掉所有 syscall 停点，还把它们当
真信号"转发"注入 signal 133（内核恰好丢弃未致命，纯属侥幸）。

修复：三分支——`SIGTRAP|0x80`（GSI 记 entry，吞掉续跑）/ `SIGTRAP`
（PTRACE_EVENT，不注入续跑）/ 其它（真信号，转发）。
