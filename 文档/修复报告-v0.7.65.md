# TwinVM 修复报告（第十六轮：三版 0 事件总根因——TRACESYSGOOD）v0.7.64 → v0.7.65

## 1. v0.7.64 真机判读：代码全对，但开关没开

- GSI 结构体 88B 已就位（.so 字节级验证：cmp #0x85 @0xe0e8、movz w2,#0x58 @0xe100）
- 但依然 **0 事件**，且这次 guest **卡死**（code=-9，看门狗 90s 强杀）
  ——冻结点：TRAP#860，"Using CollectorTypeCMC GC" 的 writev(83) 之后
  （比 v0.7.63 的 abort 点更早，说明卡死/abort 是 ART 启动的非确定性分支，
  与本轮代码无关）。

## 2. 总根因（三版 0 事件的唯一解释）

> **`PTRACE_O_TRACESYSGOOD` 没有设置！**
>
> ptrace 规则：不设 TRACESYSGOOD，syscall-entry/exit 停点报告为**纯
> SIGTRAP(5)**，而不是 SIGTRAP|0x80(0x85)。

于是 v0.7.63 的 0x85 分支永远等不到；5 号分支（PTRACE_EVENT/真 SIGTRAP）
把所有 syscall 停点**静默吞掉续跑**——guest 正常跑（无害），但一个事件
都不记录（无观测）。v0.7.63 报告里"注入 signal 133"的推断是错的：
0x85 从未出现过。

## 3. v0.7.65 修复

```
SETOPTIONS: TRACECLONE → TRACECLONE | TRACESYSGOOD | EXITKILL
```

- **TRACESYSGOOD**：syscall 停点带上 0x80 位 → 0x85 分支终于开工 →
  GSI → `[trace] #N tN nr=… a0/a1/a2` 完整 syscall 流水；
- **EXITKILL**：示踪线程若死，槽位自动 SIGKILL（防冻尸——本轮卡死
  场景的护栏）。

## 4. 验证

```
$ make -C core test → 41/41
$ checkrom --strict PASS；ROM md5=fa88cc28 未动
$ aapt：versionCode=88 versionName=0.7.65
```

## 5. 下一轮（读法）——这次真的能看见了

装 v0.7.65 → 运行 → 双日志发回：

1. `[trace] #1 … #N` syscall 流水（含参数）——无论 guest 是 abort 还是
   卡死，**死前最后 40 个 syscall 都在环形缓冲里**（★ 行点名）；
2. 卡死场景：最后一条 trace = 冻结的 syscall 号（futex？poll？）——
   卡死之谜同场破案；
3. abort 场景：native 栈 + 流水双证据 → 反汇编 abort 点（libart+0x80caf4
   区）→ 动刀。

`hello TwinVM from ART` 仍是本轮视野内的目标。
