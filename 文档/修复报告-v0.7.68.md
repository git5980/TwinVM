# TwinVM 修复报告（第十九轮：**我上一版的探针把 App 自己杀了** —— 已修）v0.7.67 → v0.7.68

> 现场：`twinvm-20261014-184524.log` + `tombstone_31`（18:44:57）

## 1. v0.7.67 的探针结果 & 一个天大的乌龙

**探针跑完了**（结果有效）：

```
[TwinVM] [policy] (zygote) sched_setattr(274) -> 信号 0        ← ★ 安全的！
[TwinVM] [policy] (zygote) io_uring_setup(426/427) -> 信号 31
[TwinVM] [policy] (zygote) kcmp(272) lookup_dcookie(18) mount(40) umount2(39)
                           swapon(224) swapoff(225) reboot(142) kexec_load(104)
                           init_module(105) finit_module(273) delete_module(106)
                           open_by_handle_at(265) name_to_handle_at(264) -> 信号 31
（userfaultfd / memfd_create / perf_event_open / bpf / setns / unshare /
  ptrace / process_vm_readv / clone3 / landlock 全部安全）
```

也就是说：**`sched_setattr` 在 arm64 上是安全的**，我上一轮"313 = sched_setattr"的推断
**错了**（313 是 x86_64 编号；那条 `Cause: ... 313` 来自**更早的一份 tombstone**）。

**而真正的乌龙是 tombstone 这次的指认**：

```
signal 31 (SIGSYS), code 1 (SYS_SECCOMP)
Cause: seccomp prevented call to disallowed arm64 system call 306
      #00 libtwinvm.so (Java_dev_twinbox_vm_Native_stage0+6496)   ← 就是我的探针代码！
      #03 ... (dev.twinbox.vm.MainActivity$1.run+86)
```

`306`(arm64) = `io_pgetevents`。**是我自己加的 zygote 探针**（fork 子进程去试调被禁
syscall）踩了地雷，而且 **`SECCOMP_RET_KILL_PROCESS` 杀的是整个进程** ——
`fork` 出来的子进程仍属同一进程，于是**探针把 App 连同 VM 一起干掉了**。
所以这一轮的 "code=127 / Runtime aborting" 根本不是 ART 的新问题，
而是**我的诊断代码自杀**。

## 2. 修复（v0.7.68）

1. **App 进程内禁止试调**：`vm_policy_probe()` 在父进程里默认直接返回，
   并打印一行说明（"App 进程内试调被禁 syscall 会连坐 KILL_PROCESS 把整个 App 杀掉"）；
2. **探针挪进"槽位子进程"**：那是做完就 `_exit` 的赴死进程，被 KILL 无所谓；
3. **结果经共享黑匣子回传**：探针结果写进 `vm_bb`（`pc=0x50524F42`="PROB" 标记），
   父进程收尸时读出来，日志照旧能看到完整名单；
4. 保留 `kZygoteBlocked` / `kAllowAudit` / `kParamAllowed` 三份名单（探针本身有价值）。

## 4. 下一轮：回到 ART 的真实问题（`StartupCompletedTask::Run`）

清掉这个乌龙后，v0.7.66/67 反复出现的同一个 abort 栈**才是要解的题**：

```
native: #00 art::StartupCompletedTask::Run+272          ← 这个任务在做什么？
native: #01 _GLOBAL__sub_I_code_generator.cc+7600       ← 静态初始化常量折叠出的代码
native: #02 InstructionSimplifierVisitor::TryReplaceWithRotateConstantPattern+140
native: #03 ElfCompilationUnitWriter<ElfTypes64>::Write+2212   (在 Aborting thread 里)
native: #04 libbase.so
```

结论性观察：**abort 是被"信号"打进来的**（栈里没有任何 abort 调用点，
`runtime.cc:719` 只是 dump 函数），`exit_group(0x7f)` 与 `code=127` 完全吻合。

下一步我会：
1. 在**槽位子进程**里加"**信号溯源**"：把 `SIGSYS/SIGSEGV/SIGABRT/…` 的
   `si_code`、`si_addr`、`si_syscall`（SIGSYS 时的 syscall 号）直接写进共享黑匣子
   —— 这样下次无论谁杀、哪个信号，都能在日志里看到"谁、什么号、什么地址"；
2. 顺带把 ART 的 **`StartupCompletedTask`** 对应源码路径查出来（AOSP 里它做的是
   "dex2oat/镜像写入相关的收尾"），判断它到底在写什么、为什么会被信号打断。
