# TwinVM 修复报告（第二十三轮：abort 现场定格 —— ART 用 mq_open 给 debuggerd 送死讯）v0.7.71 → v0.7.72

> 现场：`twinvm-live.log`（43 MB，v0.7.71）＋ 反汇编 `libart.so`

## 1. v0.7.71：探针跑了，而且给出了一条硬结论

探针输出**在 live 日志里**（主日志文件里没有 —— 因为 live 是流式写、主日志在退出时汇总）：

```
[TwinVM] [policy] 审计放行清单（38 条）：逐条 fork 子进程实测
[TwinVM] [policy]    exit_group / brk / mprotect / futex / clone / userfaultfd … -> 安全
[TwinVM] [policy] (参数化) write/read/close/socket/mmap/rt_sigaction/openat -> 信号 0
[TwinVM] [policy] 放行清单里有 0 条会被 App 策略 KILL      ← ★ 放行清单干净了
```

**结论：我们的 BPF 放行清单与 App 策略 KILL 名单「零交集」**：
`rseq`、`set_robust_list` 那类"一碰即死"的坑已经全部清除，这条路走通了。

## 2. 反汇编把 abort 现场定格

`StartupCompletedTask::Run` 的头两句（从 ROM 里的 libart.so 反汇编）：

```asm
80ca20: bl art::Runtime::NotifyStartupCompleted()      ← 第一件事
80ca38: bl art::Runtime::DeleteThreadPool()            ← 紧接着销毁线程池
```

配合黑匣子（死前最后 syscall 序列）：

```
nr=174 getuid ;  nr=66 writev(fd 0x53)  ;  nr=174 getuid
nr=240 mq_open(name, name, 0x6)  → 引擎回 ENOSYS
nr=174 getuid ;  nr=240 mq_open(...)    ← abort 中
```

而 `libc.so` 内含 `/dev/socket` + `debuggerd` 字符串 —— 这是 bionic 的
**crash dump 通道**：进程 abort 时，把它**通过 `mq_open` 建的消息队列发给 debuggerd**，
把 abort message 递出去。ART 手里拿不到 fd（我们回 ENOSYS）→ 直接 `abort()` 收尾。

**这解释了此前所有奇怪现象**：abort dump 里"没有原因行"，
因为**原因行是要通过那条 mq 送走的**，而不是打给我们的控制台。

## 3. v0.7.72：先把"它想开什么名字"打出来

在 `ENOSYS` 语音盒里，对 `mq_open(240) / mq_unlink(241)` **把 a0 指向的字符串读出来**打日志：

```
[TwinVM] ENOSYS nr=240 a0=0x6cca …
[TwinVM]   ^^ 想打开的名字: "/dev/socket/..."        ← 下一轮就能确定 abort 的真实意图
```

（`vm_mem_read` 是引擎既有的安全访存原语，guest 传野指针也只会失败，不会崩槽位。）

## 5. 下一轮

装 v0.7.72 → 点「运行」。日志里会出现 **那个名字**，据此二选一：

* **若是 debuggerd 的 socket/mq** → 说明 ART 已经在收尸阶段，真正要解决的是**它为什么 abort**
  —— 这时把 `mq_open` 改成"返回一个假的可用 fd（引擎自造一个匿名队列）"，
  让 ART 把 abort message **正常写出来**，我们就能在日志里看到**原因行全文**，
  一举拿下这个纠缠多轮的问题；
* **若是别的名字**（如某个属性/设备）→ 直接按需在 ROM 或引擎里补上即可。
