# TwinVM 修复报告（第二十四轮：**没实现 `process_vm_readv`** —— abort 消息递送断链）v0.7.72 → v0.7.74

> 现场：`twinvm-live.log`（39 MB，v0.7.72）

## 1. v0.7.72 的关键读数：abort 前的 syscall 序列

```
#497940 nr=113 clock_gettime
#497941 nr=174 getuid
#497942 nr=64  write(5, buf, 0x5a)          ← 写日志（fd 5 = logd socket，已被我们 tee）
#497943 nr=139 rt_sigreturn
#497944 nr=66  writev(0x53, …)              ← 另一条日志通道
#497945 nr=64  write(5, buf, 0x59)
#497946 nr=64  write(5, buf, 0x20)
#497947 nr=270 process_vm_readv(a0=0x34d7, a1=…, a2=1)   ← ★ 反复出现
#497949 nr=64  write(5, …, 0xa)
#497950..#497957  nr=270 / nr=64 交替        ← 日志字符串"拷贝+写出"的循环
#497958 nr=64  write(5, …, 0x200)
   ↓
runtime.cc:719] Runtime aborting...
#497990 nr=94 exit_group(0x7f)
```

**决定性观察**：ART 打 abort 时，走的正是
**`process_vm_readv`（把字符串从 guest 内存拷出来）+ `write`（发给 logd）**这条链。
而我们的引擎里 —— **`process_vm_readv(270)` 根本没有实现**，落到 `default` 分支回 `-ENOSYS`。
于是：

* 日志/abort 消息**拷不出来** → 我们永远看不到原因行；
* ART 的 `AbortMessage`/crash 上报路径失败 → 最后只能裸 `abort()` 收尾

这完美解释了纠缠多轮的"**abort 有栈、没有原因行**"。

## 2. v0.7.74：补齐 `process_vm_readv/writev`（VM 语义版）

在本 VM 里 guest 与引擎**同地址空间**，所以这两个调用就是"按 iovec 逐段拷贝"：

```
process_vm_readv (pid, local_iov, liovcnt, remote_iov, riovcnt, flags)
    → 从 remote_iov 指向的内存 → local_iov（= guest 就是自己）
process_vm_writev 反之
```

实现要点：

* 用**安全访存** `vm_mem_read/vm_mem_write` 读 iovec 表与搬数据 —— guest 传野指针只会得到
  `-EFAULT`，不会让 handler 崩掉（沿用引擎既有铁律）；
* 支持多个 iovec 的交叉搬运（按长度推进），返回累计字节数（Linux 语义）；
* iovec 数量上限 8（够 bionic/ART 用，避免栈膨胀）。
