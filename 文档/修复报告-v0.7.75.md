# TwinVM 修复报告（第二十五轮：process_vm_readv 已生效，继续追 abort 原因行）v0.7.74 → v0.7.75

> 现场：`twinvm-live.log`（35 MB，v0.7.74）

## 1. v0.7.74 的验证结果

* **`ENOSYS nr=270` 出现 0 次** —— `process_vm_readv` 实现生效，链路不再断；
* 但 abort 仍**没有原因行**，说明断点不止这一处。

abort 前的 syscall 序列（v0.7.74）：

```
#449194 nr=64  write(5, buf, 0x20)
#449195 nr=270 process_vm_readv(a0=0x5847, a1=…, a2=1)
#449196 nr=270 process_vm_readv(a0=0x5847, a1=…, a2=1)
#449197 nr=64  write(5, …, 0xa)
   … nr=270 / nr=64 循环 …
#449226 nr=270 process_vm_readv(a0=0x5847, a1=…, a2=1)
#449206 nr=64  write(5, …, 0x200)
   ↓ runtime.cc:719] Runtime aborting...
```

**新观察**：这些 `process_vm_readv` 的 `a0=0x5847` 看着像 pid/uid，
而 `a2=1` 是 **liovcnt**（1 个 local iovec）。这种形态是 bionic 的
**`pthread_getname_np` / 线程名读取**（`__pthread_internal_find` → 读自身线程结构），
不一定是"日志拷贝"。也就是说：**我上一轮把它的用途判断得过于乐观**。

## 2. v0.7.75：把 270/271 的完整参数与 iovec 内容打出来

在 `process_vm_readv/writev` 分支里加了一次性诊断（前 6 次调用）：

```
[TwinVM]   ^^ pvm_readv pid=0x5847 liov=0x72367381d0[1]=0x…/0x… riov=0x… [N]=0x…/0x… flags=…
```

这样能一次看清：
* `a0` 到底是 pid 还是别的（对照 `/proc/self/status` 的 Pid/Tgid）；
* local/remote iovec 指向哪块内存、长度多少；
* `riovcnt` 是否真的为 0（若是 0，Linux 语义下返回 0 字节 —— 那 ART 就永远读不到东西）。

## 4. 下一轮（拿数据后二选一）

装 v0.7.75 → 点「运行」，把上面那 6 行 `^^ pvm_*` 拿到手：

* **若 `riovcnt == 0`** → ART 的调用在我们这里永远搬 0 字节：需要按 Linux 语义
  **返回 0**（而不是现在的"尽力搬"），并检查 ART 是否把它当失败；若它确实需要内容，
  说明它读的是**本进程**（pid 自身），此时应直接把 remote 当作本进程地址空间处理；
* **若 iovec 指向未映射区** → 那是 guest 的"哨兵页"（ART 的 FaultHandler 故意留的），
  需要让 `vm_mem_read` 对这块区域返回 0 字节而不是 -EFAULT。
