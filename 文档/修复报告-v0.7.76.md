# TwinVM 修复报告（第二十六轮：幽灵放行 —— `process_vm_readv` 绕过 handler，实现形同虚设）v0.7.75 → v0.7.76

> 现场：`twinvm-live.log`（37 MB，v0.7.75）

## 1. 关键反常：实现"生效"了，却一行诊断都没打

v0.7.75 我加了 `pvm_*` 参数诊断（前 6 次调用打印），结果：

```
$ grep -c "ENOSYS nr=270"  → 0        （不再报未实现）
$ grep -c "pvm_"           → 0        （可我的实现里的诊断也没执行！）
$ grep -c "nr=270"         → 1632     （guest 确实在大量调用它）
```

**用离线 BPF 模拟器一验，真相立刻出来**：

```
nr 270 -> ALLOW      ← 被放行，不是 TRAP
nr 271 -> ALLOW
```

`process_vm_readv/writev` **在放行清单里**（`gen_bpf.py` 的 ALWAYS）——
它是 **v0.7.22** 为了让"引擎自己在 handler 内安全访存"而加的，
但**那个机制后来废弃了**（引擎改用自己的 `vm_mem_read/vm_mem_write`，纯内存拷贝，
根本不碰内核）。而这个残留条目造成了极隐蔽的后果：

> guest（ART）调用 `process_vm_readv` → **BPF 直接放行、绕过 SIGSYS handler** →
> 我新写的 VM 语义实现**永远不会被执行** → ART 拿到的内容与它的地址空间假设不符
> → abort 时日志 / abort message 全都递不出来（"有栈、没有原因行"）。

**教训**：放行清单是"guest 直通内核"的白名单，条目一旦失去理由就必须删 ——
否则会静默地把我们自己的实现"短路"掉，而且**离线模拟器一跑就能看出来**
（这正是昨天刚补的那条流程纪律的价值）。

## 2. 修复（v0.7.76）

1. **从放行清单移除 `process_vm_readv/writev`**（`gen_bpf.py` 的 ALWAYS），
   并在原处写下完整原因，防止将来有人"好心"加回去；
2. **清空 `vm_engine_syscall_nrs[]`**（引擎自用 syscall 表）：引擎已不需要任何自用
   syscall，留着就是同类幽灵的温床；清空后 `vm_filter_check_passthrough()` 的
   一致性自检也不会再要求放行它们；
3. 更新两处回归：
   * `bpf_sim.py`：区分"guest 必须 TRAP"与"引擎自用需放行"，支持空表（`-1` 哨兵）；
   * `guardtest.c`：遍历引擎自用表时**跳过哨兵**，避免把 `-1` 当成"未放行的 syscall"；
4. 顺手修掉两个**我自己造的解析 bug**：
   * `re.sub(r'[\s\-0-9,]+', ' ')` 会把 `VM_NR_wait4` / `VM_NR_pread64` 里的
     `4` / `64` 一起吃掉（变成 `wait` / `pread`）→ 改为只匹配 `VM_NR_[A-Za-z_0-9]+`；
   * 空表解析出 `-1` 残留 → 用哨兵 + 跳过逻辑处理。
