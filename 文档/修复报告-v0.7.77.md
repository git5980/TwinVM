# TwinVM 修复报告（第二十七轮：`process_vm_readv` 实现重写 —— 我的两处致命 bug）v0.7.76 → v0.7.77

> 现场：`twinvm-live.log`（8.6 KB，极短 —— 只跑到第 27 个 syscall 就没了）

## 1. v0.7.76 生效了，但立刻暴露我实现的 bug

摘掉幽灵放行之后，`process_vm_readv` **终于真的进 handler** 了：

```
[TwinVM] [4.2dbg] TRAP#1 nr=48 pc=0x23341c …        ← 第一次 TRAP
[TwinVM] [trace] #27  t17823 nr=270 a0=0x459f a1=0x723c3ef330 a2=0x1
[TwinVM] [trace] ★ 死前最后 syscall: nr=270         ← 就是它把槽位搞死了
```

注意：**此时只跑到第 27 个 syscall**（ART 还没起来），说明是**我的实现本身**崩了。
对照代码，找到两处致命 bug：

| # | Bug | 后果 |
|---|---|---|
| ① | local 地址写成 `liov[li].base + copied`（**全局累计字节数**） | 第二个 local iovec 起地址全错 → 越界写 → 崩 |
| ② | `if (chunk == 0) { ri++; roff = 0; continue; }` | remote iovec 长度为 0 时会**死循环**（while 条件仍成立） |

（另外参数语义也要复核：`a0=0x459f` 看着像 pid/uid，`a2=1` 是 liovcnt ——
Linux 语义下 `riovcnt` 为 0 时应当**返回 0 字节**而不是搬运。）

## 2. v0.7.77：按 Linux 语义重写

```c
process_vm_readv (pid, local_iov, liovcnt, remote_iov, riovcnt, flags)
  liovcnt<=0 || riovcnt<=0  → 返回 0          （Linux：无 iovec 即 0 字节）
  逐 local × 逐 remote 交叉搬运：
     每个 iovec 各自维护 .off（不再用全局 copied 当偏移）
     每次最多搬 4096B，搬完推进双方 .off
     地址不可访问 → 返回"已搬运字节数"（Linux 部分成功语义），绝不返回 -EFAULT 硬失败
     用完的 remote iovec 跳过；n==0 立即返回 → 杜绝死循环
  process_vm_writev 反之（src/dst 互换）
```

要点：**偏移按 iovec 独立维护**、**任何一步 n==0 就返回**、**部分成功按 Linux 语义返回**。

## 3. 验证

* `make -C core test` 5/5 PASS；`checkrom --strict` PASS；ROM md5 未变；
* APK `versionCode=100 / versionName=0.7.77`，同源签名，可直接覆盖。

## 4. 下一轮预期

装 v0.7.77 → 点「运行」。这次 `process_vm_readv` 应当**正常返回**而不是搞死槽位，
日志里会出现 v0.7.75 加的参数诊断（前 6 次）：

```
[TwinVM]   ^^ pvm_readv pid=0x… liov=0x…[1]=0x…/0x… riov=0x…[N]=0x…/0x… flags=…
```

据此确认 ART 的真实意图（读自己的线程名？还是拷日志？），并把 `riovcnt==0`
这类边界情形按 Linux 语义处理 —— 这是拿到 **abort 原因行** 的最后一环。
