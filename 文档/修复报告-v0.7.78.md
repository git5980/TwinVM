# TwinVM 修复报告（第二十八轮：handler 跑在 guest 栈上 —— 我的实现撑爆了它）v0.7.77 → v0.7.78

> 现场：`twinvm-live.log`（8.5 KB，v0.7.77）—— 仍是第 27 个 syscall 死，**位置与上一版一模一样**

## 1. 两个发现

### (a) v0.7.77 的诊断"凭空消失"了

`.so` 里查不到 `pvm_` 字符串 —— 原因很朴素：**v0.7.77 我是"整段重写"**，
把 v0.7.75 加的诊断**连同旧实现一起替换掉了**。
（又一次印证那条纪律：整段替换必须连带检查被删掉的诊断/断言。）

### (b) 真正原因：SIGSYS handler 跑在 **guest 应用栈**上

看 handler 安装代码：

```c
sa.sa_sigaction = vm_sigsys_handler;
sa.sa_flags = SA_SIGINFO;              /* 没有 SA_ONSTACK，也没建 altstack */
```

也就是说：**SIGSYS 处理过程完全使用 guest 的栈**（1 MB，且此刻正被 guest 使用）。
而我在 `process_vm_readv` 实现里放了：

* `liov[8] + riov[8]` 两个结构体数组（各 ~200 B）
* **`char tmp[4096]` 一个 4 KB 栈缓冲**

叠加 handler 自身与调用链的帧 → **栈溢出** → 崩槽位（正好发生在第 27 个 syscall 的
`process_vm_readv` 上，因为那是第一次真正执行我这段代码）。

## 2. v0.7.78 修复

1. **压缩 handler 内的栈占用**（这是根本）：
   * iovec 表 8 → **4**（bionic/ART 实际最多 2-3 个）；
   * 临时缓冲 4096 B → **512 B 分块搬运**；
2. **把诊断加回来**（这次做成"前 8 次打印"的常驻诊断，并写进注释防止再被整段替换吞掉）：
   ```
   ^^ pvm_readv a0=0x… a1=0x…[N]=0x…/len a3=0x…[M]=0x…/len a5=0x…
   ```
3. 已确认诊断真的进了 `.so`（APK 内 `libtwinvm.so` 可查到 `pvm_` 串）。

## 3. 验证

* `make -C core test` 5/5 PASS；`checkrom --strict` PASS；ROM md5 未变；
* APK `versionCode=101 / versionName=0.7.78`，同源签名。

## 4. 下一轮预期

装 v0.7.78 → 点「运行」。这次应能看到诊断行（这是第一次能真正"看见"ART 想读什么）：

```
[TwinVM]   ^^ pvm_readv a0=0x… a1=0x…[1]=0x…/len a3=0x…[N]=0x…/len a5=0x…
```

据此判断：
* 若 `a3`（remote iovec）为空或 `riovcnt==0` → 按 Linux 语义返回 0，ART 会走退化路径；
* 若它读的是自己线程结构 → 直接本进程拷贝即可（我们的实现已经是这个语义）。

同时，如果这轮还崩，下一步就把 **handler 迁到 altstack**（`SA_ONSTACK` + 8MB
`sigaltstack`）——那是彻底解决"handler 栈太小"的正解，本轮先用"压缩占用"快速验证。
