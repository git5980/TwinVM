# TwinVM 修复报告（第二十九轮：给 handler 装"无死角门禁记录"，终结推测）v0.7.78 → v0.7.79

> 现场：`twinvm-live.log`（8.5 KB，v0.7.78）—— 第 27 个 syscall (`nr=270`) 死，与 v0.7.76/77 **完全同点**

## 1. 本轮把"推测"逐条排除掉

| 假设 | 验证 | 结论 |
|---|---|---|
| 放行清单里还有 `process_vm_readv` | `bpf_gen.h` 里搜 `VM_BPF_ALLOW_NRS`：**已无** 270/271；`BPF_JEQ` 立即数里也**没有** 270/271/310/311 | ❌ 排除 |
| 离线模拟器判错了 | 用**真实参数**（a0=pid, a1=liov, a2=1, a3=riov, a4=?, a5=0）跑 `bpf_sim`：**TRAP** | ❌ 排除 |
| APK 里打的是旧 `.so` | `cmp` APK 内 `.so` 与构建产物：**一致**；且 `.so` 内可查到本轮新加的 `HND#` 串 | ❌ 排除 |
| `stale`（迟到投递）早退吞掉了它 | arm64 的 bionic `siginfo_t` **没有 `si_call_addr`** → `trap_pc=0` → `stale` 恒 false | ❌ 排除 |
| handler 栈溢出（`tmp[4096]`） | v0.7.78 已把 iovec 8→4、缓冲 4KB→512B，**症状没有任何变化** | ⚠️ 待定（可能不是主因） |
| 诊断被"整段替换"吞掉 | v0.7.78 已确认 `pvm_` 串在 `.so` 里 —— **可它仍然一行都没打** | ❗ 说明**代码没被执行到** |

**最强的证据是黑匣子**：`seq=1`（只记了 `nr=48` 一条）。而黑匣子在
`vm_handle_syscall` 入口无条件写入 —— 所以 **`process_vm_readv` 根本没进
`vm_handle_syscall`**，我写的实现与诊断自然也都没执行。

## 2. v0.7.79：把"门禁记录"装到 handler 的最前面

在 **handler 入口**（`si_syscall` 刚取到时、任何 `stale`/条件判断之前）无条件记录：

```
[TwinVM] [4.2dbg] HND#<n> nr=<syscall号> pc=0x<地址>
```

最多 400 条。这一条记录能**一次回答**：

* 若列表里**有** `nr=270` → 它确实进了 handler，问题在我实现内部（那就继续往下查）；
* 若列表里**没有** `nr=270` → 它被 BPF **放行**（或 KILL），问题在过滤器；
  那就把 `bpf_gen.h` 生成物 + 真机 `.so` 的反汇编逐条对照，找出放过它的那条规则。

## 3. 验证

* `make -C core test` 5/5 PASS；`checkrom --strict` PASS；ROM md5 未变；
* APK `versionCode=102 / versionName=0.7.79`，同源签名；`.so` 内确含 `HND#` 串。

## 4. 说明

这一轮没有"猜一个修一个"，而是**先把观测手段做到无死角** ——
前几轮反复出现"改了却没效果、诊断不输出"，根子就是**观测点不够靠前**。
`HND#` 落在 handler 第一行，之后任何早退/崩溃都逃不过它。
