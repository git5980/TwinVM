# TwinVM 修复报告（第三十轮：handler 第二次进入就崩 —— 给它 8MB 独立栈）v0.7.79 → v0.7.80

> 现场：`twinvm-live.log`（8.7 KB，v0.7.79）

## 1. `HND#` 门禁记录一锤定音

```
[TwinVM] [4.2dbg] HND#1 nr=48 pc=0x23341c        ← 全文只有这 1 条
```

`HND#` 打在 **handler 第一行**（取到 `si_syscall` 之后、任何早退判断之前），
而第 27 个 syscall 是 `process_vm_readv(270)` —— 于是结论唯一：

> **handler 只成功进入过一次；第二次（270 那次）在打印 `HND#` 之前就崩了。**

同时我逐条排除了此前的猜测（本轮完整记录）：

| 假设 | 验证方式 | 结论 |
|---|---|---|
| 放行清单仍含 270 | `VM_BPF_ALLOW_NRS` 搜不到；`BPF_JEQ` 立即数里也没有 | ❌ |
| 离线模拟判错 | 用 `bpf_sim` 的 `load_program` + 真实 `AUDIT_ARCH_AARCH64`(0xC00000B7) 逐步跟踪：**TRAP** | ❌ |
| APK 内是旧 `.so` | `cmp` APK 内 `.so` 与构建产物一致，且含 `HND#` 串 | ❌ |
| `stale` 早退吞掉 | arm64 bionic `siginfo_t` 无 `si_call_addr` → `stale` 恒 false | ❌ |
| 我的实现有 bug（越界/死循环） | v0.7.77 已重写，**但症状点在 270 进 handler 之前** | ❌（不是主因） |

## 2. 真因：**handler 跑在 guest 的应用栈上**

```c
sa.sa_flags = SA_SIGINFO;      /* 既没建 altstack，也没有 SA_ONSTACK */
```

也就是说：SIGSYS 的处理过程**直接使用 guest 的栈**（1MB，且此刻 guest 正在用）。
第一次进来（`nr=48`，参数少、路径浅）侥幸没溢出；第二次（`process_vm_readv`，
要读 iovec 表 + 搬运数据）**把栈撑爆** → 进程死，连一行日志都来不及打。

这也解释了为什么"实现了却看不到任何效果"：**不是没执行，是执行到一半就崩了。**

## 3. v0.7.80 修复

挂**独立 8MB 信号栈**并把 handler 迁上去：

```c
static char altstack_mem[8 * 1024 * 1024];
stack_t ss = { .ss_sp = altstack_mem, .ss_size = sizeof(altstack_mem), .ss_flags = 0 };
sigaltstack(&ss, NULL);
sa.sa_flags = SA_SIGINFO | SA_ONSTACK;      /* ★ */
```

好处：
* handler 不再占用 guest 栈（guest 的栈状态也更干净）；
* handler 内可以放心使用数 KB 的临时缓冲（iovec 表、分块搬运缓冲）。

## 4. 验证

* `make -C core test` 5/5 PASS；`checkrom --strict` PASS；ROM md5 未变；
* APK `versionCode=103 / versionName=0.7.80`，同源签名。

## 5. 下一轮预期

装 v0.7.80 → 点「运行」。若 altstack 是正解，这次会看到：

```
[TwinVM] [4.2dbg] HND#1 nr=48 …
[TwinVM] [4.2dbg] HND#2 nr=64 …
[TwinVM] [4.2dbg] HND#3 nr=270 …          ← process_vm_readv 终于进来了
[TwinVM]   ^^ pvm_readv a0=… a1=…[N]=… a3=…[M]=…   ← 参数诊断
```

于是能一次看清 ART 想读什么，并把它接到我们已经写好的 VM 语义实现上 ——
这是拿到 **abort 原因行** 的最后一环。
