# TwinVM 修复报告（第三十一轮：把探针做到"不可能失败"—— 裸 write）v0.7.80 → v0.7.81

> 现场：`twinvm-live.log`（8.9 KB，v0.7.80）—— **加了 altstack 后症状不变**，仍 `HND#1` 一条

## 1. 本轮又排除一个大假设

v0.7.80 给 handler 挂了 8MB 独立信号栈 + `SA_ONSTACK`，结果**完全没变化**：

```
[TwinVM] [4.2dbg] HND#1 nr=48 pc=0x23341c      ← 仍然只有这一条
#29  nr=270  a0=0x488c  a1=0x70f0471ea0  a2=0x1   → 进程消失
```

**所以栈溢出不是原因**（至少不是这个层面的）。

## 2. 顺着 trace 把"谁能进 handler"算清楚

* `#27/#28` 是 `write(5, …)` —— `fd 5` 正是**引擎自己的 console 管道**（`pfd[1]`），
  BPF 对 console 的 write 有特判 → **ALLOW，本来就不进 handler**（正常，不是问题）；
* `#29` 是 `nr=270`、`a0=0x488c`（**是 pid，不是 uid**）→ `process_vm_readv(自己, …)`；
* 离线用 `bpf_sim.load_program` + 真实 `AUDIT_ARCH_AARCH64` 逐指令跟踪：**270 → TRAP**；
* 但 handler 里 `HND#` 只出现 1 次 → **第二次 TRAP 没能进入 handler**。

到这一步，"为什么进不去"必须靠**可靠的观测**来回答，而不是继续猜。

## 3. v0.7.81：极端手段 —— 裸 `write()` 直写 console

之前所有探针（`HND#`、`^^ pvm_*`）都走 `vm_log()` → **glibc printf 路径，依赖宿主 TLS 状态**
（引擎代码里明确写着"bionic 抢占 TLS 后 glibc 会读错地址"）。如果 TLS 状态在那一刻是错的，
**日志会静默失败** —— 这正好能解释"代码明明在却一行都不打"。

所以这一版在 handler **最开头**（取到 `si_syscall` 后、任何库调用之前）插入：

```c
// 手工把 "nr=N\n" 拼进栈缓冲，然后用 **裸 svc write()** 直写 console fd
if (vm_console_fd >= 0) { __asm__ volatile("svc #0" : ... ); }
```

* **不调用 libc**、**不碰 TLS**、**不做格式化** —— 只要 fd 可写就必然留痕；
* 于是下一轮日志会出现一串 `[HR] nr=N`：
  * 若看到 `[HR] nr=270` → handler **确实进了**，问题在实现内部（继续查搬运逻辑）；
  * 若**看不到** `[HR] nr=270` → TRAP 根本没发生（内核层被别的过滤器处理），
    那就转去查"外层 zygote 策略 + 我们过滤器"的交互。

## 4. 验证

* `make -C core test` 5/5 PASS；`checkrom --strict` PASS；ROM md5 未变；
* APK `versionCode=104 / versionName=0.7.81`，同源签名。

## 5. 方法说明

连续几轮"改了没效果、日志无输出"，本质是**观测手段本身不可靠**（依赖库/ T LS/条件判断）。
这一轮把观测降到**内核原语级**（裸 write），从根上消除"看不见"的可能 ——
拿到 `[HR]` 序列后，这个纠缠已久的问题就能一次定论。
