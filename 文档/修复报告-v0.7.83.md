# TwinVM 修复报告（第三十三轮：拦下 guest 的 seccomp 安装 —— 放行清单是"绕过 handler"的元凶）v0.7.82 → v0.7.83

> 现场：`twinvm-live.log`（8.4 KB，v0.7.82）—— **加了 prctl 拦截后症状不变**

## 1. 为什么 v0.7.82 的修复"没生效"

我在 `vm_handle_syscall` 里加了 `prctl(PR_SET_SECCOMP)` 的拦截，但真机日志里
`#20/#21` 的 `prctl(a0=0x26/0x16)` **照旧执行**。用离线模拟器一查：

```
nr=167 (prctl) -> ALLOW        ← BPF 直接放行，根本不进 handler！
```

**同一个坑，第三十五次**：`prctl` 在 BPF 放行清单里（因为它在判决表里是"直发"），
所以 guest 的调用**绕过 handler 直达内核** —— 我写在 case 里的拦截代码永远不会执行。

## 2. 但不能简单摘掉（回归拦住了我）

把 `prctl` 从放行清单摘掉后，`make test` **立刻报错**：

```
判决表直发 prctl(167) 未被 BPF 放行 —— handler 内裸 svc 会二次 TRAP
源码直发未放行 —— 直发 nr=167 任何合法参数下都不是 ALLOW
```

**这个回归（v0.7.24 铁律）救了我**：`prctl` 在 `vm_passthrough_nrs[]` 里，
handler 内是 `VM_PT5` 裸 svc 直发；若 BPF 不放行它，直发会二次 TRAP（Stage 1 的
`code=-31` 同型故障）。所以**必须同时改两处**。

## 3. v0.7.83 的正确做法（两处联动）

| 位置 | 改动 |
|---|---|
| `gen_bpf.py` ALWAYS | **摘除 `prctl`** → guest 的 prctl 会 TRAP 进 handler（我们终于能看到它） |
| `vm_core.c` 判决表 | **`prctl` 移出 `vm_passthrough_nrs[]`**（不再直发）→ 避免二次 TRAP |
| `vm_core.c` case | ① `a0==38`(`PR_SET_NO_NEW_PRIVS`)、`a0==22`(`PR_SET_SECCOMP`) → **返回 0**（假装成功，绝不透传）<br>② 其它 prctl → 改为**宿主原生调用** `prctl(a0,a1,a2,a3,0)`（不再是 VM_PT 裸 svc） |

**离线验证**：

```
nr=167 (prctl) -> TRAP     ← 现在会进 handler，拦截生效
nr= 48         -> TRAP
nr=270         -> TRAP
nr= 98 (futex) -> ALLOW    ← 其它放行不受影响
nr=222 (mmap)  -> ALLOW
$ make -C core test → 5/5 PASS（含 v0.7.24 直发铁律回归）
```

## 4. 这一轮把"真凶链"彻底闭合

```
guest(bionic) 早起 #20/#21:
    prctl(38 PR_SET_NO_NEW_PRIVS, 1)
    prctl(22 PR_SET_SECCOMP, 2 FILTER, &fprog)   ← 装它自己的策略（KILL_PROCESS）
        ↓ 我们此前"放行" → 直达内核 → 装上
内核 seccomp 语义：**后装的过滤器排在最前面**
        ↓
我们这层被盖住 → guest 之后每个 TRAP 都按"它那层"判
        ↓
第一条 TRAP 就 KILL_PROCESS → 进程秒死
        ↓
现象：HND#/TRAP#/[HR] 全零、黑匣子 seq=0、"死前末尾 nr=0"（退出码被当成 syscall 号）
```

**这就是从 v0.7.55 到 v0.7.81 一直"看不见现场"的总根源。**
