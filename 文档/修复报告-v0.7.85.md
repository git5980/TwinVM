# TwinVM 修复报告（第三十五轮：上一轮结论修正 + 两处决定性加固）v0.7.84 → v0.7.85

> 现场：`twinvm-live.log`（8.4 KB，v0.7.84）

## 1. 重要更正：我上一轮的"总根源"判错了

v0.7.84 里我看到 `#20/#21` 的 prctl 出现在"拦截就绪"**之前**，就认定"guest 在装载期装了 seccomp"。
但把 v0.7.84 的 trace **逐条枚举**后发现真相：

```
#9   nr=132 sigaltstack(…)         ← 这是**引擎自己** vm_sigsys_install() 的第一步！
#10  nr=134 rt_sigaction(SIGSYS,…)
#11  nr=167 prctl(38  PR_SET_NO_NEW_PRIVS, 1)
#12  nr=167 prctl(22  PR_SET_SECCOMP, FILTER, &fprog)
#13..#21 mmap/mprotect（装载段映射）
```

对照 `vm_backend_sigsys.c`：

```c
if (prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0) != 0) return -errno;      // ← #11
if (prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &fprog, 0, 0) != 0)   // ← #12
```

**全是引擎自己的安装动作**，被 ptrace 示踪器当成了"guest 的 syscall"。
**guest 从来没有装过 seccomp** —— 上一轮的"总根源"结论作废（顺带说明：
v0.7.84 的"先装过滤器再装载"仍然是对的改进，只是它不是病根）。

（另外查出一个小 bug：`!! 引擎自用 syscall 未放行: nr=-1` —— v0.7.76 把引擎自用表清空成
`{-1}` 哨兵后，一致性自检没跳过它。本轮已修。）

## 2. 真正的观察：第一条该 TRAP 的 syscall 没有进 handler

装好过滤器后 guest 的流水：

```
#23 nr=172 getpid        → BPF 判 ALLOW（正常，不该 TRAP）
#24 nr=222 mmap          → ALLOW
#25 nr=96  set_tid_address → ALLOW
#26 nr=48  faccessat(AT_FDCWD,…) → BPF 判 **TRAP**   ← 但没有 HND#、没有 [HR]
#27 nr=0                 ← 退出码被示踪器当成 syscall 号
```

`HND#`/`[HR]` 都是 0 → **handler 从未被调用**。
最可能的解释：**跳进 guest 的那一刻，SIGSYS 处于屏蔽态** ——
这样 TRAP 只会让信号"挂起"（系统调用不执行、handler 不进入），
表现为"没进 handler、却继续跑/莫名死"。

## 3. v0.7.85：两处决定性加固

1. **跳进 guest 之前强制清空信号掩码**（`vm_loader_jump` 里 `sigprocmask(SIG_SETMASK, ∅)`）：
   保证 guest 的第一条 TRAP 就能进 handler；
2. **把裸 write 探针提到 handler 的绝对第一行**（在 `vm_cpu_current`、TLS 切换之前）：
   之前 `HND#` 走 `vm_log`（glibc printf，依赖宿主 TLS），在 TLS 被 guest 抢占的窗口里
   会**静默失败** —— 这就是"代码明明在却一行不打"的原因。
   新探针不依赖 libc/TLS/格式化，直接 `svc write(fd)` 写 `[HR] nr=N`。
