# TwinVM 修复报告（第三十六轮：arm64 上"迟到投递"检测完全失效 → 参数错位喂给实现）v0.7.85 → v0.7.86

> 现场：`twinvm-live.log`（8.0 KB，v0.7.85）

## 1. v0.7.85 的变化（死因前移了）

```
#20 nr=64  write(5, …, 0x5a)
#21 nr=135 rt_sigprocmask(0x2 /*SETMASK*/, …)     ← ★ guest 在改掩码
#22 nr=172 getpid
#23 nr=222 mmap
#24 nr=96  set_tid_address
#25 nr=48  faccessat(AT_FDCWD, …)                 ← 该 TRAP 的一条
#26 nr=64  write(a0=0x40, a1=0x5, a2=0x70ecfb8710) ← ★★ 参数完全错位！
★ 死前最后 syscall: nr=64
```

**`#26` 的三个参数根本不是 `write` 的样子**（`fd=0x40` 尚可，但 `buf=0x5`、
`len=0x70ecfb8710` 明显是别的调用的寄存器）—— 这是**典型的"信号迟到投递"**：
guest 在 `rt_sigprocmask` 屏蔽 SIGSYS 的窗口里触发 TRAP，信号被挂起；
等它恢复掩码后信号才投递，**此时 ucontext 里的寄存器早已是另一个调用的现场**。

## 2. 为什么引擎的"迟到检测"没拦住

```c
#ifdef si_call_addr
    uintptr_t trap_pc = (uintptr_t)si->si_call_addr;
#else
    uintptr_t trap_pc = 0;            /* ← arm64 走这里 */
#endif
int stale = (si->si_code == SYS_SECCOMP && trap_pc != 0 && trap_pc != now_pc);
```

**arm64 的 `siginfo_t` 没有 `si_call_addr` 字段** → `trap_pc` 恒为 0 → `stale` 恒为 false
→ **迟到投递检测在 arm64 上完全失效**。于是错位参数被当成正常调用喂给了（我们新写的）
实现 —— 这正是"改了没效果 / 莫名死"的另一个隐藏根源。

## 3. v0.7.86：arm64 专用的交叉校验

`seccomp` 的语义决定了：触发 TRAP 的系统调用号必须同时出现在
`seccomp_data.nr`（→ `si->si_syscall`）和 **寄存器 x8**（Linux 系统调用号载体）里。
两者不一致 ⇒ 一定是迟到/串味投递。于是：

```c
int stale = (si->si_code == SYS_SECCOMP && trap_pc != 0 && trap_pc != now_pc);
#if defined(__aarch64__)
    if (!stale && si->si_code == SYS_SECCOMP) {
        unsigned long x8v = (unsigned long)uc->uc_mcontext.regs[8];
        if (x8v != (unsigned long)nr) {
            stale = 1;
            vm_log("[TwinVM] !! 迟到投递：si_syscall=%ld 但 x8=%lu —— 按 -ENOSYS 原样返回", nr, x8v);
        }
    }
#endif
```

即：**不再把错位参数当真**，这类投递一律按"返回 -ENOSYS"处理（与原语义最接近，
且不会误执行任何东西）。这样既修掉了"参数错位喂给实现"，也让日志**显式记录**
每一次迟到投递 —— 下一轮就能看到它到底发生了几次、发生在哪。
