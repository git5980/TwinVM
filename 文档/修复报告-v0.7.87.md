# TwinVM 修复报告（第三十七轮：装完过滤器立刻自测 TRAP，一刀切开三种可能）v0.7.86 → v0.7.87

> 现场：`twinvm-live.log`（8.0 KB，v0.7.86）

## 1. v0.7.86 的结果：迟到投递告警 **0 条**，症状一模一样

```
#20 nr=64  write(5, …, 0x5a)
[TwinVM] 拦截就绪，装载 guest entry=0x221e80 …      ← ★ 过滤器在 #20 之后才装上
#21 nr=135 rt_sigprocmask(2 SETMASK, …)
#22 nr=172 getpid        #23 nr=222 mmap      #24 nr=96 set_tid_address
#25 nr=48  faccessat(AT_FDCWD,…)      ← BPF 判 TRAP
#26 nr=64  write(a0=0x40, a1=0x5, a2=0x70ecfe8790)   ← 参数错位
★ 死前最后 syscall: nr=64
[TwinVM] [bb] 子进程最后的 syscall（seq=0…）          ← 黑匣子：一个 syscall 都没进引擎
```

三个"零"同时成立：**`HND#`=0、`[HR]`=0、迟到告警=0**，加上黑匣子 `seq=0` ——
即：**过滤器生效之后，guest 的所有 TRAP 都没有进入我们的 handler**。
（`#26` 的参数错位则像是"信号现场串味"的残留表现。）

这条断言的三种可能必须切开：

| 可能 | 含义 |
|---|---|
| A | 过滤器**没真正生效**（`prctl` 之后被别的层覆盖 / 装的是旧程序） |
| B | 过滤器生效了，但 **SIGSYS 信号没被投递**到我们的 handler（处置/掩码/altstack 问题） |
| C | 信号投递了，但 **handler 内部**在打印任何东西之前就崩了 |

## 2. v0.7.87：装完过滤器**立刻自己触发一次 TRAP**

在 `vm_sigsys_install()` 末尾（`vm_seccomp_install()` 成功之后）直接发起一个
**必然 TRAP 且无副作用**的系统调用 `faccessat(48)`（它不在放行清单里）：

```c
vm_log("[TwinVM] 自检：马上触发一次 TRAP（faccessat）…");
register long x8 __asm__("x8") = 48;   /* faccessat */
__asm__ volatile("svc #0" : "+r"(x0) : …);
vm_log("[TwinVM] 自检：TRAP 返回 x0=%ld —— handler 工作正常", (long)x0);
```

判定方式（下一轮日志直接可读）：

* 看到 **`自检：马上触发…`** 且 handler 里打出 `[HR] nr=48`，随后 **`TRAP 返回`** →
  A/B/C 全部排除，问题在"guest 侧的执行路径"；
* 看到 **`马上触发…` 但没有任何 `[HR]`**，且**进程直接消失** → 是 **B（信号没投递）**；
* 看到 **`马上触发…` 后既没 `[HR]` 也没 `TRAP 返回`，但日志还能继续** → 是 **C（handler 内崩）**；
* 连 `马上触发…` 都没打出来 → 是 **A（过滤器安装之前就出问题）**。

无论哪一种，都能把"过滤器生效后 handler 不工作"这一团乱麻**一次性切分清楚**。

## 3. 验证

* `make -C core test` 5/5 PASS；`checkrom --strict` PASS；ROM md5 未变；
* APK `versionCode=110 / versionName=0.7.87`，同源签名。

## 4. 为什么用这个方法

前面若干轮都在"猜 + 改 + 跑真机"，而症状是"零输出"——信息量为零。
这次的思路是：**让引擎在能控制的时刻（刚装完过滤器、还没跑 guest）
主动制造一次可预期的 TRAP**，把不可观测的运行时问题**搬到一个可控的观测点上**。
