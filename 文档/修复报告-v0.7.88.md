# TwinVM 修复报告（第三十八轮：自检 TRAP 无 handler → 判别 B 成立，并加"自检前状态读取"）v0.7.87 → v0.7.88

> 现场：`twinvm-live.log`（6.1 KB，v0.7.87）—— 自检把问题**精确锁定**了

## 1. 自检结果：**判别 B（信号没投递）**

trace 里我的自检序列清晰可见：

```
#6  nr=64  write(5, …, 0x3c)                     ← 引擎日志
#7  nr=132 sigaltstack(0x723c4eadd0, 0, 0)       ← 我们建 8MB altstack
#8  nr=134 rt_sigaction(0x1f=SIGSYS, …)          ← 我们装 handler
#9  nr=167 prctl(38  PR_SET_NO_NEW_PRIVS, 1)     ← 我们装过滤器（第 1 步）
#10 nr=167 prctl(22  PR_SET_SECCOMP, FILTER, …)  ← 我们装过滤器（第 2 步）
#11 nr=64  write(5, …, 0x45)                     ← "自检：马上触发一次 TRAP…"
#12 nr=48  a0=0xffffffffffffff9c a1=0 a2=0       ← ★ 我的自检 faccessat（参数完全正确）
#13 nr=64  a0=0x40 a1=0x5 a2=0x70ed867860        ← 参数错位（信号现场串味）
★ 死前最后 syscall: nr=64
```

**`#12` 参数正确、过滤器已装好，但 handler 一条都没进**
（`[HR]` 是 handler 第一行的裸 write，也没有 `HND#`）→ **判别 B：SIGSYS 信号没有被投递**。

这条结论很硬：**过滤器在 TRAP，但信号到不了我们的 handler**。可能的具体原因只剩三个：

1. `sigaction` 装完 handler 后，**处置又被改回**（例如 `SA_ONSTACK` + 无效 altstack 导致内核
   不投递；或 `sa_flags`/`sa_sigaction` 的 ABI 细节有误）；
2. **SIGSYS 被屏蔽**（我们在 `vm_loader_jump` 里清过掩码，但 `sigaction` 之后、
   跳转之前的那段仍可能带掩码；另外 `altstack` 若无效，内核在 `SA_ONSTACK` 下
   **不会**投递给默认栈，而是直接按默认动作处理 → 进程被杀）；
3. 我们那块 `static char altstack_mem[8MB]` 在 **fork 出来的子进程**里有效，
   但 `ss_flags`/`ss_size` 若不合规，`SA_ONSTACK` 会让投递失败。

## 2. v0.7.88：自检**之前**先把信号状态读回来

在自检 TRAP 之前，把内核里的真实状态打印出来：

```
[TwinVM] 自检前状态：sigaction=%d handler=%p flags=0x%x |
         altstack=%d sp=%p size=%zu | 掩码读=%d SIGSYS被屏蔽=%d
```

这一行就能直接分辨上面三种情形：

| 观察 | 结论 |
|---|---|
| `handler=0x…` 正确、`flags` 含 `SA_ONSTACK`、`altstack sp=NULL/0` | **altstack 无效** → 去掉 SA_ONSTACK/altstack |
| `SIGSYS被屏蔽=1` | 掩码问题 → 在自检前 `SIG_UNBLOCK` |
| `handler` 不是我们的函数 | 处置被换 → 查谁换的 |
| `altstack` 正常、掩码正常、handler 正确，却仍不投递 | 内核/策略层面的 TRAP 语义问题（需查 `SIGSYS` 是否被 App 策略层吞掉） |
