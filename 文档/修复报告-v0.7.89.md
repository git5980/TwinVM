# TwinVM 修复报告（第三十九轮：信号状态全正常 → 转向"过滤器判决"验证）v0.7.88 → v0.7.89

> 现场：`twinvm-live.log`（6.9 KB，v0.7.88）

## 1. 状态读取结果：**四项全正常**

```
[TwinVM] 自检前状态：sigaction=0 handler=0x70ec12bcb8 flags=0x8000004 |
         altstack=0 sp=0x70ec148fe0 size=8388608 |
         掩码读=0 SIGSYS被屏蔽=0
```

| 项 | 值 | 判定 |
|---|---|---|
| `sigaction(SIGSYS,NULL,&cur)` | 0（成功） | ✓ |
| `handler` | `0x70ec12bcb8`（我们的函数） | ✓ 处置正确 |
| `flags` | `0x8000004` = `SA_SIGINFO(4) | SA_ONSTACK(0x08000000)` | ✓ |
| `altstack` | `sp=0x70ec148fe0 size=8388608`（8MB 有效） | ✓ |
| SIGSYS 是否被屏蔽 | `0`（未屏蔽） | ✓ |

**四项全部正常，随后 `svc faccessat` 却没有进 handler。**

这直接排除了上一轮列出的三个候选（处置被换 / 被屏蔽 / altstack 无效），
把问题逼到一个之前没验证过的环节：

> **那份装进内核的 BPF 程序，对 48 到底判什么？**

（如果它判 ALLOW，那就根本不会有 TRAP —— 我们看到的"过滤器在 TRAP"只是**推断**，
而不是事实。）

## 2. v0.7.89：用引擎自己的解释器评估**同一份程序**

在自检 TRAP 之前，用 `vm_bpf_eval()` 对 `VM_BPF_INSTRUCTIONS`（与装入内核的**同源**）

```
48 (faccessat)             → ?
64 (write, fd=1)           → ?
98 (futex)                 → ?
[TRAP=0x30000 ALLOW=0x7fff0000 KILL=0x80000000]
```

判定表：

| 评估结果 | 结论 | 下一步 |
|---|---|---|
| `48 = 0x30000 (TRAP)` | 程序没问题 → **投递链问题**（内核/策略层） | 查 seccomp 多层叠加是否把我们的 TRAP 变成了别的动作 |
| `48 = 0x7fff0000 (ALLOW)` | **程序本身就不拦 48** → 之前所有"TRAP 却没 handler"的推断都是错的 | 回到"放行清单/判决表"层，找出为什么 48 被放行 |
| `48 = 0x80000000 (KILL)` | 程序会**直接杀进程** → 与"进程秒死"完全吻合 | 解释了为何连 handler 都进不去 |

**尤其第三种**：如果 `48` 被判 KILL，那么"TRAP 却没 handler"就有了完美解释
（**KILL 绕过一切 handler**），而这也意味着我们的 BPF 程序里存在一处把普通 syscall
判成 KILL 的规则 —— 那将是本项目的**下一个真凶**。

## 4. 说明

这里的思路是**"不要相信推断，去问装进内核的那份程序"**。
前面几轮我把 `bpf_sim`（离线、读 `bpf_gen.h`）当作裁决者，但真机装进去的是
编译期常量数组；两者若因构建/宏差异而不一致，就会得出完全相反的结论。
现在改为**在真机上、用引擎自己的解释器、评估同一份数据** —— 结论不可能再有歧义。
