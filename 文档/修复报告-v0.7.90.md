# TwinVM 修复报告（第四十轮：BPF 判 TRAP、状态全正常、信号仍不投递 → 查内核过滤器实况）v0.7.89 → v0.7.90

> 现场：`twinvm-live.log`（7.2 KB，v0.7.89）

## 1. 本轮拿到两条"硬结论"，彼此矛盾

**(a) 状态全正常**（v0.7.88 已确认）：

```
sigaction=0 handler=0x70ec6d73c0 flags=0x8000004   ← 处置正确（SA_SIGINFO|SA_ONSTACK）
altstack=0 sp=0x70ec6f46e0 size=8388608            ← 8MB 栈有效
掩码读=0 SIGSYS被屏蔽=0                             ← 未被屏蔽
```

**(b) 引擎自己的解释器评估"同一份程序"**（v0.7.89 新增）：

```
自检前 BPF 评估：48(faccessat)=0x30000 [TRAP]
                 64(write,fd=1)=0x30000 [TRAP]
                 98(futex)=0x7fff0000 [ALLOW]
```

**(c) 然而** `svc faccessat` 之后，handler 依然**一条都没进**（`[HR]` 是 handler 第一行的裸 write）。

> **判 TRAP + 处置正确 + 未屏蔽 + 栈有效 ⇒ 信号却没来。**
> 只剩一个解释：**那份程序并没有真正装到内核里**（或内核实装的与我们是另一份）。

## 2. v0.7.90：读内核对自己过滤器状态的权威陈述

```c
open("/proc/self/status") → 抓 "Seccomp:" 与 "Seccomp_filters:" 两行
```

这两个字段由**内核**填写，是最权威的事实：

| 观察 | 结论 |
|---|---|
| `Seccomp: 2` 且 `Seccomp_filters: 1` | 我们的过滤器确实装上了（且只有一层）→ 问题在**投递链**（信号为何不投递） |
| `Seccomp: 2` 且 `Seccomp_filters: ≥2` | **有别的层叠在我们上面** → 真凶，且能解释"TRAP 被吞/变成别的动作" |
| `Seccomp: 0` 或 `1` | `prctl` 其实**没生效**（安装被忽略/降级）→ 回到安装路径 |
| 没有这两个字段 | 该内核/容器不暴露 → 换用 `PTRACE` 或直接反查 |
