# TwinVM 修复报告（第四十一轮：改用 prctl(PR_GET_SECCOMP) 直接问内核）v0.7.90 → v0.7.91

> 现场：`twinvm-live.log`（6.9 KB，v0.7.90）

## 1. v0.7.90 的 `Seccomp:` 行没打出来 —— 原因很有价值

我加的 `/proc/self/status` 读取**一行都没输出**。查引擎代码发现：

```
core/src/vm_core.c 里合成的虚拟文件只有：cmdline / stat / maps（VM_SYN 4 处）
/proc/self/status  → **不在合成列表里**
```

也就是说：guest 视角的 `/proc/self/status` 走的是**宿主（App）的真实文件** ——
而它在我们的 `vm_sigsys_install()` 语境下读出来的是**本进程（App）的**状态，
不一定带 `Seccomp_filters` 字段（较新内核才有），于是什么都没匹配到。

**教训**：在 VM 里做自检，凡是走"虚拟文件"的路径都可能读到**宿主**的东西，
必须用**纯系统调用接口**才可信。

## 2. v0.7.91：`prctl(PR_GET_SECCOMP)` —— 最直接的内核接口

```c
long gm = prctl(21 /*PR_GET_SECCOMP*/);     /* 0=无 1=strict 2=filter */
vm_log("[TwinVM] 自检 prctl(PR_GET_SECCOMP)=%ld", gm);
```

这是**内核直接回答"这个进程当前有没有 seccomp 过滤器"**，不可能被文件层干扰。

判定：

| 返回值 | 结论 |
|---|---|
| `2`（SECCOMP_MODE_FILTER） | 过滤器**确实装上了** → 问题必在"TRAP → 信号投递"这一环（结合已有事实：处置正确/未屏蔽/栈有效/程序判 TRAP，则要怀疑内核对 `SECCOMP_RET_TRAP` 的投递被**更外层策略**改写） |
| `0` 或 `1` | `prctl(PR_SET_SECCOMP)` 虽然返回成功，**实际没装上**（被 App 策略静默忽略）→ 安装路径要换方案 |

* `make -C core test` 5/5 PASS；`checkrom --strict` PASS；ROM md5 未变；
* APK `versionCode=114 / versionName=0.7.91`，同源签名。

## 4. 目前的完整证据链（供下一轮直接使用）

| # | 事实 | 来源 |
|---|---|---|
| 1 | 过滤器程序对 48/64 判 TRAP、对 98 判 ALLOW | 引擎解释器（真机运行） |
| 2 | SIGSYS 处置正确、未屏蔽、altstack 8MB 有效 | `sigaction`/`sigaltstack`/`sigprocmask` 读回（真机） |
| 3 | `prctl(PR_SET_SECCOMP)` 返回成功 | 代码逻辑（否则会 `_exit(97)`） |
| 4 | 自检 `svc faccessat` 后 handler 一条没进 | `[HR]`/`HND#` 全零（真机） |
| 5 | 黑匣子 `seq=0`（过滤器装好后没有任何 syscall 进引擎） | 共享内存黑匣子（真机） |

第 1~3 与第 4 相互矛盾 ⇒ 唯一未验证的环节就是**"内核里到底有没有这份过滤器"** ——
这正是本轮要回答的问题。
