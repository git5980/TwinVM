# TwinVM 修复报告（第四十二轮：★ 自检自己踩了自己的过滤器 —— 引擎不得在安装后调未放行 syscall）v0.7.91 → v0.7.92

> 现场：`twinvm-live.log`（6.9 KB，v0.7.91）

## 1. 新的关键事实：`PR_GET_SECCOMP` 那行**也没打出来**

v0.7.91 我在自检里加了 `prctl(PR_GET_SECCOMP)`，位置在"BPF 评估"**之后**、
"自检 TRAP"之前。结果日志里：

```
[TwinVM] 自检前状态：sigaction=0 handler=… flags=0x8000004 | altstack=… | 掩码读=0 SIGSYS被屏蔽=0
[TwinVM] 自检前 BPF 评估：48=0x30000 64=0x30000 98=0x7fff0000
<<< 之后什么都没有：既没有 PR_GET_SECCOMP 行，也没有自检 TRAP >>>
```

**代码顺序没错**（已核对偏移：状态 → BPF 评估 → PR_GET_SECCOMP → 自检 TRAP），
可是从 `PR_GET_SECCOMP` 那句开始**执行流就断了**。

## 2. 原因：**引擎自己调用了一个"未放行"的 syscall**

`prctl` 自 **v0.7.83** 起已被**移出 BPF 放行清单**（为的是拦住 guest 用它装 seccomp）。
于是 —— **过滤器一旦生效，引擎自己调用 `prctl` 也会被自己的过滤器 TRAP**：

```
引擎执行 prctl(PR_GET_SECCOMP)
      ↓ 被自己的 BPF 判 TRAP
   SIGSYS → 进入我们的 handler
      ↓ handler 里继续调用引擎函数/vm_log（非重入安全）
   二次 TRAP / 死锁 → 执行流断裂
```

这正好解释了 v0.7.85~91 一路的怪现象：
**过滤器生效之后，任何"未放行 syscall"（不论来自 guest 还是引擎）都会让执行流断在这里**，
而断点处的日志自然永远打不出来。

> 这也是同一个坑的**第四次**变体：
> ① guest 的 syscall 被放行 → 绕过 handler；② 引擎的 syscall 未放行 → 自我 TRAP。
> 本质都是**放行清单与调用者不匹配**。

## 3. v0.7.92：修正自检的放置与方式

1. **删掉过滤器生效之后的那段自检**（`PR_GET_SECCOMP` + `/proc/self/status` 读取）——
   它在运行时必然自我 TRAP，是**有害**的自检；
2. 把 `PR_GET_SECCOMP` 挪到 **`prctl(PR_SET_SECCOMP)` 之前**执行（此刻过滤器还没生效，
   调用安全），得到"安装前的 seccomp 状态"这个基线；
3. 保留"自检 TRAP"（它是纯 `svc`，本身不依赖引擎/库调用）。

## 5. 下一轮（终于会看到的关键输出）

装 v0.7.92 → 点「运行」。这次如果 `自检 TRAP` 之后仍然没有 `[HR]`，
就说明**安装前的基线（PR_GET_SECCOMP）**与"装完后的行为"要分开看：

* `安装前 prctl(PR_GET_SECCOMP)=0`（预期）→ 过滤器由我们首次安装；
* 若自检 TRAP 仍然无 handler → **问题不在我们的安装，而在内核不投递**
  （接下来查 `SECCOMP_RET_TRAP` 在这台设备上是否被 App 策略层改写）；
* 反之若 handler 通了 → 说明前面的"零输出"全是**自检自身自我 TRAP** 造成的假象，
  guest 的流水会立刻恢复 —— 那将是重大进展。
