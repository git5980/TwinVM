```

```

**`PR_GET_SECCOMP=2` 是在我们安装之前读的** —— 说明：
**这个进程（App，来自 zygote）在我们动手之前就已经有 seccomp 过滤器了。**

## 2. 这就解释了全部现象（架构性根因）

Linux seccomp 语义：**同一进程可叠加多层过滤器；多层同时命中时取"动作优先级最高"的那个**
（`KILL_PROCESS > KILL_THREAD > TRAP > ERRNO > USER_NOTIF > LOG > ALLOW`）。

于是：

* **App 的 zygote 策略**（Android 标准）对**很多 syscall 判 KILL** ——
  我们自己的"扫雷"输出就是证据：
  ```
  [sweep] App 策略 KILL 名单（死于 31）共 80 个：
    18 39 40 42 51 58 89 99 100 104 105 106 112 116 142 … 234 235 236 237 238 239 248 … 273 …
  ```
  **注意其中 234/235/236/237/238/239/248…273** —— 这些正是我们**放行清单/判决表里**的号！
* 我们对某个 syscall 想要 `SECCOMP_RET_TRAP`，但**外层对同一个号判 `KILL_PROCESS`** →
  **内核取 KILL** → 进程**直接死**，我们的 handler 永远没有机会；
* 这就是为什么：
  * `HND#`/`[HR]`/`黑匣子` 全零（handler 从未被调用）；
  * 现象是"进程秒死"而不是"syscall 被拦"；
  * 我们改了多少轮实现都"没效果"——**问题不在实现，在过滤机制本身与宿主策略冲突**。

**结论：在 App 进程内用 `SECCOMP_RET_TRAP` 做用户态内核，与 Android 的 zygote seccomp
策略存在根本冲突。** 凡是我们需要 TRAP 的 syscall，只要外层判 KILL，就必然失败。

## 3. v0.7.93：记录结论 + 明确下一步方向

本轮代码侧只做了一处说明性修正（自检注释与顺序），核心产出是**这个根因判定**。
下一步有三条可行路线（按推荐度）：

| 路线 | 做法 | 评价 |
|---|---|---|
| **A. 换机制：`SECCOMP_RET_USER_NOTIF`** | 用 `seccomp(SECCOMP_SET_MODE_FILTER, SECCOMP_FILTER_FLAG_NEW_LISTENER)` 拿 listener fd，用 `SECCOMP_IOCTL_NOTIF_RECV/SEND` 收/回 syscall —— **不需要信号**，因此不受"外层 KILL"影响（外层若判 KILL 仍会 KILL，但对**外层 ALLOW 的号**可以正常拦截） | ✅ 最正统；工作量大 |
| **B. 精确规避：TRAP 集合 ⊆ App 策略 ALLOW 集合** | 把"要 TRAP 的号"与扫雷得到的 KILL 名单求交集，**交集内的号改为放行**（放弃虚拟化，让 guest 直接用） | ✅ 改动最小、可立刻见效；代价是那些 syscall 失去虚拟化 |
| **C. 换宿主：把 VM 跑在独立进程/自己 fork 的干净进程里** | 例如从 `app_process`/自建 native 可执行文件启动，避开 zygote 策略 | ⚠️ 受 Android 限制（无 root 时受限） |

## 5. 我的建议

**先走 B（立刻可用）**：把扫雷得到的 App-KILL 名单（80 个号）与我们的 TRAP 集合求交集，
交集内的号一律**放行**；这样 VM 至少能稳定跑起来、把 ART 启动推进下去。
**再走 A（根本解决）**：实现 `SECCOMP_RET_USER_NOTIF` 后端，彻底摆脱信号路径。
