# TwinVM v0.8.0 —— 路线 A：`SECCOMP_RET_USER_NOTIF` 后端（不吃信号）

> 起因：真机 v0.7.92/93 确认**架构性根因** ——
> App 进程天生带 zygote seccomp 过滤器（`prctl(PR_GET_SECCOMP)=2`），
> 而内核多层 seccomp **取动作优先级最高者**（`KILL_PROCESS > TRAP > ALLOW`）；
> 我们要 `TRAP` 的号里凡外层判 `KILL` 的，内核直接 KILL → 进程秒死、handler 永不进入。
> **结论：`SECCOMP_RET_TRAP` + SIGSYS 这条路线在本宿主上与系统策略根本冲突。**

## 1. 方案：改用 USER_NOTIF（内核 5.0+，本机 6.6 支持）

```
guest syscall
   ↓ 命中我们的过滤器
内核 SECCOMP_RET_USER_NOTIF → 挂起该调用，把请求投递到 listener fd
   ↓
监听线程 ioctl(SECCOMP_IOCTL_NOTIF_RECV, &req)
   ↓ 取 req.data.nr / args[] → 调 vm_handle_syscall()（引擎原有逻辑完全复用）
ioctl(SECCOMP_IOCTL_NOTIF_SEND, &resp)   → 内核把返回值写回 guest
```

**优势**：完全不依赖信号投递 ——
* 不受 `SA_ONSTACK`/掩码/迟到投递/外层 KILL 影响；
* `vm_handle_syscall()` 一行不用改（虚拟 fd 路由、ROM 读、/proc 合成全复用）；
* 只对"外层策略判 ALLOW 的号"生效，而文件 I/O 类恰好都是 ALLOW。

## 2. 实现清单

| 文件 | 改动 |
|---|---|
| `core/gen_bpf.py` | 新增 `emit_notif()`：生成**第二份过滤器** `VM_BPF_NOTIF_INSTRUCTIONS`。集合来源 = **从 `vm_core.c` 自动提取**"引擎有专门 case 分支的 syscall"（x86/arm 各自号表，避免手写错号） |
| `core/src/bpf_gen.h` | 多出 `VM_BPF_NOTIF_INSTRUCTIONS`（arm64 141 条 / x86_64 145 条），末尾回落 `USER_NOTIF → TRAP → KILL_PROCESS` |
| **`core/src/vm_notif.c`（新）** | `vm_notif_install()`：`seccomp(SECCOMP_SET_MODE_FILTER, FILTER_FLAG_NEW_LISTENER, &fprog)` 拿 listener fd；`vm_notif_loop()`：RECV → `vm_handle_syscall()` → SEND |
| `android/jni/twinvm_jni.c` | 启动时**优先** USER_NOTIF 后端 + 起监听线程；失败或 `TVM_LEGACY_TRAP=1` 时回退旧 SIGSYS 方案 |
| `core/tests/bpf_sim.py` | 认识 `SECCOMP_RET_USER_NOTIF`（0x7fc00000） |

**关键设计**：`resp.error` 用 `-r`（r 为负 errno）回填，正值直接作为返回值 —— 与 Linux 语义一致。

## 3. 构建期踩的坑（都已修，留档）

1. `VM_BPF_NOTIF_INSTRUCTIONS` 的**最后一行也要有续行符** —— 否则紧随的 `}` 会掉到宏外
   （报 `extraneous closing brace`）；
2. `#include "bpf_gen.h"` 必须放在**文件级**（旧代码放在函数内，宏展开路径不同）；
3. `SECCOMP_RET_USER_NOTIF` 在部分头文件里没有 → 两个 C 文件各自补 `#ifndef` 回退定义；
4. 生成器的后处理状态机要吃准"NOTIF 段"边界（以 `#define/#if/#endif/注释` 为界），
   否则会把相邻 `INSTRUCTIONS` 的结束 `}` 吃掉。

## 5. 下一轮预期

装 `TwinVM-Stage4-v0.8.0-notif.apk` → 点「运行」，日志里应出现：

```
[TwinVM] 拦截就绪（USER_NOTIF 后端，listener fd=N）
[TwinVM] USER_NOTIF 监听线程已启动
```

随后 **syscall 流水应当真正恢复**（不再有"过滤器后全静默"）：

* 成功 → ART 启动可以继续往下推进（这是自 v0.7.55 以来第一次绕开该冲突）；
* 若 `USER_NOTIF 安装失败: …` → 说明 `seccomp(2)` 被外层策略拦，日志会带 errno，
  届时改走"**父进程先装 listener 再 fork**"的变体（子进程继承 listener）。

（回退开关：`TVM_LEGACY_TRAP=1` 使用旧的 SIGSYS/TRAP 后端，便于对比。）
