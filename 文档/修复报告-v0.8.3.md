# TwinVM v0.8.3 —— 监听线程守则：绝不自递归（socket 自锁的真正机理与修法）

> 现场：`twinvm-live.log`（115 KB，v0.8.2）—— **卡点未变**

## 1. 为什么 v0.8.2 的修法没生效

v0.8.2 我在 `vm_notif.c` 里加了"socket 直答"，但真机日志里**引擎那句
`socket(AF_UNIX) -> 原生放行` 照旧打印**，然后 90 秒无输出被判卡死 —— 说明请求
**已经进了引擎**，而引擎里的实现是：

```c
case 198: ... {
    if (a0 == 1 /* AF_UNIX */) {
        vm_log("socket(AF_UNIX) -> 原生放行（本地 IPC）");
        return VM_PT3(VM_NR_socket, 1, a2, 0);   // ★ 裸 svc 直发
    }
```

**`VM_PT3` 是"handler 内裸 svc 直发"** —— 在 USER_NOTIF 架构下这是**自递归**：

```
guest 发 socket() → 内核挂起 → 监听线程 RECV
   → 引擎处理 → 裸 svc socket()  ← 由**监听线程**发出
      → 又命中我们自己的过滤器 → 内核再次挂起 → 等监听线程答复
         → 而监听线程正卡在这一步 → **死锁**
```

这与 v0.7.x 时期"SIGSYS handler 内裸 svc 会二次 TRAP"是**同一类错误**，
只是换成了 USER_NOTIF 版本：**服务者不能调用被自己服务的 syscall**。

## 2. v0.8.3 修法（两处）

| 位置 | 改动 |
|---|---|
| `vm_notif.c` | **所有 socket 请求由监听线程直接答复 `-EACCES`**（不再转交引擎、不做任何 socket 调用）。理由：监听线程里创建真 socket 必然自递归；而 VM 本来也没有网络栈 |
| `vm_core.c` | socket 分支**去掉 `VM_PT3` 直发**，改为直接返回 `-EACCES`（兜底：万一还有别的路径进到这里，也绝不阻塞） |
| `vm_notif.c` | 在监听线程入口写下**守则**：本线程只做 `ioctl(NOTIF_RECV/SEND)` 与纯内存操作 |

**通用原则（写进注释，后续沿用）**：
> **监听线程内绝不调用任何可能被自己过滤器拦截的 syscall。**
> 需要"真 syscall"的服务（如创建 fd），必须改由**别的线程**做，
> 或者由监听线程用 `SECCOMP_IOCTL_NOTIF_ADDFD` 把 fd 注入 guest。

## 4. 下一轮预期

装 `TwinVM-Stage4-v0.8.3-notif.apk` → 点「运行」：

* **socket 不再卡** → ART 拿到 `EACCES` 后应继续（`libstatssocket` 等有退化路径）；
* 若换到**别的号**卡住 → 同类自递归问题，按同一模式处理（监听线程直答 / 换线程执行）；
* 若继续推进 → 就会走到 ART Runtime 初始化的更深处。

## 5. 备用方案（若 ART 必须要有真 socket）

`SECCOMP_IOCTL_NOTIF_ADDFD` 允许监听线程**把一个真 fd 注入被拦截的进程**：
由**独立线程**（不受 NOTIF 服务阻塞）创建 socket，再用 ADDFD 交回 guest。
这条路已在报告里记下，等确认真需要时实现。
