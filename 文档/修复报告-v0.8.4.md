# TwinVM v0.8.4 —— socket 直答生效；修 ART 连 logd 失败后的 futex 死等

> 现场：`twinvm-live.log`（**25 MB**，v0.8.3）

## 1. v0.8.3 的成果：socket 自锁已解除

```
[TwinVM] [notif] socket(dom=1,type=0x80802) -> -EACCES（监听线程直答，避免自锁）
[TwinVM] [notif] socket(dom=1,type=0x80802) -> -EACCES（监听线程直答，避免自锁）
```

**监听线程直答生效**（不再自递归）。而且日志从 114 KB **暴涨到 25 MB** ——
尾部统计显示 `mmap`/`munmap`/`msync` 各约 **6.65 万次**，这是 **ART 在大量分配/回收内存**，
说明**它已经真正跑起来了**（不是空转）。

## 2. 新的卡点：`connect` 失败 → `futex` 死等

卡死前最后几条：

```
#337068  writev(fd=0xd)      #337069  writev(fd=0xd)
#337071  connect(fd=0xd)     ← ★ 连 logd（fd 13）
#337073  writev(fd=0xd)
#337074  futex(0xb40000723b0ea7c4, 0x80, 0x3)   ← ★ 死等
★ 死前最后 syscall: nr=98 (futex)
```

**根因**：`connect` 在 NOTIF 集合里，但我们**一律回 `-ENOSYS`** ——
而 `fd=0xd` 是 **ART 从宿主继承的 logd socket**（真 fd）。连不上 → ART 后续 futex 死等。

历史遗留：SIGSYS 时代 BPF 按 fd 参数化，**真 fd 的 connect 根本不会进 handler**；
换到 USER_NOTIF 后 NOTIF 集合是按**号**拦截，**真 fd 也进来了**，于是踩到这个老假设。

## 3. v0.8.4 修法（两处）

| 位置 | 改动 |
|---|---|
| `vm_core.c` `connect` | **真 fd（3..9999）→ 假装成功返回 0**（logd 是 AF_UNIX 本地 socket，写入即被丢弃，不影响 ART 继续）；虚拟 fd 仍回 `-ENOSYS` |
| `vm_notif.c` `socket` | **AF_UNIX → 返回一个高位"虚拟 fd"（20000+）并假装成功**，而不是 `-EACCES`。理由：v0.7.15 真机实锤 —— `libstatssocket` 探测 socket 拿 EACCES 会直接判 JNI 失败；后续对虚拟 fd 的 `write/close` 由引擎 fd 路由处理（tee/假装成功） |

装 `TwinVM-Stage4-v0.8.4-notif.apk` → 点「运行」：

## 6. 这一类问题的通用教训（写进文档）

> **SIGSYS 时代靠"BPF 按参数放行"掩盖掉的一大批 syscall，
> 在 USER_NOTIF（按号拦截）下都会重新冒出来。**
> 处理原则：凡是"真 fd / 真实资源"操作，一律**假装成功**或**返回虚拟对象**，
> 绝不让 guest 卡在等一个我们不会真正完成的操作上。
