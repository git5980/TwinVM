# TwinVM v0.8.6 —— ★ 抓到真正的死锁：监听线程被 `process_vm_writev` 卡住

> 现场：`twinvm-live.log`（14 MB，v0.8.5）

## 1. 决定性证据：两个线程的"最后活动"不对称

```
[trace] #4151    t797  nr=29  ioctl(0x3, 0xc0502100, …)     ← 监听线程 t797
[trace] #192849  t797  nr=271 process_vm_writev(0x313, …)    ← ★ t797 的最后动作
[trace] #192850  t797  nr=29  ioctl(0x3, 0xc0182101, …)
[trace] #192852  t797  nr=29  ioctl(0x3, 0xc0502100, …)      ← 之后 t797 再无事件
...
[trace] #193208  t787  nr=98  futex(0xb40000723aeea7c4, 0x80, 0x3)  ← 主线程死等
```

* **`t797` 是我们的 USER_NOTIF 监听线程**（可以看到它在 `ioctl(fd=3)` = listener）；
* 它最后一个动作是 **`process_vm_writev(271)`** —— 这个 syscall 在引擎里用于
  "把数据写进 guest 内存"（`vm_mem_write` 的安全访存路径）；
* 而 **`271` 当时还在 NOTIF 集合里** → **监听线程自己发的 `process_vm_writev`
  又被自己的过滤器挂起** → **监听线程自我阻塞**；
* 于是 `t787`（ART 主线程）的 `futex` **永远等不到监听线程来服务下一个请求** → 全局死锁。

**这与 socket（v0.8.3）是同一个错误的第三次出现**：
> **监听线程内绝不能执行任何会被自己过滤器拦截的 syscall。**

## 2. v0.8.6：把 `process_vm_readv/writev` 移出 NOTIF 集合

```
_VFS_ARM 去掉 270/271   _VFS_X86 去掉 310/311
```
并在生成器里写明原因（防止将来被"顺手加回来"）。

同时**复核了整张 NOTIF 表**（这次做了逐项验证）：

| 号 | 归属 | 是否正确 |
|---|---|---|
| `futex(98)` `munmap(215)` `mmap(222)` `clock_gettime(113)` `clone(220)` `rt_sigprocmask(135)` `wait4(260)` `gettid(178)` | **放行清单（ALLOW）** | ✓（线程/内存原语必须原生跑，否则创建线程即死锁） |
| `openat(56)` `close(57)` `fstat(80)` `read(63)` `write(64)` `socket(198)` `connect(203)` `execve(221)` `faccessat(48)` | **USER_NOTIF** | ✓（要虚拟化的文件/进程语义） |
| `process_vm_readv/writev(270/271)` | **已移出 NOTIF** | ✓（本轮修复） |

## 3. 验证

* `make -C core test` 5/5 PASS；`checkrom --strict` PASS；ROM md5 未变；
* 逐项核对 NOTIF 段：`270/271` 已不在其中，`56/57/80/63/64/198/203/221` 均指向 `USER_NOTIF`；
* APK `versionCode=123 / versionName=0.8.6`，同源签名。

## 4. 这个 bug 的通用形态（第三次出现，写进铁律）

> **USER_NOTIF 架构下，"监听线程"是整个 VM 的心脏。**
> 它只能做：`ioctl(NOTIF_RECV/SEND)`、纯内存计算。
> **任何**会被自己过滤器拦截的 syscall（无论直接还是间接、无论来自引擎哪一层）
> 都会让心脏停跳，表现为"guest 所有线程突然全部静止"。
>
> 排查套路：**看监听线程（那个反复 ioctl(fd=3) 的 tXXX）的最后一条 syscall** ——
> 它卡在哪里，就是把哪个号错误地放进了 NOTIF 集合。

## 5. 下一轮预期

* 若死锁解除 → ART 主线程的 futex 能被正常唤醒，流水继续增长；
* 若再静止 → 按上面"铁律 + 排查套路"直接看监听线程的最后一条 syscall，一步定位。
