# TwinVM v0.8.7 —— ★★★ 最致命的一个：`ioctl` 在 NOTIF 集合里，监听线程一开口就自缢

> 现场：`twinvm-live.log`（**5.7 KB**，v0.8.6）—— 日志骤降，说明卡在更早

## 1. 现场：连"拦截就绪"都没打印

```
[TwinVM] guest 槽位启动 pid=21152：ROM 67 inodes 就绪
[TwinVM] !! 看门狗：90 秒无任何控制台输出 —— 判定卡死，已强杀槽位
[TwinVM] [bb] 子进程最后的 syscall（seq=0）
```

**`USER_NOTIF 后端`/`监听线程已启动` 这两行都没出现** —— 而代码顺序是：

```c
sr = vm_notif_install(...);            // 打印"拦截就绪（USER_NOTIF 后端）"
pthread_create(&nth, NULL, vm_notif_loop, NULL);   // 打印"监听线程已启动"
```

也就是说：**`vm_notif_install()` 之后、打印之前就死了**，或者**监听线程一起就死**。

## 2. 根因：`ioctl` 在 NOTIF 集合里 —— 监听线程的"生命线"被自己拦下

监听线程的全部工作就是：

```c
ioctl(g_listener, SECCOMP_IOCTL_NOTIF_RECV, &req);   // ← 收请求
ioctl(g_listener, SECCOMP_IOCTL_NOTIF_SEND, &resp);  // ← 回答复
```

而 **`ioctl(29)` 恰好在 NOTIF 集合里**（因为引擎要拦截 guest 对虚拟 fd 的 ioctl）。
于是：

```
过滤器装好 → 监听线程第一次 ioctl(NOTIF_RECV)
   → 命中我们自己的过滤器 → 内核挂起这个 ioctl → 等监听线程来答复
      → 而它正卡在这一步 → **立刻死锁**，整个 VM 从第一毫秒就停摆
```

**这是同一类错误的最极端形态**：前三次（socket / connect / process_vm_writev）
是"某个业务路径偶然用到"；而 `ioctl` 是**监听线程自己的心跳**，
一旦被拦，VM 连启动都完不成。

## 3. v0.8.7：把 `ioctl` 移出 NOTIF 集合（唯一必须移出的一个）

在生成器里加入**监听线程安全集**并写明推导：

```python
# ioctl(29/16) 是唯一"监听线程必然调用"的号（NOTIF_RECV/SEND 本体）——
# 必须移出；其余（read/write/close…）由"监听线程不主动调用"来保证，
# 保留在 NOTIF 里才能让 guest 的 write-tee / 虚拟 fd read 继续工作。
_LISTENER_SAFE_ARM = {29}
_LISTENER_SAFE_X86 = {16}
```

**为什么只移它**：`read/write/close/openat/fstat/socket/connect/execve/faccessat`
都是 guest 侧必须虚拟化的语义，若一并移出会丢掉一半能力。
而"监听线程不调用它们"这条约束，**由代码结构保证**（监听线程只做 ioctl + 纯内存操作，
且之前几轮已把 socket/connect/process_vm_* 的自递归逐个消除）。

## 4. 逐项验证（arm64 NOTIF 段实测）

| 号 | 归属 | 期望 | 实测 |
|---|---|---|---|
| `ioctl(29)` | — | 不在 NOTIF（监听线程生命线） | ✓ 不在 |
| `read(63)` `write(64)` `close(57)` | NOTIF | 保留（tee / 虚拟 fd 路由） | ✓ |
| `openat(56)` `fstat(80)` `faccessat(48)` | NOTIF | 保留（VFS） | ✓ |
| `socket(198)` `connect(203)` `execve(221)` | NOTIF | 保留（已在监听线程内直接答复） | ✓ |
| `process_vm_readv/writev(270/271)` | — | 不在（v0.8.6 已移出） | ✓ |
| `futex/mmap/clone/rt_sigprocmask…` | ALLOW | 原生放行 | ✓ |

## 5. 验证

* `make -C core test` 5/5 PASS；`checkrom --strict` PASS；ROM md5 未变；
* APK `versionCode=124 / versionName=0.8.7`，同源签名。

## 6. 这一类 bug 的完整脉络（四连击，全部已修）

| 版本 | 被错误放进 NOTIF 的号 | 表现 |
|---|---|---|
| v0.8.3 | `socket(198)` | guest 的 socket() 自递归死锁 |
| v0.8.4 | `connect(203)` | 连 logd 后 futex 死等 |
| v0.8.6 | `process_vm_readv/writev(270/271)` | 监听线程自己卡住 → 全局静止 |
| **v0.8.7** | **`ioctl(29)`** | **监听线程一开口就自缢 → VM 起不来** |

**铁律（最终版）**：
> **NOTIF 集合 = "guest 需要虚拟化、且监听线程永不调用"的号。**
> 每加入一个号之前，先问：**监听线程会不会用到它？** 会 → 绝不能加。
