# TwinVM v0.9.1 —— ★ 精确定位：`seccomp(2)` 调用被**永久挂起**；加超时判定与自动降级

> 现场：`twinvm-20261014-214418.log`（v0.8.9）—— **新打的阶段进度立功了**

## 1. 界面/日志打点一步定位

```
[TwinVM] ▶ [1/6] 槽位启动 pid=18454，ROM 67 个文件就绪
[TwinVM] ▶ [2/6] 安装拦截器（USER_NOTIF）…
[TwinVM] [notif] 步骤0：进入安装（下一步 prctl）…
[TwinVM] [notif] 步骤1：prctl(PR_SET_NO_NEW_PRIVS) 返回 0（errno=0）
[TwinVM] [notif] 步骤2：syscall(seccomp, SET_MODE_FILTER, NEW_LISTENER)…
   ← 之后 90 秒无任何输出，看门狗强杀（code=-9）
```

**结论（无歧义）**：
* `PR_SET_NO_NEW_PRIVS` **成功**（返回 0）→ 不是它的问题；
* **`seccomp(SECCOMP_SET_MODE_FILTER, SECCOMP_FILTER_FLAG_NEW_LISTENER)` 调用之后，
  永远没有返回** —— 它被**永久挂起**。

## 2. 为什么会"永久挂起"

`seccomp(2)` 本身是一个普通系统调用，正常情况**立刻返回**一个 listener fd。
它**不返回**只可能是一种情况：

> **这个调用被外层的 seccomp 过滤器判成了 `SECCOMP_RET_USER_NOTIF`** ——
> 需要"外部的监听者"（App/系统）读取并答复；
> 而在这个进程/这台设备上**没有那样的监听者**（或监听者不会处理它），
> 于是内核把我们的调用**永远挂着**。

这与 v0.7.93 发现的"App 天生带 zygote 过滤器"完全一致：
**Android 的加固策略不只拦 syscall，还会对某些"敏感操作"（如自己装 seccomp）
使用 USER_NOTIF 做管控** —— 结果就是"我们想装用户态内核"这件事本身被摆了一道。

（`prctl(PR_SET_NO_NEW_PRIVS)` 能返回 0、而 `seccomp(2)` 被挂起，也正说明
策略是**针对 seccomp 安装这一动作**的，而不是笼统地拦所有敏感调用。）

## 3. v0.9.1：超时判定 + 自动降级（不再黑屏 90 秒）

```c
// 父进程（fork 之前）在**独立线程**里安装，主线程最多等 3 秒：
pthread_create(&ith, NULL, tvm_inst_thread, &inst_rc);
for (int ms = 0; ms < 3000; ms += 100) { if (inst_done) break; usleep(100*1000); }

if (inst_done && inst_rc == 0)  → ✓ 父进程装好，子进程继承（listener fd 跨 fork 保留）
else if (!inst_done)            → ✗ 判定"被永久挂起" → **自动降级**到 SIGSYS/TRAP 后端
```

三处改进：

1. **安装移到 `fork` 之前的父进程**（真机已知子进程会挂，换到父进程至少能判定；
   且过滤器与 listener fd 都跨 fork 继承）；
2. **3 秒超时**：被挂起也能**立刻得出结论**（而不是等看门狗 90 秒）；
3. **自动降级**：检测到挂起就改走 `SIGSYS/TRAP` 后端（`vm_sigsys_install`），
   `▶ [2/6] ✓ 拦截器就绪（SIGSYS/TRAP 回退）` —— 保证 VM 至少能继续跑。

## 5. 下一轮预期（界面会直接说话）

装 v0.9.1 → 点「运行」，3 秒内界面/日志就会出现下面之一：

| 输出 | 含义 | 后续 |
|---|---|---|
| `✓ 父进程已装好 USER_NOTIF …` | **父进程能装**（子进程才有问题）→ 继承方案可行 | VM 有望真正跑起来 |
| `✗ **seccomp(2) 被永久挂起**…改用 SIGSYS/TRAP` | 确认是策略管控 | 回到"路线 A 不可用"的结论，转 **SECCOMP_FILTER_FLAG_TSYNC 之外的第三条路**（见下） |
| `⚠ 父进程装 USER_NOTIF 失败: -N` | 拿到明确 errno | 按 errno 施策 |

**若确认"任何进程都无法自装 seccomp"**，剩余可行方向：

1. **借宿主已有的过滤器**：App 本身可能已经有一个（含 USER_NOTIF 监听？），
   想办法发现并复用它的 listener fd（`/proc/self/fd` 扫描 + `SECCOMP_IOCTL_NOTIF_RECV` 试探）；
2. **不用 seccomp 做虚拟化**：改用 `ptrace`（`PTRACE_SYSCALL`）—— 不依赖 seccomp，
   在 Android 上对**自己 fork 的子进程**是允许的（我们本来就有 tracer 线程，
   而且它已经在工作！）；
3. **限制目标**：只做"文件系统重定向 + 日志可见"，放弃 syscall 虚拟化。

其中 **方向 2（ptrace 后端）** 其实最顺 —— 项目里**已经有 ptrace 示踪器在工作**，
把它从"只观察"升级为"拦截并改写返回值"即可，且完全绕开 seccomp 限制。
