# TwinVM v1.0.2 —— ★ 揪出"双后端并存"：ptrace 与 USER_NOTIF 同时拦截同一批 syscall

> 现场：`twinvm-live.log`（15 KB，v1.0.1，用户运行 500 秒后手动退出）

## 1. 日志里的自相矛盾（一眼看出问题）

```
[TwinVM] ▶ [2/6] 安装拦截器（USER_NOTIF）…
[TwinVM] ▶ [2/6] ✓ 拦截器就绪（**ptrace 后端**：seccomp 已被系统封死）     ← 判定"挂起"
[TwinVM] ▶ [2/6] ✓ 拦截器就绪（USER_NOTIF, listener fd=118）              ← 又说"装好了"！
[TwinVM] ▶ [3/6] ✓ 监听线程已启动
```

**同一台机器、同一次运行，两个后端都被启用了。** 原因：

* v0.9.1 加的"3 秒超时"判定认为 `seccomp(2)` 被挂起 → 设 `g_notif_suspended = 1`；
* 但 **`seccomp(2)` 在超时之后仍然返回了成功**（listener fd=118）→
  父进程侧的线程把 `g_notif_inherited` 也置了位；
* 结果：**ptrace 拦截 + USER_NOTIF 拦截同时工作** → 同一个 syscall 被**处理两次**
  （一次被 ptrace 跳过改 x0，一次被 USER_NOTIF 答复）→ guest 拿到不一致的结果
  → `x0=0xf3` 野指针 → SIGSEGV。

**这解释了为什么 v1.0.1 修了"不该拦 270"之后崩溃现场一模一样** ——
因为真正的病根是**两套拦截机制打架**，而不是某个号被拦。

## 2. v1.0.2 修法：**互斥（只允许一个后端）**

| 位置 | 改动 |
|---|---|
| 父进程安装线程 | 若已判定 `g_notif_suspended`，则**忽略**姗姗来迟的 seccomp 成功，并打印<br>`▶ ⚠ seccomp 超时后才返回成功（fd=N）—— 忽略，只用 ptrace` |
| 子进程后端选择 | `if (g_notif_suspended)` 分支**优先且唯一**：走 ptrace，**不再**检查 `g_notif_inherited` |
| 监听线程 | **ptrace 模式下不启动** USER_NOTIF 监听线程（避免对一个没有请求的 listener 做阻塞 RECV）<br>输出改为 `▶ [3/6] ptrace 模式：跳过监听线程（拦截在示踪器里完成）` |
| 超时 | 3 秒 → **1.2 秒**（`seccomp(2)` 正常是"秒回"或"永不回"，1.2 秒足够区分；也减少误判窗口） |

## 3. 验证

* `make -C core test` 5/5 PASS；`checkrom --strict` PASS；ROM md5 未变；
* APK `versionCode=132 / versionName=1.0.2`，同源签名。

## 4. 下一轮预期（日志里应只剩一条后端声明）

装 `TwinVM-Stage4-v1.0.2-ptrace.apk` → 点「运行」，`[2/6]`/`[3/6]` 段应变成：

```
▶ [2/6] 安装拦截器（USER_NOTIF）…
▶ ⚠ seccomp 超时后才返回成功（fd=N）—— 忽略，只用 ptrace
▶ [2/6] ✓ 拦截器就绪（**ptrace 后端**：seccomp 已被系统封死）
▶ [3/6] ptrace 模式：跳过监听线程（拦截在示踪器里完成）
▶ [4/6] 装载 dalvikvm …
```

**只有 ptrace 一个后端**在拦截 → 不再有"双重处理"→ 若 ART 那条 `x0=0xf3` 消失，
说明修对了；若仍有崩溃，则是真的语义问题，届时按 `GUEST FAULT` 现场继续定位。

## 5. 一个额外收获

这次也验证了 **ptrace 后端能稳定跑 500 秒**（期间大量 syscall 被拦截改写），
说明该机制在本机上**确实可用且不崩** —— 唯一的问题就是"别让两个后端同时上岗"。
