# TwinVM v1.0.4 —— ★ 新线程的初始 SIGSTOP 被"注入"了：ART 等不到唤醒

> 现场：`twinvm-live.log`（**330 KB**，v1.0.3）—— 比上版（13 KB）**涨了 25 倍**

## 1. v1.0.3 的成果：SIGSEGV 消失，流水暴涨

```
▶ [6/6] 已进入 ART
（无 GUEST FAULT —— v1.0.3 的 entry/exit 修复生效，addr=0xf3 崩溃彻底消失）
#1 … #4340  共 4340 个 syscall
```

**从"进 ART 就崩"到"稳定跑 4340 个 syscall"** —— entry/exit 寄存器分离的修复是对的。

## 2. 新卡点：`futex` 死等，而且**全程只有一个线程**

```
#4292  nr=98  futex(0xb4000071ea666984, 0x80, 0x3)
#4293  nr=98  futex(…)                      ← 连续重试
#4294  nr=98  futex(…)
★ 死前最后 syscall: nr=98 (t26046)
```

```
出现过的线程: 只有 t26046     ← ★ 没有任何新线程！
```

**`futex(addr, FUTEX_WAIT|PRIVATE)` 是在等另一个线程唤醒，但那个线程从没跑起来。**

## 3. 根因：`PTRACE_O_TRACECLONE` 的"新线程初始停点"被我们注入了 SIGSTOP

我们启动时设了 `PTRACE_O_TRACECLONE`（想跟踪新线程）。它的语义是：
**`clone` 出来的新线程在开始执行前会先停下**，并给 tracer 一个 `SIGSTOP` 事件。

而 tracer 循环原来的分支是：

```c
} else {
    ptrace(PTRACE_SYSCALL, t, 0, sig);   /* "真信号：必须转发" */
}
```

于是**新线程的初始 SIGSTOP 被当成"真信号"原样注入** → **新线程真的被 SIGSTOP 挂住** →
它永远不会运行、永远不会去唤醒主线程 → **主线程 `futex` 死等** →
日志里"只有一个线程"、`clone` 之后毫无下文。

（这也解释了为什么 `futex` 参数看着"怪"：`a1=0x80` 只是 `FUTEX_PRIVATE_FLAG`，
`a2=3` 是 artifact —— 重点不在参数，而在"没人来唤醒"。）

## 4. v1.0.4 修法

```c
} else if (sig == SIGSTOP && t != g_t_pid) {
    /* 新线程的初始停点：**吞掉 SIGSTOP**（不注入），直接续跑 */
    vm_log("[trace] 新线程 t=%d 初始停点：吞掉 SIGSTOP，续跑", (int)t);
    ptrace(PTRACE_SYSCALL, t, 0, 0);
}
```

另外**给 `clone/clone3` 加了显式日志**，便于确认线程创建链路：

```
[trace] ★ clone(nr=220) 由 t=… 发起 —— 期待新线程停点
[trace] 新线程 t=… 初始停点：吞掉 SIGSTOP，续跑
```

## 6. 下一轮预期

装 `TwinVM-Stage4-v1.0.4-ptrace.apk` → 点「运行」，日志里应出现：


"多线程 ART"这一整块，也是之前所有方案都没走到过的地方）。
