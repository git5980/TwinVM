# TwinVM v1.0.6 —— ★ 宿主 fd 泄漏：ART 拿到 fd=99 后反复 read → 重试死循环

> 现场：`twinvm-live.log`（**102 KB**，v1.0.5）—— 日志降噪生效（从 26 MB 降到 100 KB）

## 1. v1.0.5 的降噪成功，但新卡点更清晰了

日志现在**只记被拦截的 syscall**（不再被 GC 刷屏），卡死现场一目了然：

```
#1193..#1200  nr=63  read(fd=0x63=99, buf=0xb40000723b091000, 0x400) × 8   ← ★ 反复读同一个 fd
#1201         nr=57  close(0x63)
#1202         nr=167 prctl(0x53564d41="AVMS", …)     ← PR_SET_VMA 命名匿名内存
#1203         nr=66  writev(0x53, …)
★ 死前最后 syscall: nr=98 futex
```

被拦截 syscall 统计：`read(63) 457`、`prctl(167) 215`、`openat(56) 126`、`close(57) 112`…

## 2. 根因：`fd=99` 是**宿主/引擎的 fd**，被 fork 继承给了 guest

* `fd 99` 从来不是我们分配的（虚拟 fd 一律 `≥10000`，见 `vm_vfs_open` 返回 `VM_FD_BASE + i`）；
* 它是 **`fork()` 时从父进程（App/引擎）继承下来的宿主 fd**；
* ART 拿到它后**反复 `read`** —— 而我们 v0.8.5 的"隔离守卫"对真 fd **返回 0（EOF）**，
  ART 把 0 理解成"暂时没有数据，稍后再读" → **重试循环** → 最终 `futex` 死等。

**两个问题叠加**：
1. **泄漏**：子进程继承了宿主全部 fd（0..255）；
2. **语义**：`read(真 fd)` 返回 0 会诱发重试 —— 应返回 **`-EBADF`**（"这个 fd 不存在"）。

## 3. v1.0.6 修法（两处，标本兼治）

### (a) 治本：`fork` 后**关闭继承的宿主 fd**

```c
close(L->rfd);
/* 只保留 console 管道与 listener，其余 3..255 全部关闭 */
int keep[4] = { L->wfd, vm_notif_fd() };  int nk = …;
for (int fd = 3; fd < 256; fd++)
    if (not in keep) close(fd);
vm_log("▶ 已关闭继承的宿主 fd（保留 console=%d）", L->wfd);
```

### (b) 治标：`read(真 fd)` 从 `0` 改为 **`-EBADF`**

```c
if (a0 > 0 && a0 < VM_FD_BASE) {
    vm_log("!! read(真 fd=%ld) → -EBADF：guest 不该看到宿主 fd（隔离守卫）", a0);
    return -VM_EBADF;      /* 明确"不存在"，调用方会放弃而不是重试 */
}
```

**这一条同时把 v0.8.5 那次的判断纠正过来** —— 当时我选 0(EOF) 是"友好"，
但真机证明它诱发重试循环；`EBADF` 才是正确的"不可用"信号。
