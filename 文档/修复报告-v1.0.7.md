# TwinVM v1.0.7 —— ★ fd 清理放错了进程：guest 槽位是 `jni_guest_main` 内部 fork 出来的

> 现场：`twinvm-live.log`（102 KB，v1.0.6）

## 1. v1.0.6 的部分生效 + 关键线索

```
#1193..#1198  read(fd=0x5, buf=0xb40000723ae91000, 0x400) × 6    ← fd 从 99 变成了 5
#1199         close(0x5)
#1200         prctl(AVMS)
#1201         writev(0x4, …)
★ 死前最后 syscall: nr=98 futex
```

**`fd 99 → fd 5`** 说明：
* v1.0.6 的"EBADF 语义"确实起作用了（ART 放弃了 99）；
* 但**它马上又拿到了另一个宿主 fd（5）**，继续同样的重试模式。

而且日志里**完全没有**我 v1.0.6 加的那行：

```
▶ 已关闭继承的宿主 fd（保留 console=N）      ← 从未打印
```

## 2. 根因：清理代码放进了"错误的那次 fork"

`twinvm_jni.c` 里有**多处 `fork`**：

| 位置 | 作用 |
|---|---|
| `tvm_tracer_main()` 里的 `fork`（line 642） | 创建被追踪的子进程骨架 |
| **`jni_guest_main()` 内部还有 2 次 `fork`** | **真正的 guest 槽位进程** |

我把 fd 清理加在了**前者**，而 **guest 槽位是 `jni_guest_main()` 内部 fork 出来的** ——
那条路径上**从来没有执行过清理**，所以 ART 依然继承着宿主 fd。

（那行日志没出现，就是最直接的证据：**代码根本没跑到**。）

## 3. v1.0.7 修法

### (a) 把 fd 清理移到**槽位进程的真正入口** `jni_guest_main()` 开头

```c
static void jni_guest_main(const VmRom* rom, int console_fd) {
    /* ★ 每个槽位进程的第一步：关闭继承的宿主 fd，只留 console(+listener) */
    int keep[3] = { console_fd, vm_notif_fd() }; int nk = …;
    for (int fd = 3; fd < 256; fd++)
        if (not in keep) close(fd);
    vm_log("▶ 槽位已清理继承的宿主 fd（保留 console=%d）", console_fd);
    …
}
```

**放在这里才万无一失** —— 无论槽位是哪个 fork 出来的，进入 guest 代码前一定过这一关。

### (b) `read(真 fd)` 守卫改为**限流多次记录**（每个坏 fd 记 8 次）

```c
static long s_fd[8]; static int s_n[8];
… vm_log("!! read(真 fd=%ld) → -EBADF（第 %d 次）…", a0, s_n[slot]);
```

**目的**：下次日志里能直接确认"ART 是否还在反复 read 同一个坏 fd"这个模式 ——
上一次因为只打一条（`warned` 标志），反而看不出重试次数。

## 4. 验证

* `make -C core test` 5/5 PASS；`checkrom --strict` PASS；ROM md5 未变；
* APK `versionCode=137 / versionName=1.0.7`，同源签名。

## 5. 下一轮判定

装 `TwinVM-Stage4-v1.0.7-ptrace.apk` → 点「运行」，重点看两行：

| 观察 | 结论 |
|---|---|
| 出现 `▶ 槽位已清理继承的宿主 fd（保留 console=N）` | 清理**这次真的执行了** |
| 不再有 `read(真 fd=…) → -EBADF（第 N 次）` | fd 泄漏根除 |
| 若仍有 EBADF 告警 | 说明是 ART 自己 openat 拿到后又用错，另作处理（会带次数，好判断） |

## 6. 经验（值得记下）

> **同一个函数里有多次 `fork` 时，"子进程初始化代码"必须放在最靠近 guest 入口的那一次。**
> 这次我把清理放在了 tracer 的 fork 里，而真正的槽位是 guest_main 内部再 fork 的 ——
> **日志里那行"应该出现却没出现"的日志，就是定位这个错误的关键证据。**
