# TwinVM v1.1.1 —— ★★ 找到"诊断日志全丢"的真因：tracer 线程里 `vm_log` 写不出去

> 现场：`twinvm-live.log`（44 KB，v1.1.0）

## 1. v1.1.0 的矛盾

```
▶ [1/6] 槽位启动 pid=31925，ROM 67 个文件就绪
▶ 槽位 fd 清理完成（关掉 0 个高位 fd，保留 console=141）
▶ [6/6] 已进入 ART
[trace] #… 543 条            ← ptrace 停点**在正常工作**
```

**但**：
* `[ptrace] GSI: r=… op=… nr=…` **0 条**（我新加的最关键诊断）
* `[ptrace] 回填 #…` **0 条**
* `[ptrace] !! GETREGSET 失败` **0 条**

**而 GSI 日志就在 `[trace]` 之前几行、同一个分支里** ——
`[trace]` 打了 543 条，GSI 却一条没有，这在同一段代码里**不可能同时成立**。

## 2. 真因：两条日志通道不同

```c
// ① vm_log：走 vm_console_fd（console 管道）
vm_log("[ptrace] GSI: …");        ← 全丢

// ② live_write：直写 g_live_fd（实时日志文件）
live_write(hm, n);                ← [trace] 走这条，成功
```

**console 在 guest 启动后已被接管**（guest 的 stdout/stderr 重定向到 console），
于是 **tracer 线程里所有 `vm_log` 输出全部丢失** —— 而 `[trace]` 用的是
`live_write`（直接写实时文件 fd），所以完好。

**这解释了为什么连续几轮"诊断加了却看不到"**：不是代码没跑，是**日志通道选错了**。

## 3. v1.1.1 修法

新增 **`ptrace_log()`**：与 `live_write` 同路径（直写实时文件 + `LOGI` 兜底），
并**把 tracer 线程内全部 `vm_log` 替换为 `ptrace_log`**（共 16 处）：

```c
static void ptrace_log(const char* fmt, ...) {
    char buf[512];
    int k = snprintf(buf, sizeof(buf), "[TwinVM] ");
    va_list ap; va_start(ap, fmt);
    vsnprintf(buf + k, sizeof(buf) - (size_t)k - 1, fmt, ap);
    va_end(ap);
    size_t n = strlen(buf);
    if (n + 1 < sizeof(buf)) { buf[n] = '\n'; n++; }
    live_write(buf, n);          /* ★ 关键：走实时文件，不走 console */
    LOGI("%s", buf);
}
```

同时**放宽限流**，让几百条 syscall 的运行也能看到诊断：
* GSI 记录：6 条 → **20 条**
* 心跳：每 2000 → **每 200** 条 syscall

## 4. 验证

* `make -C core test` 5/5 PASS；`checkrom --strict` PASS；ROM md5 未变；
* APK `versionCode=141 / versionName=1.1.1`，同源签名。

## 5. 下一轮必然能看到（这次通道对了）

装 v1.1.1 → 运行 → 日志里**一定**会出现：

```
[TwinVM] [ptrace] GSI: r=88 op=1 arch=183 nr=56（t=…）      ← entry 停点原始值
[TwinVM] [ptrace] GSI: r=88 op=2 arch=183 nr=56（t=…）      ← exit 停点
[TwinVM] ▶ 已虚拟化 200 个 syscall（最近 nr=…）
[TwinVM] [ptrace] 回填 #1：nr=56 → x0=10000
```

**由 `op` 的真实取值就能判定**：我假设的 `op==1(entry)/2(exit)` 是否成立 ——
这正是"回填从未发生"的最后一个未知量。

## 6. 方法论教训（第三次同类）

> **"代码写了但日志没有"时，先怀疑日志通道，而不是怀疑逻辑。**
> 这已经是本项目第三次因为"静默"浪费轮次（前两次：`read` 真 fd 守卫、
> 寄存器访问失败的 `if (ok)` 无 else）。
> **排查顺序应该是：① 通道通不通 → ② 分支进没进 → ③ 逻辑对不对。**
