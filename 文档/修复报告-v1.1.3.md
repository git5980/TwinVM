# TwinVM v1.1.3 —— ★★★ 揪出"卡 300 秒"的元凶：`close` 风暴（446 次，每次 EBADF）

> 现场：`twinvm-live.log`（42 KB，v1.1.2，用户实测**卡 300 秒不动**）

## 1. v1.1.2 的修复**部分生效**

```
[ptrace] 回填 #1：  nr=64 → x0=80       ← ★ 不再是恒定的 57！FIFO 配对生效了
[ptrace] 回填 #201：nr=57 → x0=-9
[ptrace] 回填 #401：nr=57 → x0=-9
```

**`nr` 开始随 syscall 变化** —— v1.1.2 的 entry/exit FIFO 配对**方向正确**。

## 2. 但暴露了下一个（也是更严重的）问题：`close` 风暴

被拦截 syscall 分布：

```
446  nr=57  (close)     ← ★★★ 占全部拦截的 87%！
 14  nr=167 (prctl)
 12  nr=64  (write)
  4  nr=66  (writev)
  3  nr=79  (newfstatat)
  2  nr=56  (openat)     ← 只 2 次，与 close 严重不匹配
```

**因果链**：

1. `close(fd)` 里的 `fd` 是 **`0xfa~0xff`（250~255）** —— 这是**我们没发过的"真 fd 号段"**；
2. 引擎的 `case VM_NR_close` 对真 fd 走 `vm_vfs_close()` → 虚拟表里没有 → **返回 `-EBADF(-9)`**；
3. **调用方（ART）拿到 EBADF 后重试** → 又一次 close → 又是 EBADF → **死循环**；
4. 界面**卡住 300 秒不动**，用户只能手动退出。

**这解释了"为什么改了半天还是卡"** —— 不是程序在等某个资源，而是**在一个永不成功的 close 重试环里空转**。

## 3. v1.1.3 修法：`close` 对真 fd **假装成功**

```c
case VM_NR_close: {
    if (a0 == 0 || a0 == 1 || a0 == 2) return 0;   /* stdio */
    /* ★ 真 fd（3..VM_FD_BASE-1）一律返回 0：对 guest 而言"关就关成功了" */
    if (a0 >= 3 && a0 < VM_FD_BASE) return 0;
    return vm_vfs_close(c->vfs, (int)a0);          /* 虚拟 fd：正常回收槽位 */
}
```

**语义依据**：我们本来就是**虚拟文件系统** —— fd 由我们发号，
guest 想关哪个 fd 都**无害**（它不是宿主的真资源）。
返回 EBADF 只会让调用方走进"错误处理/重试"分支，毫无收益。

**这一条同时消除**：
* 446 次的 `close` 风暴；
* 随之而来的 300 秒卡死；
* 以及"close 失败"可能引发的其他退化路径。

## 6. 本轮教训（第二类：**错误返回值的连锁反应**）

> **对虚拟化层来说，"返回错误"往往比"假装成功"更危险。**
> `-EBADF` 在真实内核里意味着"这个 fd 不存在，别再用了"；
> 但在**调用方有重试逻辑**的场景（ART 的 fd 管理尤其如此），
> 它会变成**无限重试**。
>
> 判断标准：**这个错误是否会让调用方做出"有意义的不同行为"？**
> 否 → 假装成功；是 → 才给错误。
>
> 本项目已累计三处同类修复：`read`（0→EBADF，反向）、`connect`（真 fd 假装成功）、
> 以及本轮的 `close`（真 fd 假装成功）。
