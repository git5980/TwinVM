# TwinVM v1.1.6 —— 挖出疑似总根因：父进程引擎从未装配（零 g_cpu）

> 输入：v1.1.5 真机日志（1647 行）。本轮证据链大丰收：[sig] 现形、PR_SET_PTRACER
> 修复生效、guest 走到 3 倍深度、卡点转移——并且顺藤摸瓜挖出一个架构级缺陷。

## 1. v1.1.5 日志判读（四项实锤）

### 1.1 崩溃信号三要素现形

```
[sig] t=8771 收到信号 6（code=-1 发送方 pid=8771）pc=0x723c1f7c1c lr=0x723c1f7bf8
```

信号 6 = **SIGABRT（自杀）**。用 ROM 里的 linker64 符号表离线符号化：
`pc = __dl_abort+0xa0、lr = __dl_abort+0x7c`（linker bias=0x723c158000，
偏移 0x9FC1C/0x9FBF8）——**guest 是主动 abort()，不是段错误**。
PC 落在 abort() 自身，真正要的是**调用者**——v1.1.6 的 FP 链回溯补上。

### 1.2 PR_SET_PTRACER 修复生效，深度 3 倍

v1.1.3 的 close 假装成功 + v1.1.5 的 PR_SET_PTRACER 假装成功都验证通过：
guest 从 489 事件推进到 **1514 事件**，debuggerd 转储线程（t8772）也正常 clone
出来了。卡点后移到：`libc: failed to open /dev/null: Permission denied`。

### 1.3 /dev/null EACCES 的两个嫌疑人

- 嫌疑 A：openat 的**只读文件系统守卫**（`(a2 & 3)!=0` → EACCES，debuggerd 用
  O_RDWR=0x2 打开 /dev/null 被挡）；
- 嫌疑 B（更根本，见 §2）：路径根本没读出来（vm_mem_read 失败也回 EACCES）——
  两个路径不可区分，v1.1.6 双修。

### 1.4 [tee] 的 PEEKDATA 悬案

guest 的 write/writev 载荷我的 tee 全部读成 "0 B"（PEEKDATA 对 guest 栈/堆地址
屡屡 EIO），而引擎的 process_vm_readv 路径工作正常——**tracee 内存读取不再依赖
PEEKDATA，全面换 process_vm_readv + errno 落日志**。

## 2. ★★★ 疑似总根因：父进程引擎零装配

架构事实：v1.0.0 起 syscall 由**父进程**（示踪线程）在 exit 停点调
`vm_handle_syscall` 判决；但全工程**唯一的 `vm_machine_setup` 跑在子进程**
（jni_guest_main，fork 之后）——fork 内存独立，**父进程的 g_cpu 永远是零值**：

| 零值字段 | 后果 |
|---|---|
| `vfs=NULL` | guest 的 openat 读不出路径 → 一律 -EACCES |
| `mem.pid=0` | process_vm_readv(0)=ESRCH → write/writev 载荷全丢（**ART 的 Fatal signal/abort 原文进不了日志的直接原因**） |

**为什么 boot 还能全过？** 装载阶段（dalvikvm+linker64+全部 DT_NEEDED）是
exec_dyn 在子进程**进程内直调 vm_vfs_open**（不走 syscall）——装载不经过父侧
引擎。这正好解释"六阶段全绿 → ART 一到真 openat（#473）就死"。

**修复**：父进程在 fork 后立即 `vm_machine_setup(L->rom, pid, 0)`，并把
`vm_console_fd` 指到 live 文件（此前=2=App stderr=/dev/null，引擎 tee 全进黑洞）。
装配自检行 `[engine] 父进程引擎装配完成：pid=… vfs=OK mem_pid=… console=…`
会出现在日志头部，一行定生死。

## 5. 下一轮判据（真机跑 v1.1.6）

```
[TwinVM] [engine] 父进程引擎装配完成：pid=… vfs=OK mem_pid=… console=…
    ← 头部必须见到（否则判读全部作废，先看为什么没跑）
[TwinVM] [tee] fd=2 writev（N B）: <Fatal signal 原文>   ← abort 原因现形
[TwinVM] [sig]   #0 ret=0x… #1 ret=0x… …                   ← abort 调用链
[TwinVM] [maps] guest 布局落盘：…                          ← 符号化基址
openat("/dev/null") -> fd=100xx [虚拟字符设备]              ← debuggerd 不再死
```

若装配行出现且 tee 现出原文 → 直接对凶手动刀；若 vfs=NULL 仍现 → 装配时序问题
（fork 与 setup 的先后），下一步把装配挪进握手前。

## 6. 本轮教训（第五类：**跨进程架构要重验"谁在跑引擎"**）

> 切 ptrace 后端（v1.0.0）时 syscall 判决权移交给了父进程，但引擎装配调用
> 还留在子进程——**架构迁移最容易漏的就是这种"初始化还在旧世界"**。
> 判据：新架构里每个使用 g_cpu 的路径，都要问一句"它在哪个进程跑、
> 那里的 g_cpu 是谁装配的"。
