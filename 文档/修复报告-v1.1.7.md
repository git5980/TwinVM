# TwinVM v1.1.7 —— 观测通道总闸门：dumpable=0（全量读失败的共同根因）

> 输入：v1.1.6 真机日志（1674 行）。v1.1.6 的父进程引擎装配验证通过，并顺藤
> 摸到了所有"读不出 guest"现象的共同根因。

## 1. v1.1.6 判读（三项实锤）

1. **装配成功**：`[engine] 父进程引擎装配完成：pid=12867 vfs=OK mem_pid=12867 console=135`
   ——v1.1.6 的核心修复落地，引擎在父侧真正可用。
2. **/dev/null 设备生效**：`openat("/dev/null") -> fd=10060 [虚拟字符设备]`，
   EACCES 卡点解除；**tee 首次读到 writev 载荷**：
   `libc: expected /dev/null fd to be 0, actually 10060: Try again`。
3. **内存读取同源失败**（关键证据）：
   - t12867（guest 主线程）：从事件 #1 起 tee/engine 全部读失败，
     `pv_errno=1(EPERM) / peek_errno=5(EIO)`；
   - t12884（dump 线程）：崩溃处理器 #486 `prctl(PR_SET_DUMPABLE,1)` **之后**
     的读取全部成功。

**结论：guest 槽位继承 App 进程的 dumpable=0（zygote 传统）**。
process_vm_readv / PEEKDATA 走 ptrace_may_access，对 non-dumpable 目标
（无 CAP_SYS_PTRACE）一律 EPERM——**引擎从第一天起就是瞎的**：
openat 路径 EACCES、writev 载荷 [bad iov]、[sig] FP 链断、/proc/maps ENOENT，
全是这一条。崩溃处理器自己把 dumpable 设回 1 后 dump 线程才可读——铁证。

## 2. 新卡点：/dev/null 的 POSIX fd 语义

linker64 `debuggerd_dispatch_pseudothread`（0x1014bc）反汇编判决：

```
close(0..1023) → open("/dev/null",O_RDWR) → 若 fd!=0 → fatal
    "expected /dev/null fd to be 0, actually %d"（0xa69c）
→ dup2(0,1) dup2(0,2) → pipe2 ×2 → writev 崩溃包 → fork 转储子进程
```

伪线程全量清扫 fd 后重开 /dev/null，依赖 POSIX "最低空闲 fd" 语义要求
拿回 fd 0——VFS 发 10060 直接 fatal（v1.1.6 日志末行实锤）。

## 6. 本轮教训（第六类：**权限状态也是"系统调用语义"的一部分**）

> 排查"读不到目标内存"时，除了地址和原语，还要问**目标的权限位**——
> dumpable/ptracer/selinux 域。一个继承来的 dumpable=0 让整条观测链
> （引擎、tee、FP 链、maps）集体失明，还各自表现为不同的 errno
> （EPERM/EIO/ENOENT/EACCES）——同一根因，五种伪装。
