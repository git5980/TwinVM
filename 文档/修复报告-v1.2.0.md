# TwinVM v1.2.0 —— 库装载三件套：fstatfs 补名单 + mmap-fill（ptrace 后端的 .so 映射）

> 输入：v1.1.9 真机日志（707 行）。exec 自我认知修复验证通过，guest 走到
> **linker 运行时装载 DT_NEEDED**（liblog.so）——这是 ART 启动链的真正深水区。

## 1. v1.1.9 判读

- **"unable to stat" 消失**——/proc/self/exe 闭环验证通过（v1.1.9 修复生效）；
- ld.config 链全通：`/system/etc/ld.config.txt → fd=10000 [ROM]`；
- guest linker 开始装载 liblog.so：`openat → fd=10000 [ROM] ✓ → fstat(80) ✓ →
  readlinkat/newfstatat ✓`，死于：
  `CANNOT LINK EXECUTABLE "dalvikvm": unable to fstatfs file for the library "liblog.so": Bad file descriptor`

## 2. 两个新卡点（一并修）

### 2.1 fstatfs(44) 漏出拦截名单

`tvm_virt_nr` 有 43（statfs）没有 **44（fstatfs）**——linker 的 fstatfs 带着
虚拟 fd=10000 直通宿主内核 → EBADF。名单补 44（引擎的 statfs 填充分支现成）。

### 2.2 mmap(虚拟 fd)：SIGSYS 时代设计在 ptrace 后端完全不可用

linker 过了 fstatfs 就要 `mmap(fd=10000)` 映射库内容。两个坑：
- 222 本来就在"明确不拦截"名单 → 原生执行 → 虚拟 fd → EBADF；
- 引擎的 mmap 分支用 `vm_syscall6+memcpy` 在**调用者进程**造页——SIGSYS 后端
  下调用者=guest 进程（正确）；ptrace 后端下调用者=**父进程**（灾难：页造到
  父进程里，guest 拿到的是父进程地址）——这就是悬了很久的"x86 mmap(虚拟fd)
  处理路径死之谜"的真相。

## 3. v1.2.0 修复：mmap-fill（参数改写 + 原生执行 + 内容回填）

```
entry：不动 x8（不跳过）——改写参数：prot |= PROT_WRITE、
       flags = (MAP_FIXED 保留)|MAP_PRIVATE|MAP_ANONYMOUS、fd=-1、offset=0，
       让子进程的内核真造页（返回真实 guest 地址）；
exit ：x0 = guest 新页地址 → 父进程用 process_vm_writev 分块灌入
       ROM inode 内容（源=父进程 ROM 映射，fork 继承、本就共享）。
```

- 权限收紧交给 guest linker 自己的 mprotect（bionic 装段必调）；
- i-cache：全新匿名页从未执行过，无陈旧行（REUSE 风险已知，[sig] 会现形）；
- 配套：引擎导出 `vm_vfs_fd_data()`（fd→ROM inode 数据）。

## 6. 本轮教训（第八类：**后端迁移要审" syscall 的物理执行域"**）

> 同一段引擎代码，在 SIGSYS 后端（跑在 guest 进程里）和 ptrace 后端（跑在
> 父进程里）语义完全不同——**凡是"在调用者地址空间里动手"的 syscall 实现
> （mmap/mprotect/brk 家族），换后端必须重审**。判据：这个 case 里的每一次
> 内存写入/映射，落在了哪个进程的地址空间？
