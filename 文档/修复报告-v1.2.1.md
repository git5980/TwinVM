# TwinVM v1.2.1 —— /apex 动态直读：ROM 缺的 art 库从设备真身取

> 输入：v1.2.0 真机日志（5731 行）。mmap-fill 全面验证通过，死点推进到
> ROM 内容缺口：libartbased.so。

## 1. v1.2.0 判读

- **mmap-fill 全面开工**：**227 次"灌入完成"**——linker 用它装完了一串库：
  liblog → libnativehelper → libsigchain → libdl_android → libc++ → libc →
  libm → libdl → libunwindstack → libbase → **libart** → libartpalette →
  liblz4 → libnativebridge → libnativeloader → libartbase → …
  （每个 .so 数段映射，全部成功——机制正确性实证）
- **新卡点**：`libartbased.so` ENOENT——linker 找遍 `/system/lib64`、`/odm/lib64`、
  `/vendor/lib64` 全 miss。**ROM 里确实没有这个文件**（Android 16 从 libartbase
  新拆出来的库，当初 syncrom 快照没包含）。checkrom 不报它是因为它不是
  DT_NEEDED 链（运行时 dlopen/构造期装载）。

## 2. v1.2.1 方案：/apex/com.android.art/ 白名单直读宿主

宿主机的 `/apex/com.android.art/lib64/` 里就有 libartbased.so——**同一台
OnePlus、同一个系统版本 = 同快照铁律天然满足**，App 域可读。让 VFS 在
ROM miss 后对 `/apex/com.android.art/` 前缀做"直读宿主"：

| 件 | 实现 |
|---|---|
| **动态文件表** | 槽 64..95（VM_MAX_FILES 64→96），rom_idx==-3，`g_dyn_data/g_dyn_len`（malloc 全量缓冲） |
| openat | /apex 前缀 miss → 宿主 open+fstat+读全量 → 动态槽（≤64MB）→ VFS fd |
| read/seek | vm_vfs_read/seek 支持 -3（与 ROM 文件同语义） |
| fstat/newfstatat | -3 → 0100555+真实 size；/apex 路径 stat → 宿主真 stat |
| **mmap-fill** | vm_vfs_fd_data 支持 -3（灌内容来源=动态缓冲）——父进程统一视角 |

非 /apex 路径仍严格 ENOENT（隔离不放松）。

## 3. 验证

- `make -C core test` 5/5 PASS；`checkrom --strict` PASS；ROM md5 未变（fa88cc28）；
- APK SIGN_OK / versionCode=151；包内 ROM md5 = fa88cc28 ✓。

## 4. 下一轮判据（真机跑 v1.2.1）

```
openat("/apex/com.android.art/lib64/libartbased.so") -> fd=100xx [/apex 直读 NB]
[mmap-fill] ✓ fd=100xx … 灌入完成     ← 动态文件也走映射
```

此后 linker 继续装剩余库（可能再触发若干 /apex 直读）→ ART Runtime init →
理想 `Hello TwinVM from ART`。若卡新点照常落日志。

## 5. 本轮教训（第九类：**镜像快照会过期于系统演进**）

> ROM 是某次快照的静态集合，而 art 生态在拆库（libartbase→libartbased）。
> 对"找不到文件"类卡点，先问：**这是逻辑 bug，还是快照缺口？**——
> 直读宿主同版本源（/apex）是零成本闭环；正式做法是重新 syncrom 扩 fixture。
