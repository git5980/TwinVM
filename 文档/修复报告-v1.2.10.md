# TwinVM v1.2.10 —— 排除法到最后一步：read 回读校验

> 输入：v1.2.9 真机日志 + crashes zip（280 个）+ logcat。

## 1. v1.2.9 判读（telemetry 立功）

```
[stat-telemetry] 真身 307B: 19748 (twinvm-selftest) t 23628 1818 0 0 -1 4194368 844 ...
[stat-telemetry] 解析 startstack=0x7ffd769d30     ← ★ 真值存在！
```

离线验证：`startstack=0x7ffd769d30 ∈ [stack] 7ffcf6d000-7ffd76c000`（落盘
maps 实证）——**stat 数据 ✓、maps 数据 ✓、包含关系 ✓**。

## 2. bionic 真实实现反汇编（ROM 的 libc.so，__find_main_stack_limits @0x9a618）

```
fopen("/proc/self/stat") → fgets(1024) → strrchr(')') 
→ sscanf(p+1, " %*c %*d…(25 个)…%lu", &startstack)   ← 格式对齐验证 ✓
fopen("/proc/self/maps") → fgets 循环
→ sscanf(line, "%lx-%lx", &lo, &hi)
→ lo<=startstack<=hi → 命中即成功
```

逻辑完全正确。**排除法走到尽头：唯一未验证的环节＝vm_mem_write 是否真的
把数据送进了 guest 内存**（stdio 链的 fstat st_blksize=4096 与 trace 的
read(fd, buf, 0x1000) 完全吻合，说明 stdio 在工作，但内容未验证）。

## 3. crashes zip / logcat 侧

- 280 个 crash log **全部是扫雷探针的 SIGSYS tombstone**（无害但量大，
  污染 DropBox——列入待办：加开关/默认关）；
- guest 自身无系统 tombstone（被 trace，crash_dump 无法 attach——符合预期）。

## 4. v1.2.10（一处）

read 分支加**回读校验**：写入后用 vm_mem_read 把前 48B 读回来比对，
`[read-verify] fd=… n=… ✓/✗ 回读=一致/不一致: <前 60 字符原文>`（限 8 次）。
若 ✗——数据没送达（vm_mem_write 的静默失败），下一刀修写入；
若 ✓——数据在 guest 内存里是对的，那 bionic 读的是别处（缓冲被踩？），
dump 出的 60 字符会直接告诉我们那是什么。
