# TwinVM v1.2.11 —— read-verify 的盲区：48B 比对漏掉了 startstack 和 [stack]

> 输入：v1.2.10 真机日志（6163 行）+ logcat + crashes zip（375 个，全扫雷探针）。

## 1. v1.2.10 判读

- **8 次 read-verify 全 ✓**——cmdline/cpu/stat/maps 前两块内容确认送达
  guest（`9206 (twinvm-selftest) t 1730…` 与 `02000000-12000000 rw-p…`）；
- guest 仍死于 `stack not found`（同址 abort）；
- crashes zip：375 个全是扫雷探针 SIGSYS（待办：加开关）。

## 2. 找到了 verify 的盲区（这轮的核心推理）

| 位置 | 特征 |
|---|---|
| stat 的 startstack 字段 | 文件第 ~170 字节——**比对只覆盖前 48B** |
| maps 的 [stack] 行 | 文件末尾（~第 50 块 read）——**8 次 verify 限额在 maps 第 2 块就用完** |

**若 vm_mem_write 存在部分写入**（如跨页失败、截断），前 48B 一致 + 后段
全是旧内存/垃圾 → bionic 解析 startstack 得到垃圾值 → maps 里永远找不到
→ "stack not found"——**与全部观测完美兼容**。

## 3. v1.2.11 升级（三件）

1. **全长比对**：malloc n 字节回读整块 memcmp；不一致时打**首个差异偏移 +
   期望/实得字节 + 后 40 字符**；
2. **[stat-mid]**：stat 内容的 [120,260) 字符区直接落日志（startstack 所在）；
3. **[maps-hit]**：读到含 `[stack]` 的块时打点（确认末尾块送达）。

## 4. 验证

`make -C core test` 5/5 PASS；checkrom PASS；APK 161 SIGN_OK；ROM fa88cc28 ✓。

## 5. 下一轮判据（真机跑 v1.2.11）

```
[read-verify] fd=10060 n=304 ✓ 全长一致            ← 或 ✗ 首个差异@+N
[stat-mid] fd=10060 n=304 中段[120,260)：…140730620179136…   ← startstack 原文
[maps-hit] fd=10060 本块含 [stack] 行（n=4096）      ← 末尾块确认
```
- ✗ → vm_mem_write 部分写入，定位修它（终极根因）；
- 全 ✓ → 数据完全在 guest 内存里，转攻 bionic 解析（在父进程用 ROM 的
  strrchr+sscanf 格式串模拟解析 304B 验证）。

## 6. 教训（第十四类：**验证工具的覆盖范围要覆盖"关键数据"**）

> 48B 抽头验证 = 只验了门牌号没验客厅。verify 的采样点必须落在**下游
> 真正消费的字段上**（本案＝startstack 与 [stack] 行）——先看消费方读哪，
> 再定验证点。
