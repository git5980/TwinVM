# TwinVM v1.2.111 —— installApk 三连坑修复 + ROM 自愈 + FGS 竞态防线

> 真机实锤链：16:01 crash（ForegroundServiceDidNotStartInTime）+
> live 日志（ROM 装载失败: -5）。两案同源：v1.2.109 installApk 把 ROM 写坏了。

## 案一：installApk 错位写入（ROM 损坏 → -5/-20）

v1.2.109 的 JNI 内嵌版三处错位（磁盘格式：表在 [64, 64+N×292)，非 data_off）：

| # | 坑 | 后果 |
|---|-----|------|
| 1 | inode 表写到 data_off 处（应在头后） | 表区损坏 → inode 越界 → **-5** |
| 2 | 只搬数据不改旧 inode 的 off（+292） | 旧文件 CRC 全错位 → **-20** |
| 3 | 追加点用旧逻辑尾（未计 292 移位） | APK 自踩旧数据区尾 → **-20** |
| 4 | 前缀扫描漏 / 分隔符 | 连装两次都叫 install-1（同名遮蔽） |

**修法（引擎层重写）**：新增 `vm_rom_install()`（core/src/vm_rom.c，
纯 C 无 JNI 依赖）+ JNI 只留薄包装。

**主机全链验证（131MB 真 ROM）**：
```
装 SampleApp → vm_rom_load 重载（全 inode CRC 验证）→ 135 ✓
再装一次 → install-2（递增）→ 136 ✓
python 交叉验证：全 inode CRC ALL OK、总长一致、内容逐字节相等
make test 回归 5/5
```

## 案二：ROM 秒败 → stopService 撞上未兑现的 startForegroundService（16:01 crash）

```
.754 点按钮 → dispatch：startForegroundService（异步）
.755 ROM 装载失败（-5，案一的损坏 ROM）→ 线程秒收尾
.759 cleanup：stopService —— 服务还没创建！
     → "Bringing down service while still waiting for start foreground"
.761 FATAL: ForegroundServiceDidNotStartInTimeException
```

**修法（双端）**：
- RunService：`sForeground`/`sStopRequested` 静态标志；startForeground 成功
  才置位；若此刻已请求停 → 自行 stopSelf（不给系统留账）
- cleanup：未前台时绝不 stopService（改设标志让服务自停）

## 案三：ROM 自愈（TA 手机上已损坏的 demo.rom）

- `romPath()` 轻体检：magic + 总长 + **末 inode 越界检查**（错位损坏必炸）
- App 启动后台线程：`Native.verifyRom()` 全量 CRC（131MB mmap）不过 →
  删掉重提 assets（恢复出厂但无需卸载重装）
