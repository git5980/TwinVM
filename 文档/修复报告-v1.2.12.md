# TwinVM v1.2.12 —— 终极反转：telemetry 自己差一个字段（startstack 其实一直是 0）

> 输入：v1.2.11 真机日志（6180 行）+ logcat + crashes zip（375 个，全探针）。

## 1. 三轮排除法全部通过的悖论

v1.2.9→v1.2.11 连续验证：stat 真身 307B 全长送达 ✓、maps 204KB 全长
送达 ✓、bionic `__find_main_stack_limits` 反汇编逻辑 ✓、"startstack=
0x7ffd769d30 ∈ [stack]" 包含关系 ✓——**四对全对，结果却错**。

## 2. 悖论破解（本机构造已知字段值自测）

用 stat 第 26/27/28 字段 = 111111111/222222222/333333333 构造文本：

| 格式 | 读出的字段 | 结果 |
|---|---|---|
| **v1.2.9 起我改的**（4×%*d + 7×%*u …） | 第 **27** 字段（endcode） | 222222222 ✗ |
| **v1.2.8 原版**（5×%*d + 8×%*u …） | 第 **28** 字段（startstack） | 333333333 ✓ |

**三重真相**：
1. `0x7ffd769d30` 是 **endcode**，不是 startstack！
2. **真正的 startstack 自始至终是 0**（fork-from-thread 的 kernel 边角，
   v1.2.8 原版 telemetry 早就打出来了）；
3. 我的 **stat-fix 修复代码（用 [stack] 起点替换第 28 字段）本来就是对的，
   但被差一的解析挡住从未触发**（ss=endcode≠0）。

v1.2.9 那次"修正格式"把对的改错了——三轮排除法全在错误的靶场上打。

## 3. v1.2.12（一行）

恢复 v1.2.8 原版字段对齐（5×%*d + 8×%*u …，读第 28 字段）。
stat-fix 从此触发：startstack=0 → 读真 maps 取 [stack] 行起点 →
文本替换第 28 字段 → bionic 找到栈。

## 4. 验证

`make -C core test` 5/5 PASS；checkrom PASS；APK 162 SIGN_OK；ROM fa88cc28 ✓。


## 6. 教训（第十五类，也是最后类：**改"观测格式"要和源格式 diff**）

> 修观测代码的解析格式时，必须用**已知字段值的构造数据**做回归——
> sscanf 的 %*d/%*u 数量差一个就是另一个字段。本案：v1.2.8 对的格式
> 被 v1.2.9"顺手简化"改错，之后三轮排除法（read-verify 全长比对、
> bionic 反汇编、包含关系验证）全部在错误前提下空转。
> 另：**诊断数据（telemetry）和修复触发（gate）不能共用一个可能有 bug
> 的解析结果**——gate 应直接用原始 token 定位（我的 stat-fix 恰好是
> token 定位实现的，否则连它都会错）。
