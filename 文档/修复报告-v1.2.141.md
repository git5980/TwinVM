## 静态审计结论（真 framework.dex 全链依赖扫描）

```
attach 链的真正要求（我此前的根本误判）：
  ActivityThread.currentActivityThread() 单例  ← 手工 new 的空壳内部全 null
  ContextImpl.createAppContext/createSystemContext 工厂
  LoadedApk.getPackageInfoNoCheck
  OnePlus IActivityExt 定制点（ActivityThread 初始化时装配）
  → 全都在 ActivityThread.systemMain() 启动流里建立！
```

**关键洞察**：`systemMain()` 是【系统进程入口】——设计上就不需要
system_server 协商（system_server 自己跑 systemui 用的）——
正是容器需要的形态。

## 修复（Bootstrap v15：正道启动流）

```java
ActivityThread.systemMain()          ← 静态方法，反射调用
  → 真 ActivityThread 单例（ext/Instrumentation/LoadedApk 全初始化）
  → getSystemContext() → 真 ContextImpl
attach 参数：
  Context       = systemContext（真件！MiniContext 仅保底）
  ActivityThread = systemMain 的单例（手工 new 时代结束）
```

systemMain 自身若炸：四帧诊断（M3-at-因）——大概率指向 binder
（ServiceManager）——那正是方案 B（vm_binder 层做最小桩）的靶。
