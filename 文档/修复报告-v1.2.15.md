# TwinVM v1.2.15 —— 通读结案：200KB 缓冲把 [stack] 行切掉了

> 输入：v1.2.14 真机日志（6203 行）+ logcat + crashes zip。按 TA 要求
> **先通读全部日志再综合修复**——三个探针第一次同轮出数据，互相印证出
> 完整因果链。

## 一、通读还原的完整因果链（证据编号都来自本轮日志）

1. **stat 完全正常**（1795-1816 行）：
   - telemetry 真值 startstack=0x7ffd769d30（第 28 格，格式考试过）；
   - `[stat-mid]` 打出原文中段：第 26/27/28 格 = 430188085248 / 430188090576 /
     **549713255728**——换算 0x6429354000 / 0x64293554d0 / **0x7ffd769d30** ✓；
   - read-verify 全长一致 ✓（数据完整送达 guest）。
2. **maps 出事了**（1818 行）：
   `[stack-snap] 读时 maps 无 [stack] 行（len=204799）`
   ——guest 打开 maps 那一刻，**204799 字节里没有 [stack] 行**。
3. **204799 = 200×1024 − 1**：我的 maps 缓冲区正好 200KB——**读满截断**。
   [stack] 行按地址序排在 maps **末尾**（栈地址最高）→ 恰好被切掉。
4. **为什么之前三轮都被骗**：abort 后 tracer 落盘的 maps 是**流式**写的
   （不受 200KB 限制）→ 有 [stack]。我们一直拿"事后照片"对账，
   而崩溃处理还会把栈撑满 8MB，进一步坐实了假象。
5. bionic：stat 解析出 startstack（真值）→ 逐行扫 maps 找包含区间 →
   **[stack] 行不存在** → "stack not found" → abort。（此前 v1.2.6~14 的
   修复杂因都不白费：数据链全通后，凶手只剩这一条。）

## 二、v1.2.15 综合修复（四件，一次配齐）

| # | 修复 | 说明 |
|---|---|---|
| 1 | **maps 缓冲 200KB → 1MB** | 根治截断（guest 实测 ~200KB，1MB 余量充足） |
| 2 | **读满检测** | len 达容量即打 `[maps] !! 读满`——永不无声截断 |
| 3 | **[stack-synth] 保底** | 读后若无 [stack] 行，用 stat 第 28 格 startstack 合成一页 append（token 定位，与 gate 解耦） | 
| 4 | 保留 [stack-snap]/[stack-clamp] | 观测与钳制逻辑不动（对"行存在但不含"的场景仍有效） |

## 五、教训（大白话版）

**装满了的桶要喊一声**：缓冲区读满 = 数据可能被切，必须打日志。
本案 204799 这个数字在日志里躺了三版（v1.2.7 起 maps 直读就是它），
没人注意它恰好等于 200KB−1——**异常值要和常量对账**。
