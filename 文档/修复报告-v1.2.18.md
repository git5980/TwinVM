# TwinVM v1.2.18 —— ★ 修 v1.2.17 体检失败的根因：tracer 死在 `waitpid`，`g_hang_probe` 永远轮不到

> 输入：v1.2.17 全量包 + 3 份真机日志（系统 logcat / 120 份 tombstone / live log 2017 行）
> 结论：**v1.2.17 的体检修复方向对，但触发机制不成立** —— guest 阻塞在 futex 时
> tracer 正卡在阻塞式 `waitpid` 里，循环不转，标志位没人看。

## 一、v1.2.17 日志的第 3 行就是答案

```
[TwinVM] !! 看门狗：90 秒无任何控制台输出（累计 90 秒）——判定卡死。
[TwinVM] ★ v1.2.17：请求示踪线程做等待现场体检（hang 与 crash 同等待遇）……
[TwinVM] !! 体检完毕（见上方 [hang] 行），强杀槽位。
[TwinVM] [hang] GETREGSET 失败 errno=3
```

**该出现的 `[hang] pc=… lr=…` 一行没有，取而代之的是 `errno=3`（ESRCH）。**
且这行是**主线程**打的（它是 `[hang]` 分支的 else）。

## 二、根因：两个错误叠在一起

### (1) 假设错误：`PTRACE_SYSCALL` 不会在长 syscall 阻塞期间返回停点

v1.2.17 源码注释写的是：

> "tracee 睡在 futex，本次停点是 PTRACE_SYSCALL 的即时返回"

**这是不成立的。** 真机黑匣子已经证明 guest 的现场是：

```
[blackbox] child syscall: 98 0xb40000722c04d984 0x80 0x3 …
[blackbox] child wchan: futex_wait_queue
[blackbox] child State: S (sleeping)
```

`futex_wait_queue` = **内核里真的睡下去了**。`PTRACE_SYSCALL` 只在 syscall 的
**entry / exit** 停，**阻塞期间没有任何停点**。所以：

```
guest:  futex_wait ──────────（一直睡，永不产生停点）
tracer: waitpid(-1, __WALL) ──（永远等不到，卡死）
        ↑ 循环不转 → 第 959 行的 if (g_hang_probe) 永远执行不到
main:   g_hang_probe=1 → 等 3 秒 → 超时 → 只留下自己那次失败的 GETREGSET
```

### (2) ptrace 语义：寄存器访问要求 tracee **处于停点**

`PTRACE_GETREGSET` 的 `ESRCH` 明确含义之一是 **"is not currently being traced by the caller, or is not stopped"**。
主线程不是 tracer（错）+ tracee 此刻在睡不在停（也错）→ 双重不满足 → `errno=3`。

**所以"换个线程下单"解决不了**：即使 tracer 去读，只要 tracee 还在 futex 里睡，
`GETREGSET` 一样会失败。**必须先把阻塞中的 tracee 强制拉进停点。**

## 三、v1.2.18 修复（两处，缺一不可）

### (a) tracer 循环改 **非阻塞轮询**

```c
// 旧：do { t = waitpid(-1, &st, __WALL); } while (t < 0 && errno == EINTR);
t = waitpid(-1, &st, __WALL | WNOHANG);
if (t == 0) {
    if (g_hang_probe && g_t_pid > 0) {
        g_hang_probe = 0;
        /* ★ 用 PTRACE_INTERRUPT 把睡在长 syscall 里的 tracee 强制拉停 */
        if (ptrace(PTRACE_INTERRUPT, g_t_pid, 0, 0) == 0) {
            pid_t t2; int st2;
            do { t2 = waitpid(g_t_pid, &st2, __WALL); } while (t2 < 0 && errno == EINTR);
            if (t2 == g_t_pid && WIFSTOPPED(st2)) { t = t2; st = st2; g_probe_stop = 1; }
        } else { /* 如实记录 PTRACE_INTERRUPT 失败 errno */ }
    }
    if (t == 0) { usleep(2000); continue; }
}
```

* **忙时无额外开销**：guest 一发 syscall，`waitpid` 立即返回停点，行为与原来完全一致；
* **阻塞时每 2ms 醒一次**，于是标志位终于有人看，体检也终于能在**正确线程 + tracee 已停**的条件下做。

### (b) 吞掉我们自己造的 SIGSTOP

`PTRACE_INTERRUPT`（配 `PTRACE_TRACEME` 而非 `PTRACE_SEIZE`）产生的是**组停**，
`WSTOPSIG` 为 `SIGSTOP`。若按原逻辑落到最后那个"真信号转发"分支，
**SIGSTOP 会被注入 guest 并永久停住它**（SIGSTOP 不可捕获）。所以新增：

```c
} else if (g_probe_stop && t == g_t_pid) {
    g_probe_stop = 0;
    ptrace(PTRACE_SYSCALL, t, 0, 0);   /* 吞掉，不注入 */
}
```

## 四、顺带确认：那 120 份 tombstone **不是 bug**

分类结果：

| 类别 | 数量 | 说明 |
|---|---|---|
| `signal 31 (SIGSYS) SYS_SECCOMP` | **116** | **策略扫雷的预期死亡** —— 子进程逐个试 syscall，被 App 的 zygote 策略拒 |
| `signal 11 (SIGSEGV) SEGV_ACCERR`，`pc=0`，sp 在 `[anon:stack_and_tls:main]` | 2 | **自检故意触发的崩溃**（验证崩溃处理链） |

扫雷共扫出 **107 个被拒的号**：
`18 39 40 42 51 58 89 99 100 104 105 106 112 116 142 143 144 145 146 149 151 152 159 161 162
170 171 180 181 … 234 235 … 273 … 288-313 437 439`

**→ 这些 tombstone 是自检的正常产物（每次运行都会生成上百个），排查时应忽略。**

## 五、最重要的独立发现：**guest 全程只有 1 个线程，`clone` 从未被调用**

从 guest 自己的 `/proc/self/stat` 真身里读出的第 20 字段：

```
7139 (twinvm-selftest) t 2147 1818 0 0 -1 4194368 846 0 0 0 0 38 0 0 20 0 1 ...
                                                                    ↑ field20 = num_threads = 1
```

配合另外三项证据：

| 证据 | 值 |
|---|---|
| `num_threads`（/proc/self/stat 第 20 字段） | **1** |
| `clone(220)` 出现次数 | **0** |
| `PTRACE_EVENT_CLONE` 出现次数 | **0** |

**结论（可确证）**：
> **ART 主线程阻塞在一个永远不会被唤醒的 private futex 上
> （`futex(uaddr, FUTEX_WAIT|FUTEX_PRIVATE, 3, NULL)`，无超时），
> 而唯一能唤醒它的那个线程从未被创建过。**

卡死前的动作序列（引擎日志，按时间）：

```
newfstatat(/system/framework/arm64/boot-okhttp.art)
newfstatat(/apex/apex-info-list.xml)
socket(AF_UNIX) ×4                      ← logd
openat(/proc/self/stat)  → 真身 303B
openat(/proc/self/maps)  → synth 329668B
socket(AF_UNIX) ×1
→ futex 无限等待
```

`openat(/proc/self/stat)` + `openat(/proc/self/maps)` 正是 ART 的
**`Thread::InitStackHwm()`**（读 maps 找 `[stack]`、读 stat 第 28 字段拿 `startstack`）。
**ART 就卡在它之后、创建第一个线程之前。**

拿到调用链即可本地符号化 → **"谁在等、等谁的锁"一击定案**
（候选：scudo 分配器锁 / `std::call_once` / ART `Mutex` 的 `kSharedMod` / uffd）。

**推测方向（供验证，不作结论）**：单线程 + 无超时 futex + 状态值 `3`，
最像 **一次性初始化（call_once/once_flag）或分配器锁被"留在占用态"**。
若调用链落在 libc/分配器，则要回查我们拦截过的 syscall 是否让某次
"加锁→异常路径"没走完。
