# TwinVM v1.2.19 —— ★ 看门狗判据修正（活动即前进）+ 补回 ptrace 迁移漏掉的 `msync`

> 输入：v1.2.18 真机日志（5076 行 / 473 KB）
> 结论：**用户判断正确** —— 那不是卡死，是**看门狗误报**；
> 而误报下面还埋着一个**真 bug**：ptrace 迁移漏掉 `msync(227)`，导致引擎里
> v0.7.41 的血泪修复成了**死代码**。

`PTRACE_INTERRUPT` + 非阻塞轮询让体检**真的跑起来**了（上一次是 `errno=3` 无输出）。

## 二、★ 用户指出：这不是卡死，是看门狗误报 —— **证据完全支持**

黑匣子逐次采样：

```
[blackbox] silent 71s; child syscall: 227 0x3c3de000 0x1000 0x0 …
[blackbox] child wchan: ptrace_stop    child State: t (tracing stop)
[blackbox] silent 73s; child syscall: 227 0x3c599000 …
[blackbox] silent 75s; child syscall: 227 0x3c75c000 …
[blackbox] silent 77s; child syscall: 227 0x3c91c000 …
[blackbox] silent 81s; child syscall: 227 0x3cca0000 …
[blackbox] silent 85s; child syscall: 227 0x3d01f000 …
[blackbox] silent 89s; child State: R (running)      ← ★ 它在运行！
```

经全量核对，`msync` 的 **30 个地址样本全程严格单调递增、零重复**：

```
0x39268000 0x39429000 0x395ee000 … 0x3c599000 0x3c75c000 0x3c91c000 0x3cca0000 0x3ce5f000 0x3d01f000
```

**→ 100% 是前向遍历（有前进），不是重试循环。看门狗判错了。**

### 误报机理

看门狗只认「**90 秒无控制台输出**」，但日志**只记录被拦截的 syscall** ——
`msync / mmap / mprotect / futex / brk` 这些**不在拦截清单**的 syscall
干活再久也**一行不输出** → 被当成卡死。

## 三、v1.2.19 修复之一：看门狗改由「guest 活动」驱动

```c
/* tracer：任何 ptrace 停点都算"guest 在前进" */
g_guest_ticks++;

/* 看门狗：活动即重置静默计时 */
if (g_guest_ticks != last_ticks) { last_ticks = g_guest_ticks; last_out = now; }

/* 判据：只有"既没输出、也没有任何 guest 活动"才是真卡死 */
if (now - last_out >= VM_HANG_SILENCE_S) { …判卡死… }
```

同时做了两件事：

1. **删掉「总时长」硬上限**（原 `now - t0 >= VM_HANG_TOTAL_S`）——
   它会在 guest 明明在动的时候到点就杀，是本类误报的第二个来源。
2. **加进度心跳**（每 10 秒一条，便于肉眼确认"它在动"）：

```
[TwinVM] [alive] 已运行 40s：guest 活动 183421 次停点（最近 nr=227 pc=0x72306fda4c）
         ——无控制台输出属正常（未拦截的 syscall 不打印）
```

心跳里的**停点计数**还能顺便区分两种"没输出"：
* 计数缓慢增长 → 慢但真实的工作（本次的 msync 遍历）；
* 计数每秒涨百万 → **同点紧循环**（另一种病，值得另查）。

## 四、★★ 修复之二：补回被 ptrace 迁移漏掉的 `msync(227)`

查引擎源码时发现，**v0.7.41 早就修过这个坑**：

```c
/* v0.7.41：msync（arm64 227 / x86_64 26）直接成功。
 * 真机实锤：ART 对映射（含 ROM 虚拟 fd 的映射）调 msync，拿到 ENOSYS 就**无限重试**
 * —— 8MB live 日志里 130k 行全是 ENOSYS nr=227（实际约 8.7M 次调用），
 * UI 表现就是永久"运行中"。VM 里没有需要真实回写的对象（ROM 只读、映射都是
 * MAP_PRIVATE），返回 0 语义上安全。 */
case VM_NR_msync:   return 0;
```

**但这段代码在 ptrace 后端下是死代码**：

| 后端 | 覆盖机制 | msync 是否被拦 |
|---|---|---|
| SIGSYS/TRAP（旧） | BPF **放行清单**制 —— 不在清单即 TRAP 进 handler | ✅ 会进引擎 |
| **ptrace（v1.2.x 现用）** | **显式白名单** `tvm_virt_nr()` | ❌ **227 没写进去** |

于是 `msync` 直达真实内核 → 对**未映射区间**返回 `ENOMEM` →
ART 逐页往前扫（每页一次 **`MS_SYNC` 真回写**，故约 1 MB/s）→
**慢到把看门狗也拖进误报**。

**两件事其实是同一个根**：msync 不该走内核。

### 修复

```c
case 227:            /* v1.2.19：补回 ptrace 白名单，让 v0.7.41 的 return 0 生效 */
    return 1;
```

修好后的效果：**msync 立刻返回 0**（无磁盘回写、无长遍历），
ART 那趟"逐页 msync"会在极短时间内走完（或根本不再需要走）。

**顺带核实了地址语义**：遍历区间 `0x39268000-0x3d01f000` 落在
`0x3904e000-0x40800000` 这个**空洞**里（maps 转储完整，结尾是标准 `[stack]`），
即**确实在对未映射内存反复 msync** —— 与"该由 VM 直接回 0"的结论一致。

## 六、下一轮判据

```
[TwinVM] [alive] 已运行 10s：guest 活动 N 次停点（最近 nr=…）
[TwinVM] ▶ [4/6] 装载 dalvikvm …
   ← msync 不再拖时间，应能很快越过此处
```

若仍见 `nr=227` 高频出现：
* 计数**缓慢**增长 → 仍在走某段合法但慢的逻辑（看门狗不会杀，可继续观察）；
* 计数**暴涨** → 同点循环，届时按 `pc` 反查是哪段代码在打转。

## 七、教训（第 5 类：判据错，不是程序错）

> v1.2.17/1.2.18 连着两轮都在"修体检"，
> 而真正的毛病是**判据本身把"忙"当成了"死"**：
> 「90 秒无输出」在**只记被拦 syscall** 的日志策略下，
> 等价于「90 秒没碰到需要虚拟化的调用」——这与"卡死"根本不是一回事。
>
> **通用规则**：超时判据要盯**被监控对象的真实进展信号**（这里是 ptrace 停点），
> 而不是**某个副产物**（控制台输出）。副产物会因为日志策略变化而失真。
