# TwinVM v1.2.2 —— /apex 直读触发不了：ld.config 搜索路径不问 /apex → 同名回退

> 输入：v1.2.1 真机日志（5724 行）。/apex 直读 0 次命中——机制对了，
> 但 linker 根本不会请求 /apex 路径。

## 1. v1.2.1 判读

- mmap-fill 稳定复现（227 次灌入）；
- libartbased.so 仍 ENOENT：linker 按 **ROM 里项目合成的 ld.config.txt** 搜索
  ——`namespace.system.search.paths = /system/lib64:/odm/lib64:/vendor/lib64`，
  **永远不会请求 /apex/...**，v1.2.1 的 /apex 前缀白名单自然 0 次命中；
- 设备真实语义：Android 10+ 的 `/system/lib64` art 库本就是
  `/apex/com.android.art/lib64` 的**硬链接**——同名文件两处可见。

## 2. v1.2.2 修复：/system/lib64 miss → /apex 同名回退

```
openat("/system/lib64/libartbased.so")
  → ROM miss
  → 自动映射 /apex/com.android.art/lib64/libartbased.so
  → 宿主真 open（同机同版本=同快照）→ 读全量进动态槽（rom_idx=-3）
  → 日志："openat(...) -> fd=100xx [/apex 直读 NB ← /apex/.../libartbased.so]"
```

- openat 与 newfstatat 两处一致回退；
- 非 /system/lib64 与 /apex 前缀的路径仍严格 ENOENT（隔离不放松）；
- ROM 的 ld.config.txt 不动（改它要重打 ROM，违反 ROM 冻结）。

## 3. 验证

- `make -C core test` 5/5 PASS；`checkrom --strict` PASS；ROM md5 未变（fa88cc28）；
- APK SIGN_OK / versionCode=152；包内 ROM md5 = fa88cc28 ✓。

## 5. 本轮教训（第十类：**补通道前先看调用方会走哪条路**）

> v1.2.1 白名单挂在 /apex 前缀上，但没人会请求 /apex——**加通道之前先确认
> 请求方的搜索路径**（这里是 ROM 的 ld.config.txt）。修在"数据侧"还是
> "请求侧"要看谁更容易对齐真实语义：本例真机语义就是两路径同名，
> 所以在 VFS 层做映射最保真。
