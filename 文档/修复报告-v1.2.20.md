# TwinVM v1.2.20 —— ★★★ 体检换通道：`PTRACE_INTERRUPT` 注定失败（EIO），改用 `/proc` + `process_vm_readv`

> 输入：v1.2.19 真机日志（2048 行 / 162 KB）
> 一句话：**心跳机制成功区分了"忙"与"死"**（这一轮是**真卡死**，看门狗判对了）；
> 而体检仍拿不到现场的原因找到了 —— `PTRACE_INTERRUPT` **只支持 PTRACE_SEIZE**。

## 一、v1.2.19 的两个成果

### (1) 心跳机制的价值被证实（区分"忙"与"死"）

```
[alive] 已运行 40s：guest 活动 7013 次停点（最近 nr=98 pc=0x723bb16da4）
[alive] 已运行 50s：guest 活动 7013 次   ← ★ 计数【冻结】
[alive] 已运行 60s：guest 活动 7013 次
…
[alive] 已运行 100s：guest 活动 7013 次
[TwinVM] !! 看门狗：90 秒无任何控制台输出（累计 106 秒）——判定卡死。
```

**停点计数冻结在 7013** → **这次是真卡死**，看门狗**判对了**（对比 v1.2.18：计数在涨 → 误报）。
一条心跳就把两轮的性质分开了 —— 这就是它的价值。

### (2) msync 回归修复生效

本轮 `nr=227` 拦截 0 次、**那个 1 MB/s 的 msync 遍历消失了**
（上一轮是它把 guest 拖成"看着像卡死"）。日志从 473 KB 降到 162 KB。

## 二、新问题：体检仍无输出，因为 `PTRACE_INTERRUPT` 用不了

```
[TwinVM] [hang] PTRACE_INTERRUPT 失败 errno=5
```

`errno=5` 是 **`EIO`**（不是 EPERM）。`man 2 ptrace` 写得很明确：

> **EIO**：… `PTRACE_INTERRUPT` **只支持通过 `PTRACE_SEIZE` 附属的 tracee**。

而我们用的是 **`PTRACE_TRACEME`** → **这个请求注定失败**，与"guest 是否睡着"无关。
（v1.2.18 我按"能强制拉停"来设计，方向就错了。）

同时黑匣子确认了卡死性质：

```
[blackbox] child syscall: 98 0xb40000723b04d984 0x80 0x3 …   ← futex
[blackbox] child wchan: futex_wait_queue
[blackbox] child State: S (sleeping)
```

## 三、v1.2.20 换通道：体检**根本不需要 ptrace**

关键认识：**取等待现场这件事，从来不需要 ptrace。**

| 需要的信息 | 可取通道 | 是否要求对方停止 |
|---|---|---|
| 当前 syscall 号 / 参数 / **sp** / **pc** | **`/proc/<pid>/syscall`**（运行中亦可读） | ❌ 不需要 |
| 内存布局（模块基址） | `/proc/<pid>/maps` | ❌ 不需要 |
| 栈内容 | **`process_vm_readv`**（跨进程普通读） | ❌ 不需要 |

于是新增 **`tvm_hang_dump_procfs(pid)`**：完全走上面三条，
**不碰 ptrace、不需要停点、也不需要"必须是 tracer 线程"**。

```c
/* 1) /proc/<pid>/syscall → nr a0..a5 sp pc */
sscanf(ln, "%ld %llx %llx %llx %llx %llx %llx %llx %llx",
       &hnr, &a0,&a1,&a2,&a3,&a4,&a5, &sp, &pc);
live_write("[hang] nr=… sp=0x… pc=0x… a0=… a1=… a2=… a3=…");

/* 2) /proc/<pid>/maps → 可执行段表 */

/* 3) process_vm_readv(sp, 8KB) → 找出指向可执行段的返回地址 */
live_write("[hang] sp+0x… 0x… /apex/…/libart.so +0x…");     ← ★ 等待者调用链

/* 4) maps 全量落盘，供离线符号化 */
```

调用点在**看门狗判卡死处（主线程）**，在置 `g_hang_probe` 之前执行：

```c
tvm_hang_dump_procfs(pid);      /* ★ 主线程直接可用 */
g_hang_probe = 1;               /* tracer 侧只作补充 */
```

并**移除**了 tracer 里那段注定失败的 `PTRACE_INTERRUPT`（现在只清标志、继续轮询）。

### 副产品：纠缠四轮的"线程问题"从设计里消失

| 版本 | 做法 | 结果 |
|---|---|---|
| v1.2.16 | 主线程直接 GETREGSET | `ESRCH`（不是 tracer） |
| v1.2.17 | 改由 tracer 代办 | tracer 卡在 `waitpid`，标志没人看 |
| v1.2.18 | tracer 非阻塞轮询 + `PTRACE_INTERRUPT` | `EIO`（TRACEME 不支持） |
| **v1.2.20** | **换通道（procfs + process_vm_readv）** | **不要求停点、不要求 tracer 身份 —— 问题消失** |

> 教训：**当"必须满足某个前提"反复做不到时，先问这个前提是不是必需的。**
> 四轮都在解决"怎么在正确线程里拿到停点"，而正确解法是**换一条不需要停点的取数通道**。

## 五、下一轮判据（终于该出调用链了）

```
[TwinVM] [hang] nr=98 sp=0x723be67010 pc=0x723bb16da4 a0=0xb40000723b04d984 a1=0x80 a2=0x3 a3=0x0
[TwinVM] [hang] sp+0x… 0x… /apex/com.android.art/lib64/libart.so +0x…    ← ★ 等待者调用链
[TwinVM] [hang-maps] guest 布局：…
```

拿到调用链即可本地符号化 → **"谁在等、等谁的锁"一击定案**
（候选：scudo 分配器锁 / `std::call_once` / ART `Mutex` 的 `kSharedMod` / uffd）。

**已知现场特征（供交叉验证）**：
* `futex(uaddr=0xb40000723b04d984, FUTEX_WAIT|FUTEX_PRIVATE, val=3, timeout=NULL)`；
* `timeout=NULL` → **永久等待**，必须有人唤醒；
* guest 进程 **`num_threads=1`**（v1.2.18 从 `/proc/self/stat` 第 20 字段读出）、
  `clone` 与 `PTRACE_EVENT_CLONE` **均为 0 次** → **能唤醒它的线程从未被创建**；
* 卡点在 ART `Thread::InitStackHwm()` 之后、创建第一个线程之前。
