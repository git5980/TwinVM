## 二、★ 循环的真身：ART 的低 4GB 内存分配器在试候选地址

### (1) 从 `[caller]` 拿到调用者

```
[caller] nr=227 #1 lr=0x723adc1540 a0=0xd6a000    a1=0x1000
[caller] nr=227 #2 lr=0x723adc1540 a0=0xd6b000    a1=0x1000
[caller] nr=227 #3 lr=0x723adc1540 a0=0xd6c000    a1=0x1000
…
```
**同一个调用点，地址逐页 +0x1000 顺序前扫。**

### (2) 用"段大小 + 段权限布局"反查模块，再用 ROM 验证

`lr` 落在 `0x723adbf000-0x723adec000`（**180KB、rwxp 匿名**）。而 libartbase 的
`LOAD R E` 段 = `FileSiz 0x2cbf0 ≈ 180KB` —— **完全吻合**。
换算 `lr` → vaddr：`0x25000 + (0x723adc1540 - 0x723adbf000) = 0x27540`。

**反汇编该处，函数名直接给出答案**：

```
_ZN3art6MemMap29MapInternalArtLow4GBAllocatorEmiiil
= art::MemMap::MapInternalArtLow4GBAllocator(size_t, int, int, int, off_t)
```

### (3) 用 ROM 里的字符串交叉印证

从 libartbase 里读出的独有文案：

```
art/libartbase/base/mem_map.cc          ← 源文件（日志里带行号 1120）
) cannot fit in low_4gb                 ← 分配失败告警
Using memfd for future sealing
memfd_create failed:
Check failed: ::art::IsParamAligned(ptr, GetPageSize())
```

→ 该路径用 **memfd** 承载镜像，并在 **低 4GB** 内找落点；找不到就打印
"cannot fit in low_4gb"。

### (4) 黑匣子的三件套，构成完整循环

```
215 munmap(0x7225fed000, 128MB)     ← 永远解映射【同一个】地址
222 mmap(hint=0x100f000, 128MB)     ← 低位候选【递增】：0x100f000→0x1142000→0x14d8000→…
227 msync(候选区内页, 4096, 0)       ← 逐页 touch（扫描/校验）
```

**三个 syscall 全部来自同一模块**（pc 相间 0xC40，都在上面那段里）。

### (5) 核心疑点：**低位候选地址从未真正落地**

maps 转储显示 **`0x02000000`（32MB）以下没有任何映射**。
即：ART 请求低地址、**内核没给低地址** → 分配器判定"这儿不行" → 换下一个候选 → **无穷**。

**这就是"数字无限增加"的本质**：不是死锁，是**一个永远找不到落点的搜索循环**。

## 三、v1.2.22 补齐的四组诊断（下一轮一次定位）

| 新增 | 内容 | 为什么需要 |
|---|---|---|
| **`[mmap] hint=… → ret=…`** | 匿名 mmap 的**请求地址 vs 内核实际返回**，不同则标 `← 未按 hint` | **直接验证上面的核心疑点**：内核到底有没有给低地址 |
| **`[rom-map]`** | 每次 ROM 段映射：`路径 addr len prot off mprotect=结果` | 一张表说清"哪个库在哪、权限有没有收紧成功"（本次卡了一整轮就是因为缺它） |
| **`[vmmap]`** | 引擎**段登记表**（带模块路径）随体检一起落盘 | 比 `/proc/maps`（host+guest 混在一起、几千条）精确得多——**任何 pc/lr 归哪个库一目了然** |
| **`vm_diag()` 直写通道** | 引擎诊断绕开 console 直写实时日志 | tracer 线程里 `vm_log` 会丢（v1.1.0 已实锤）；这四组诊断必须走对通道 |

> 注意最后一条的必要性：`[mmap]`/`[rom-map]` 都从 **tracer 线程**发出，
> 若用 `vm_log` 就会"写了但看不到"——这正是前面几轮反复踩的坑。

## 五、下一轮判据

装 v1.2.22 跑一次，看两处：

```
[mmap] hint=0x100f000 len=0x8000000 prot=0x3 flags=0x22 -> ret=0x??????  ← ★ 关键
[rom-map] /system/lib64/libartbase.so addr=0x… prot=0x5 mprotect=0        ← 权限是否收紧成功
```

**若 `ret` 明显大于 `hint`（且高于 4GB）** → 证实"内核不给低位"，
则根因是**低位地址空间在 slot 进程里被占**（host 与 guest 共享地址空间，
host App 的映射有 3000+ 条）。下一步应对：
* 让引擎**在低 4GB 预留一块专用区**并让 ART 优先落在里面；
* 或在 host 侧**先把低 4GB 清空/避开**（例如启动早期预留一个大的低地址 VA 坑）。

**若 `ret == hint`（内核照给了）** → 说明落点没问题，
问题在**分配器的验收条件**（很可能与"权限被我们映射成 rwx / mprotect 结果"有关），
届时看 `[rom-map]` 的 `prot` 与 `mprotect=` 一栏即可定案。

## 六、本轮方法论要点

1. **"段大小 + 段权限布局"可以在没有符号表的情况下反查模块** ——
   180KB 的 `rwxp` 段 → 比对 ROM 各库的 `LOAD R E` 大小 → 唯一命中 libartbase，
   再用 ROM 内字符串（`cannot fit in low_4gb`）交叉印证，两次独立证据锁定；
2. **反汇编能直接读到 AOSP 的源文件名与行号**（`mem_map.cc:1120`）——
   这比猜实现快得多；
3. **诊断必须先确认通道**：`[mmap]` 走 `vm_log` 会静默丢失，
   所以本轮专门加了 `vm_diag()` 直写通道（第 4 次踩同一个坑，这次做成机制）。
