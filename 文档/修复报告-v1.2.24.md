# TwinVM v1.2.24 —— ★★★ 一次"差点发出去"的灾难级自伤：删 `case` 带走了共享的 `return 1;`

> 输入：v1.2.22 真机日志（498 KB）
> 结论：本轮**最重要的产出不是新功能，而是拦下了一个会让拦截整体失效的改动**。

## 一、事故经过（真实发生，未发布）

v1.2.23 我按架构原则**撤销 `msync(227)` 的拦截**，做法是删掉：

```c
        case 227:
            return 1;        ← ★ 这个 return 是和上面那串 case **共享**的
```

但源码实际形状是：

```c
        case 96: case 99: case 163: case 167: case 43: case 44: case 221:
        /* …注释… */
        case 227:
            return 1;        ← 上面 27 个 case 全都靠它
```

于是**删掉 `case 227:` 连同 `return 1;` 一起没了** → `tvm_virt_nr()` 退化成
`return 0`（全部落 default）→ **syscall 拦截被整体关闭**。

### 连锁现象（这才是发现它的线索）

```
构建产物 libtwinvm.so 里：
  [caller]   串消失
  SETREGSET  串消失
  已拦截      串消失
  回填        串仍在（退出路径，另一处）
nm 符号表：
  tvm_intercept_now  ← ★ 不在！被判定"从未被调用"而删除
```

**推理链**：`tvm_virt_nr()` 恒为 0 → `tvm_intercept_now()` 的调用点不可达 →
函数被删除 → 它内部的串全部消失。**这也解释了为什么 `noinline`、`#pragma clang optimize off`
都压不住** —— 根本不是优化器删了函数体，而是**它判定该函数没人调用**。

**幸好：v1.2.23 从未导出到设备（设备上仍是 v1.2.22）。** 若发了，症状会是
"一切看起来都在跑，但拦截其实完全没生效" —— 极难排查。

## 二、本轮真正的技术结论（三条）

### (1) v1.2.22 新加的 `[mmap]`/`[rom-map]` 诊断一条都没出 —— 原因明确

```
[mmap] hint=   0 条
[rom-map]      0 条
[vmmap] 引擎段登记表： 0-0 r--p … [empty]     ← ★ 登记表是空的
```

**`mmap(222)` 不在拦截清单里** → 引擎的 `case VM_NR_mmap` 从不执行 →
放在里面的日志自然不会打。而且**这本来就是对的**：

### (2) ★ 架构级认识：ptrace 后端下，**操作 tracee 内存的 syscall 不能被拦截**

ptrace 后端里引擎跑在**父进程**、guest 在**子进程**；
`mmap/munmap/mprotect/mremap/msync/madvise/brk` 这类要**按地址操作子进程内存**的调用，
引擎根本替它做不了（父进程的 `memcpy`/`mmap` 只作用于自己）。

* 所以 **v1.2.19 我把 `msync(227)` 加进拦截清单是错的**：`case VM_NR_msync: return 0;`
  变成一句**谎言**，而 ART 的 `MapInternalArtLow4GBAllocator` 恰恰**用 msync 的成败
  判断候选区间可用性** → 永远"可用"→ 永远换下一个候选 → 那个无限循环；
* **v1.2.24 已撤销**：让 msync 走子进程原生执行，由内核给真实答案（v0.7.41 的
  "8.7M 次重试"是 SIGSYS 后端回 ENOSYS 造成的，与原生行为无关）；
* 同批确认：`mmap/munmap/mprotect/brk` 都在"明确不拦截"清单里 ✓ 架构自洽。
* 另外发现项目**已有** ptrace 兼容的 ROM 填页机制 `[mmap-fill]`
  （把虚拟 fd 的 mmap 改写成匿名原生 mmap，再在 exit 停点灌 ROM 内容）——
  这才是 ptrace 下正确的做法。

### (3) 本轮卡点是 `futex`，而 `[hang]` 栈扫描**静默失败**

```
[alive] 40s…100s：guest 活动 7013 次停点（nr=98 futex）   ← 计数冻结 = 真卡死
[hang] nr=98 sp=0x723c059010 pc=0x723bb7fda4 …
[hang] （栈上无可执行段地址）                              ← 只说了"没有"，没说"为什么"
```

看门狗判对了（判据已按"活动即前进"改造 ✓），但栈扫描空手而归且**不解释原因**。
v1.2.24 补上自检：

```
[hang] sp 所在段=<模块名或[anon]或★不在任何映射>  pc 所在段=…
[hang] 栈读取失败：tvm_read_pv=<rc> errno=<e> nseg=<n>（扫不了）
```

## 三、v1.2.24 的改动清单

| 改动 | 说明 |
|---|---|
| **恢复 `return 1;`** | 并把教训直接写进源码注释（"删 case 时先确认有无共享语句"） |
| **撤销 `msync(227)` 拦截** | 见 §2(2)：架构性修正，让内核回答真假 |
| **拦截主体抽成 `tvm_intercept_now()`（noinline）** | 便于"是否存在"用 `nm` 一眼核验（这次正是靠它定位） |
| **新增 `[ptrace] 已拦截 N 次`** 计数 | 每 500 次一条：**能自证拦截真的在跑**（不再依赖间接推断） |
| **栈扫描自检** | 报告 sp/pc 落在哪个段、`tvm_read_pv` 的返回与 errno |
| `[caller]` 改为直接调 `ptrace_log` | 不再经局部缓冲，减少被优化掉的可能 |

> **v1.2.23 的 `-#pragma clang optimize off` 保留**（无害的保险），
> 但真正的解释是 §1 的"共享语句"。

## 五、流程改进（本轮最大的收获）

这次能拦住灾难，靠的是**"改完必须证明代码真的进了产物"**：

1. **每个新诊断串，构建后在 `.so` 里 `count()` 一遍** —— 为 0 就说明没编进去；
2. **关键函数用 `nm` 确认符号存在**（`tvm_intercept_now` 的消失就是第一现场）；
3. **APK 内 `.so` 与源码产物比 md5** —— 防"包了旧 .so"（此前已踩过一次）。

**三条建议固化为每次发版前的自检**（已在本轮执行）。

## 六、下一轮判据

装 v1.2.24 跑一次，应能看到：

```
[ptrace] 已拦截 500 次（x8 改写 + 交引擎）      ← ★ 拦截确实在跑
[TwinVM] [caller] nr=… lr=0x… pc=0x…            ← 调用者留痕
[hang] sp 所在段=<模块>  pc 所在段=<模块>        ← 栈扫描的自检
[hang] sp+0x… 0x… /apex/…/libart.so +0x…        ← ★ 等待者调用链
```

**拿到调用链即可符号化 futex 等待者**，与已知现场交叉验证：
`futex(uaddr=0xb40000723b04d984, FUTEX_WAIT|PRIVATE, val=3, timeout=NULL)`、
`num_threads=1`、`clone` 0 次 → **能唤醒它的线程从未被创建**。
