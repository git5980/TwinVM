## 二、`sp 所在段=★不在任何映射` —— 是我的**诊断**错了，不是数据错

核对 maps：

```
723bb28000-723bc68000 rw-p            ← sp=0x723bc66f30 落在这里（栈）
```

**sp 完全合法。** 原因是我的段表**只收了可执行段**（`pm[2]=='x'`），
而栈是 `rw-p`，自然"找不到"；同理"栈上无可执行段地址"也是被这个过滤器误导。

## 三、★ 更本质的问题：`/proc/<pid>/syscall` **给不了帧指针**

`/proc/<pid>/syscall` 只提供 `nr a0..a5 sp pc` ——
**没有 `x29`（帧指针）、没有 `x30`（LR）**。
而 **AArch64 的调用链必须靠 `x29` 链回溯**（`[x29]` = 上一帧 fp，
`[x29+8]` = 返回地址）。只拿 `sp` 去扫栈，经常一个返回地址都扫不到 ——
这正是 v1.2.24 那句"（栈上无可执行段地址）"的根因。

## 四、v1.2.25：**在真实 ptrace 停点上抓帧**

新增 `tvm_dump_frames(pid, nr, regs)`：

```c
/* 段表用**全量**（含非可执行段，用于判定地址归属；可执行段额外标记） */
parse /proc/<pid>/maps  → sg[]（lo/hi/base/name/named/exec）

/* ① 停点全貌：这几项足以定出等待者 */
[frames] nr=227 lr=0x… sp=0x… x29=0x…

/* ② 沿 x29 帧链回溯最多 16 帧，每帧映射到"模块 + 偏移" */
fp = regs[29];
while (fp && i < 16) {
    read [fp]    → 上一帧 fp
    read [fp+8]  → 返回地址 ra
    [frames]   #00 ra=0x… /apex/com.android.art/lib64/libart.so +0x…
    fp = 上一帧;
}
```

**触发方式（按需、只抓一次）**：
* 看门狗判卡死时置 `g_want_stack`；
* `[loop]` 检测器每 60 秒置一次；
* 示踪器在**下一个 syscall 停点**看到标志 → 取全套寄存器 → 抓帧 → 清标志。

**为什么必须在 ptrace 停点上做**：此时 tracee 处于停点，
寄存器**权威且稳定**（`/proc` 读运行中的任务是有竞态的，且缺 x29/x30）。

## 六、下一轮判据（这一轮该出调用链了）

装 v1.2.25 跑一次，卡死/循环时应出现：

```
[TwinVM] [frames] nr=227 lr=0x… sp=0x… x29=0x… 段表=3172
[TwinVM] [frames]   #00 ra=0x… /apex/com.android.art/lib64/libart.so +0x…
[TwinVM] [frames]   #01 ra=0x… …                        ← ★ 等待/循环者调用链
```

**拿到 `#00`~`#05` 即可离线符号化** —— 立刻能回答"是谁在以 445/s 的速度
对内存逐页 msync"，以及它与已知现场（`MapInternalArtLow4GBAllocator`、
`num_threads=1`、`clone` 0 次）的关系。

## 七、两条工程结论（累积）

| 教训 | 本轮体现 |
|---|---|
| **诊断工具本身也会错** | "sp 不在任何映射"是**我的过滤器**造成的假象，数据是好的；报告必须写清"判定条件" |
| **要取什么就先确认数据源有没有** | 要 `x29` 就得走 ptrace 停点；`/proc/syscall` 天然没有 → 换通道而不是硬猜 |
