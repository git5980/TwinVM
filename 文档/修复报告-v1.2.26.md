> 输入：v1.2.25 真机日志（2.84 MB）

## 一、抓帧成功 —— 但第一版全显示"★模块未知"

v1.2.25 的抓帧机制本身工作正常：

```
[frames] nr=227 lr=0x723aef6540 sp=0x723c058ed0 x29=0x723c058ef0 段表=512
[frames]   #00 ra=0x6876f23aef60ec ★模块未知 +0x0
[frames]   #01 ra=0x7c5d723aefdf78 ★模块未知 +0x0
```

**`ra` 高位全是乱码** —— 本机开着 **PAC + TBI**（tombstone 实锤：
`pac_enabled_keys: 000000000000000f`、`tagged_addr_ctrl: PR_TAGGED_ADDR_ENABLE`），
**栈上的返回地址高位带签名/标签**，真地址只在低位。

## 三、★ 用 ROM 段大小反查匿名段（这招再次奏效）

这些段都是匿名的（引擎把 ROM 段映射成匿名页），但**段大小**能和 ROM 各库的
**可执行 PT_LOAD 大小**一一对上：

| 观测段大小 | ROM 库的可执行 LOAD 段 | 命中 |
|---|---|---|
| **9800 KB** | `libart.so` = 9799 KB | ✅ 唯一 |
| **676 KB** | `libc.so` = 673 KB | ✅ 唯一 |
| **180 KB** | `libartbase.so` = 178 KB / libcutils 180 / libpcre2 184 | 需再判：**ROM 里只有 `libart.so` 与 `libartbase.so` 导入 `msync`** → **libartbase** |

### 结论：调用链完整成立

```
msync(227) 逐页扫描
  ← #00/#01  libartbase.so   (178KB 文本段)
  ← #02..#07 libart.so       (9799KB 文本段)     ← 循环主体
  ← #08/#09/#11  4KB 单页 r-xp（蹦床/桩）
  ← #10      libc.so         (673KB 文本段)
```

* **`msync` 的调用者（`lr=0x723aef6540`）与 #00/#01 同段** → 就是 **libartbase**，
  与上一轮独立得出的 `art::MemMap::MapInternalArtLow4GBAllocator`(libartbase) **交叉印证** ✓
* **#02..#07 全在 libart** → 是 **libart 在驱动**这次低 4GB 分配（`gc::Heap` 初始化路径）；
* 4KB 单页可执行段出现在链中间，是 ART 的入口桩/蹦床。

## 四、v1.2.26 的改动（把"离线分析"变成"日志自带"）

| 改动 | 说明 |
|---|---|
| **PAC/TBI 去掩码（39..56 位搜索）** | 帧链里直接打印 `去PAC39位`，且**取第一个落在已映射段内的候选**，不再显示"★模块未知" |
