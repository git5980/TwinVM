# TwinVM v1.2.27 —— ★★★ "栈上无可执行段地址"连续五轮不退的**真因：PAC 签名**

> 输入：v1.2.26 真机日志（499 KB）

## 一、本轮现象：`[frames]` 一条都没有

```
已拦截 1 条（500 次）   [caller] 82 条   [loop] 0 条   sp 所在段 1 条
```

本轮是 **futex 阻塞型卡死**，不是循环型：

```
[alive] 100s：guest 活动 7013 次停点（nr=98 futex）   ← 计数冻结在 7013
[hang] nr=98 sp=0x723c157010 pc=0x723bb81da4 a0=0xb40000723b04d984 a1=0x80 a2=0x3
看门狗：90 秒无输出（累计 105 秒）→ 判卡死 → 强杀
```

**为什么 `[frames]` 抓不到**：抓帧机制是"在**下一个 syscall 停点**执行"。
而 guest **阻塞在内核里（futex wait）→ 永远没有下一个停点** → 机制永不触发。
**这个设计缺陷正好落在最需要现场的场景上。**

## 二、★ 两个诊断缺陷（都是我自己的）

### (1) `sp 所在段=★不在任何映射` 是**过滤器造成的假象**

实测 `sp=0x723c157010` 明明在：

```
723c058000-723c158000 rw-p     ← 栈区，sp 落在里面
```

原因：体检用的段表带 `pm[2]=='x'` 过滤（**只收可执行段**），而栈是 `rw-p`。
另外还有 **两个隐患**：容量 `seg[256]` 而真机 maps 有 **3176~3195** 段；
而且这张表和另一个 `hsegs[256]` 是**两张不同的表**，v1.2.26 我改错了地方。

### (2) **★★★ `（栈上无可执行段地址）` 连续五轮不退的真因 = PAC 签名**

栈扫描的逻辑是"把栈上的 8 字节值拿去和**可执行段区间**比较"。
但本机开着 PAC（tombstone：`pac_enabled_keys=0x000000000000000f`），
**栈上的返回地址高位带签名** —— v1.2.25 抓帧实测形如：

```
ra=0x6876f23aef60ec    ← 真地址是 0x723aef60ec，高位全是签名
```

**直接拿原值比较永远比不中** → 每轮都报"无可执行段地址"。
这和 v1.2.26 帧链"★模块未知"是**同一个根因**，我上一轮只修了帧链、**漏了栈扫描**。

## 三、v1.2.27 的修复

| 修复 | 细节 |
|---|---|
| **段表全量收录** | 去掉 `pm[2]=='x'`；改由 `seg[].exec` 标记，定位 sp/pc 用全量 |
| **容量 256 → 8192** | 真机 3176~3195 段，256 会截断 |
| **栈扫描 PAC 去掩码** | 与帧链同一套办法：对每个栈值依次试 **39..56 位掩码**，取第一个命中**可执行段**的候选，并在日志里标出 `(去PAC39位)` |

修复后输出形如：

```
[hang] sp 所在段=[anon]  pc 所在段=[anon]          ← 不再假报"不在任何映射"
[hang] sp+0x1a8 0x723bb24b08 (去PAC39位) [anon] +0x…    ← ★ 等待者调用链
```

## 四、本轮现场要素（已锁定，待调用链印证）

| 项 | 值 | 含义 |
|---|---|---|
| 卡点 | `nr=98 futex`，停点冻结 7013 | 单线程阻塞，**没有新停点** |
| futex 参数 | `uaddr=0x723b04d984`、`op=0x80`、`val=3`、`timeout=NULL` | `FUTEX_WAIT\|PRIVATE`，等该地址的值从 3 变化 |
| `pc` | `0x723bb81da4`，所在段 **676KB** = `libc.so`(673KB) | futex 包装在 libc ✓ |
| 进程事实 | `num_threads=1`、`clone` 0 次 | **能唤醒它的线程从未被创建** |


拿到 `sp+0x…` 若干条后：
1. 按段大小反查模块（9800KB→libart、676KB→libc、178KB→libartbase）；
2. 反汇编对应偏移，即可点名**是谁在等这个 futex**；
3. 与 `num_threads=1` / `clone=0` 交叉验证 → 确认"等一个永不会被 signal 的锁"，
   下一步就能针对"该创建的线程为何没创建"下手。

## 七、教训（本轮最重要）

**"诊断修了一半"等于没修**：v1.2.26 我只修了**帧链**的 PAC 掩码，
**漏了栈扫描**同一处问题，导致最关键的阻塞场景仍然空白。
**同一根因要一次把所有使用点都找出来**（本轮已用 `去PAC=2` 做了产物级确认）。
