不是死循环、不是死锁 —— 是 **ART 正在合法地建堆**：

## 二、★★★★ 真正的瓶颈：**我们自己的 2ms 轮询**

原示踪循环：

```c
t = waitpid(-1, &st, __WALL | WNOHANG);
if (t == 0) {  …  usleep(2000);  continue;  }     /* ← 2ms 轮询 */
```

**实测吞吐（v1.2.25/26/27 三轮一致）：**

```
8900 停点 / 20s  =  445 syscall/s  =  2.247 ms / 次
轮询周期                             =  2.000 ms
```

**吻合到小数点。** 也就是说：**guest 的每一次 syscall 都在等我们的轮询节拍。**

**后果**：ART 建堆要跑几十万次 syscall（低 4GB 逐页 memfd 复制 + msync）
→ 被限速成 **几分钟** → **看门狗判"卡死"强杀**。
这就是 `JNI_CreateJavaVM` 永远走不完、UI 永远"运行中"的直接原因。

> 当年改成 WNOHANG 轮询是有原因的（v1.2.20：guest 阻塞在 futex 时没有停点，
> tracer 死等 `waitpid` 就轮不到体检标志）。**但代价是全局 2ms 地板，得不偿失。**

## 三、v1.2.28 的改法：**阻塞等待 + 信号唤醒**

```c
static void tvm_sig_wake(int sig) { (void)sig; }        /* 空处理函数 */
static void tvm_install_wake_sig(void) {
    struct sigaction sa; memset(&sa, 0, sizeof(sa));
    sa.sa_handler = tvm_sig_wake;
    sa.sa_flags = 0;                    /* ★ 不带 SA_RESTART！ */
    sigemptyset(&sa.sa_mask);
    sigaction(SIGUSR1, &sa, NULL);
}

/* 示踪循环 */
t = waitpid(-1, &st, __WALL);           /* ★ 阻塞：停点即到即处理 */
if (t < 0) { if (errno == EINTR) continue; break; }

/* 看门狗置好标志后，立刻打断示踪器 */
if (g_t_thr) pthread_kill(g_t_thr, SIGUSR1);
```

**关键点**：
* 处理函数**必须不带 `SA_RESTART`** —— 否则 `waitpid` 会被自动重启，**不会**返回 `EINTR`；
* "guest 阻塞在 futex 时也要能体检"这个需求**没有丢**：体检本来就由**主线程**用
  `/proc/<pid>/syscall` + `process_vm_readv` 完成（不需要停点、不需要 tracer 身份），
  主线程置标志后发信号，示踪器回到循环顶部处理即可。
