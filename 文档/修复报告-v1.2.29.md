**修复前 445/s → 修复后 ~15,400/s，提升 34 倍。**

**直接后果：ART 建堆的 msync/mmap/munmap 风暴（约 62 万次 syscall）在 ~50 秒内跑完了** ——
这是前几轮**从未发生过**的事（之前永远被 2ms 地板拖住 → 被看门狗杀掉）。

## 三、★★★★★★ 新的（也是最后的）阻塞者已点名

建堆跑完后 guest 转为阻塞：

```
[hang] nr=98 sp=0x723be67010 pc=0x72364f6da4
       a0=0xb40000723b04d984  a1=0x80  a2=0x3  a3=0x0
黑匣子连续 80s~90s 都是同一条：98 0xb40000723b04d984 0x80 0x3 0x0
```

即 `futex(uaddr=0x723b04d984, **FUTEX_WAIT|FUTEX_PRIVATE**, 期望值=3, **无超时**)`。

栈扫描（v1.2.27 的 PAC 修复）给出调用链，逐帧符号化：

```
futex(阻塞)                                    ← pc 在 libc 的 futex 包装
 ← libc        je_free +0x8c
 ← libartbase  art::MemMap::CheckMapRequest
 ← libart      art::Thread::Init(ThreadList*, JavaVMExt*, JNIEnvExt*)   +0x510
 ← libart      art::Thread::Thread(bool)                                +0x1e8
 ← libart      art::Thread::Attach(char const*, bool, _jobject*, …)     +0xc4
 ← libart      art::Thread::Startup()                                   +0xa8   ★★
 ← libart      art::Runtime::Init(art::RuntimeArgumentMap&&)            +0x1388
 ← libart      art::Runtime::Create(art::RuntimeArgumentMap&&)          +0x50
 ← libart      art::Runtime::Create(std::vector<…> const&, bool)        +0x44
 ←             JNI_CreateJavaVM                                         +0xfc
```

### 关键事实

| 项 | 值 | 含义 |
|---|---|---|
| 等待对象 | `pthread_mutex_t @ 0x723b04d984`，`期望值 = 3` | bionic 互斥字：**LOCKED(1) \| WAITERS(2) = 3** |
| 超时 | `NULL` | **无限等** |
| 线程数 | `num_threads=1`、`clone` 0 次、`PTRACE_EVENT_CLONE` 0 | **进程只有 1 个线程** |
| 位置 | `art::Thread::Startup()` → `Thread::Attach` → `Thread::Init` | **ART 线程系统初始化中** |

**即：单线程进程在等一把已被持有的静态互斥锁，且永不放弃。**

## 四、v1.2.29：把"谁持锁"取证出来（决定性实验）

两种可能**修法完全不同**，必须先分清：

| 可能 | 判据 | 修法方向 |
|---|---|---|
| **自死锁** | `owner_tid == 本进程 pid` | 同一线程二次加锁（非递归锁）→ 查我们是否**改写/重放了某个 syscall**导致锁状态不一致 |
| **等不存在的线程** | `owner_tid != 本进程 pid` | 该线程从未被 `clone` 出来 → 查线程创建的 syscall 路径 |

新增取证（在体检里，`nr==98` 时）：

```
[futex] uaddr=0x723b04d984 段=<大小>KB<模块> lockword=0x3(LOCKED=1 WAITERS=1) owner_tid=<N> 本pid=<P> → ★…
[futex] 原始 16 字节：03 00 00 00 <owner_tid 小端> …
```

* 读地址前先做 **TBI 去标签**（`a0 & 0x007FFFFFFFFF`）—— 与 PAC 掩码同一类坑；
* 同时输出该锁**所在段的大小**（便于按 ROM 段大小反查是哪个库的全局变量）；
* 输出原始 16 字节，便于人工核对 bionic 互斥体布局。

## 六、下一轮判据

```
[futex] uaddr=0x723b04d984 段=<大小>KB lockword=0x3(LOCKED=1 WAITERS=1) owner_tid=<N> 本pid=<P> → ★结论
```

* **若 `owner_tid == P`** → **自死锁**：查 `Thread::Startup` 路径上
  我们是否对某个 syscall 做了不该做的改写（尤其 `futex`/`clone`/`sigprocmask`），
  或信号处理（v1.2.28 新装的 SIGUSR1！）打断了 ART 的锁协议；
* **若 `owner_tid != P`** → **等一个不存在的线程**：查 ART 为何**一次 `clone` 都没发**，
  重点看 `Thread::Startup` 里"创建 signal-catcher / 线程池"那一步是否被我们挡掉。

> **⚠ 已列入排查清单**：v1.2.28 为唤醒示踪器安装了 **SIGUSR1 处理函数**。
> 若 ART 的锁协议依赖信号时序，这个处理函数**可能**是新的干扰源 ——
> 下一轮若 `owner_tid == 自己`，优先怀疑它（可临时只装给示踪器线程、
> 或用 `tgkill` 定向、或改用 `signalfd`/`eventfd` 唤醒）。

## 七、累积方法论（本轮新增）

| 教训 | 体现 |
|---|---|
| **性能瓶颈会伪装成"卡死"** | 2ms 轮询把 ART 建堆拖成几分钟 → 看门狗判"卡死"强杀。**看门狗判死前，先算一遍吞吐量级** |
| **观测值要换算成"每次多少 ms"再比对代码常量** | `8900 停点/20s` → `2.247ms/次` ↔ `usleep(2000)`：一算即中 |
| **同一平台坑会反复出现** | PAC/TBI 掩码：帧链 → 栈扫描 → futex 地址，**三处都要做**（本轮 futex 已补） |
