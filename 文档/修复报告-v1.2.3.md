# TwinVM v1.2.3 —— Abort message 探针：si_value.sival_ptr（离真相只差一行）

> 输入：v1.2.2 真机日志（5737 行）。本轮判读信息量大：guest 深度再翻倍，
> abort 机器全部符号化，只差"原因文本"的最后一格。

## 1. v1.2.2 判读

### 1.1 libartbased ENOENT 竟然不致命（红鲱鱼实锤）

guest 走过了 libartbased 的三路 ENOENT 继续跑（cmdline 读、GC 已起、
~760 个事件）——它不是死因。/apex 同名回退 0 命中＝设备上该路径也没有
此文件（open 失败）。真正的死点在其后：

```
#763 uname → #764-767 cmdline×2 → cache-info.xml ENOENT → socket(AF_UNIX) → ABORT
```

### 1.2 abort 现场完全符号化（离线三步对账）

1. maps 落盘定位 PC 所在区：`723bc6c000-723bd15000 rwxp`；
2. 对账 mmap-fill 日志：`fd=10005 at=0x723bc6c000 off=372736 n=689216`；
3. fd=10005 复用序（768 行）＝ **libc.so** → 文件偏移 0x8968C
   → 符号化＝ **abort+0xa0**（tgkill 发信点，lr=abort+0x7c）。

### 1.3 最后一格：abort 原因在 sigqueue 里

libc abort() 用 `rt_tgsigqueueinfo` 发 SIGABRT（si_code=**-1 = SI_QUEUE**），
**si_value.sival_ptr = android_set_abort_message 存的消息串指针**——
debuggerd 就是读它打出 "Abort message: '…'"。我们的 [sig] 打了 si_pid
没打 si_ptr，原文一直差这一格。ART 的 FATAL 日志只走 logd socket
（socket 建了没 connect 就 abort 了），stderr 分支为空——所以只有这条路。
