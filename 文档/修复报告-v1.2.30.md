# TwinVM v1.2.30 —— ★★★★★ 撤掉我 v1.2.28 引入的 SIGUSR1 处理函数（怀疑打断了 ART 的挂起协议）

> 输入：v1.2.29 真机日志（829 KB）

## 一、取证结果（并**修正我上一轮的过度解读**）

```
[futex] uaddr=0x723b04d984 段=4096KB[anon:libc_malloc] lockword=0x3(LOCKED=1 WAITERS=1) owner_tid=0 本pid=29315
[futex] 原始 16 字节：03 00 00 00 | 00 00 00 00 | 00 00 00 00 | 83 72 00 00   (末 4 字节 = 29315 = pid)
```

* 锁在 **malloc 区**（不是静态全局）；
* `lockword = 3` = **LOCKED | WAITERS**，且**无超时**。

### ★ 更正：`owner_tid=0` **不能**排除自死锁

我上一轮把"owner=0"直接读成"等一个不存在的线程"，**这个推断不成立**：
**bionic `pthread_mutex_lock` 的快路径是 `CAS(state: 0 → LOCKED)`，它只写 `state`、不写 `owner_tid`**
（`owner_tid` 只在慢路径成功时赋值）。所以 owner=0 + LOCKED 完全可能是"**同一线程二次加锁**"
的自然现象。这条取证能给出锁字与所在区，但**不足以定 owner**。

## 二、★★★★★ 新的头号嫌疑：**我 v1.2.28 装的 SIGUSR1 处理函数**

### 时间线完全吻合

| 版本 | 变化 | 结果 |
|---|---|---|
| ≤ v1.2.27 | 2ms 轮询，吞吐 445/s | 卡在建堆，**从未到达 `Thread::Startup`** |
| **v1.2.28** | ① 阻塞 `waitpid`（吞吐 34 倍）② **新装 SIGUSR1 空处理函数** | **第一次跑到 `[6/6] 已进入 ART`、读到 cmdline** |
| v1.2.29 | 建堆跑完 | 新阻塞点：`Thread::Startup()` 等一把 LOCKED&#124;WAITERS 的锁 |

**"第一次跑到这里"和"新装 SIGUSR1"是同一个版本发生的。**

### 机理

```
JNI_CreateJavaVM → Runtime::Init
  → **art::Thread::Startup()** → Thread::Attach → Thread::Thread → Thread::Init
  → futex(…, FUTEX_WAIT|PRIVATE, 期望值=3, 无超时)      ← 永久等待
```

**ART 用 `SIGUSR1` 承担线程挂起（suspend）协议。** 我把它覆盖成空处理函数后：
挂起请求被**静默吞掉** → 等"挂起完成"的那一段**在屏障上永久等待** ——
正好表现为"单线程、等一把 LOCKED|WAITERS、无 owner、无超时"的锁。

## 三、v1.2.30 的改法：**撤掉信号，只保留性能收益**

```c
/* 不再安装 SIGUSR1（函数体保留作反例记录） */
static void tvm_install_wake_sig_DISABLED(void) { … }

/* 两处唤醒一并删除 */
- if (g_t_thr) pthread_kill(g_t_thr, SIGUSR1);
```

**为什么可以安全撤掉**（这个信号本来就是"顺手的便利"，不是必需）：

| 需求 | 真正的实现 |
|---|---|
| guest 阻塞在 futex 时也要体检 | **主线程**直接用 `/proc/<pid>/syscall` + `process_vm_readv` 做，**不需要停点、不需要 tracer 身份** |
| 抓调用链 | v1.2.27 的 **procfs 栈扫描已加 PAC 去掩码**，阻塞场景照样出 24 条返回地址 |

**保留的是唯一有实测收益的那一项**：阻塞 `waitpid`（吞吐 445/s → **15,400/s，34 倍**）。

```
[alive] … guest 活动 <继续增长>          ← 吞吐应保持 ~15k/s
```

**若 futex 阻塞依旧**，则按下列顺序推进（已在计划内）：
1. **futex 调用留痕**：给 `nr=98` 加 args 记录（op/uaddr/val，节流），
   看是否出现 `FUTEX_WAKE` 以及它与 `FUTEX_WAIT` 的配对 —— 直接分出"自死锁"还是"丢信号"；
2. **反汇编 `art::Thread::Startup()`**（libart.so 在手），看它在此处到底等什么；
3. 若确认是信号协议：改为**定向唤醒**（只给示踪器线程用 `tgkill` + 不冲突的实时信号），
