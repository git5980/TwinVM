# TwinVM v1.2.32 —— ★★★★★ 根因收窄完成：**整个运行里 `clone` 一次都没发生**

> 输入：v1.2.31 真机日志（831 KB）+ logcat + 崩溃包（9 个 tombstone）

## 一、★ 崩溃包是噪声（已确认）

9 个 `crashes-*.log` 全是 **`twinvm-selftest` 线程的 `SIGSYS / SYS_SECCOMP`**
（`Cause: seccomp prevented call to disallowed arm64 system call 249` = `request_key`），
即 App 自带策略自检的**预期副产物**，与本问题无关 ✓

## 二、★★★★★ futex 环形留痕给出决定性证据

```
[futex-hist] 共记录 5 次 futex 调用，倒出最近 5 条：
  #0  WAKE (PRIVATE) uaddr=0x723b5332e0 val=2147483647   (INT_MAX = 唤醒全部)
  #1  WAKE (PRIVATE) uaddr=0x723ae7c490 val=2147483647
  #2  WAKE (PRIVATE) uaddr=0x723ba7b008 val=2147483647
  #3  WAKE (PRIVATE) uaddr=0x723aee31d0 val=2147483647
  #4  WAIT (PRIVATE) uaddr=0x723764d984 val=3            ← 阻塞在这里，且此前无任何 WAIT
```

**整个运行只有 5 次 futex 调用。前 4 次都是"唤醒全部"（`pthread_cond_broadcast` 形态），
第 5 次才是一次 WAIT —— 而它等待的地址上，从来没有任何 WAKE。**

### 两个此前判断的修正

| 之前 | 现在 | 依据 |
|---|---|---|
| "是 `pthread_mutex_t`（LOCKED\|WAITERS）" | **更可能是 `pthread_cond_wait`** | `WAKE` 的 val 都是 `INT_MAX`（bionic `pthread_cond_broadcast` 的形态）；bionic 的 `pthread_cond_wait` 以 `state + 增量` 作为期望值，`3` 与之吻合 |
| "`owner_tid=0` → 无持有者" | **该字段本就不可靠** | bionic 互斥快路径 `CAS(0→LOCKED)` **不写** owner_tid |

**但两者结论一致且更重要：没有人会来唤醒它。**

## 三、★★★★★★ 根因收窄：**`clone` 从未被调用**

对全日志做穷举检索：

```
nr=220 (clone)  在 trace / 黑匣子中：0 次
nr=435 (clone3) 在 trace / 黑匣子中：0 次
PTRACE_EVENT_CLONE / new-thread / GETEVENTMSG：0 次
黑匣子采到的 syscall 种类：98(futex) ×46、227(msync) ×1、running ×4 —— 别无其它
```

**即：guest 从头到尾只有 1 个线程，从未创建过任何线程。**
而 ART 的启动需要"signal-catcher / 线程池"这类**辅助线程**完成握手；
主线程于是在 `Thread::Startup` 之后的某处**等一个只可能由另一个线程送来的唤醒**。

### 问题的形态因此彻底变了

> **不再是"锁的语义是什么"，而是："`pthread_create` 为什么在 `clone` 之前就失败了？"**

bionic 的 `pthread_create` 在 `clone` **之前**依次要做：
`mmap` 线程栈 → `mprotect` 守卫页 → `__init_tls`（读 auxv / program headers）→ `rt_sigprocmask` 等。
**其中任一步返回错误，都会"静默返回失败、完全不调 `clone`"** —— 与观测完全吻合。

## 四、v1.2.32：盯住这条链上的 syscall 返回值

新增 **失败 syscall 留痕**（只盯 watchlist，且**只在返回 `-errno` 时**打印，每 nr 最多 6 条）：

```c
static int tvm_fail_watch(long nr) {
    switch (nr) {
        case 222: /* mmap */   case 215: /* munmap */  case 226: /* mprotect */
        case 220: /* clone */  case 435: /* clone3 */  case 214: /* brk */
        case 98:  /* futex */  case 135: /* rt_sigprocmask */
        case 167: /* prctl */  case 99:  /* set_robust_list */
        case 96:  /* set_tid_address */  case 261: /* prlimit64 */
        case 163: /* getrlimit */        case 260: /* wait4 */
            return 1;
        default: return 0;
    }
}
```

输出形如：

```
[fail] nr=222 → -12（首次）      ← mmap 失败（ENOMEM）
[fail] nr=226 → -1 （首次）      ← mprotect 失败
```

**这条链上任何一次失败都会直接解释"线程为何生不出来"**，
而且只打印失败项，对已修好的 15k/s 吞吐没有影响。

## 六、下一轮判据

```
[fail] nr=… → -…          ← ★ 线程创建链上到底哪一步失败
```

* **若看到 `nr=222 → -12`（mmap ENOMEM）** → 线程栈分配失败：
  查 guest 的地址空间碎片/RLIMIT，以及我们是否漏放行了某个相关 syscall；
* **若看到 `nr=226`/`nr=135` 失败** → 守卫页 / 信号掩码设置失败；
* **若一条 `[fail]` 都没有** → 说明 pthread_create 根本没被 ART 调到（而是 ART 主动
  在等一个它自己也没去创建的线程）→ 那就转向**反汇编 `art::Thread::Startup()`**
  （libart.so 在手，地址已能由 v1.2.27 的帧链给出）确认它的顺序假设。

## 七、方法论（本轮）

| 教训 | 体现 |
|---|---|
| **"从未发生"也是强证据** | `clone` 0 次这一条，比任何栈回溯都更能定性问题 |
| **穷举检索要有意识覆盖全部通道** | trace / 黑匣子 / 事件三种通道都查了，才能说"一次都没有" |
| **把问题从"语义"转成"时序"** | 从"这把锁是什么"转到"线程为何没被创建"，方向立刻清晰、可验证 |
