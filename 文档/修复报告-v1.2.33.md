# TwinVM v1.2.33 —— ★★★★★ 抓到 `mmap → EINVAL`；并修掉 `getrlimit` 一律返回"无限"的真 bug

> 输入：v1.2.32 真机日志（832 KB）

## 一、★★★★ 失败 syscall 留痕命中了

```
[fail] nr=222 → -22（首次）
```

**`mmap` 返回 `-22 = EINVAL`** —— 这是整条"线程创建链"上唯一失败的 syscall。

> 意义：v1.2.32 的判据表里，`nr=222 → -22` 正好对应
> "**线程栈分配失败**"这一行，只是 errno 是 `EINVAL`（参数非法）而非 `ENOMEM`。
> `EINVAL` 通常意味着：**`MAP_FIXED` 传了非页对齐地址** / **`len == 0`** /
> **file-backed 的 `offset` 未按页对齐** / flags 组合非法。

## 二、★★★★★ 顺着它找到一个真 bug：`getrlimit` 对所有资源都回"无限"

`bionic` 的 `pthread_create` / `ART` 的 `Thread::Init` 都要用 `RLIMIT_STACK`
（线程栈大小、栈 HWM 计算）—— 而引擎的实现是：

```c
case 163: {                     /* getrlimit(arm64) */
    uint64_t inf[2] = { ~0ULL, ~0ULL };        /* ← 不分资源，一律 RLIM_INFINITY */
    if (a1) { … }
    return 0;
}
```

**`RLIMIT_STACK` 被报成"无限"，与 Android 实际的 8MB 不符**，
会污染 bionic/ART 的线程栈与栈 HWM 计算 ——
而 **v1.2.27 的帧链正好把卡点定在 `Thread::Init`**（那里要读 `/proc/self/stat`
的 `startstack` 并算栈上限），两者指向同一处。

### 修法（v1.2.33）

```c
uint64_t rl[2] = { ~0ULL, ~0ULL };
switch ((int)a0) {
    case 3: rl[0] = 8ULL * 1024 * 1024; rl[1] = ~0ULL; break;   /* RLIMIT_STACK = 8MB */
    case 7: rl[0] = 1024;               rl[1] = 4096;   break;  /* RLIMIT_NOFILE */
    default: break;                                             /* 其余无限 */
}
```

## 三、★ 同时更正我自己上一轮的一个判断

我上一轮说"`getrlimit` / `prlimit64` 在引擎里完全没有实现" —— **这个判断是错的**。
真实情况是它们**已经实现**，但用的是**数字字面量 `case 163:`**（不是 `case VM_NR_getrlimit:`），
所以我按宏名 grep 没搜到，误判为"未实现"。

**教训：在 C 项目里检索"某 syscall 是否实现"，必须同时搜宏名与数字字面量。**

## 四、v1.2.33 同时补上失败 syscall 的**参数**留痕

只有 `nr`+`errno` 无法定位：`mmap` 的 `EINVAL` 必须看到
`hint/len/prot/flags/fd/off` 才能判断是"`MAP_FIXED` 地址未对齐"、"长度非法"还是"地址越界"。

```c
static unsigned long long g_wargs[6];
static volatile long g_wargs_nr = -1;      /* entry 时记录 watchlist 的参数 */
…
ptrace_log("[fail] nr=%ld → -%ld args=0x%llx,0x%llx,0x%llx,0x%llx,0x%llx,0x%llx", …);
```

watchlist 扩面到线程创建全链：`mmap/munmap/mprotect/clone/clone3/brk/futex/
rt_sigprocmask/prctl/set_robust_list/set_tid_address/prlimit64/getrlimit/wait4/
sched_getaffinity/sigaltstack/rt_sigaction/getpid/gettid/rseq`。

## 六、下一轮判据

```
[fail] nr=222 → -22（首次） args=0x<addr>,0x<len>,0x<prot>,0x<flags>,0x<fd>,0x<off>
```

按参数即可一眼定性：

| 参数特征 | 结论 | 修法 |
|---|---|---|
| `off & 0xfff != 0` | file-backed `offset` 未按页对齐 | 查我们的虚拟 fd / ROM 映射路径 |
| `flags & 0x10` 且 `addr & 0xfff != 0` | **`MAP_FIXED` 地址未对齐** | 查 ART 从（我们合成的）`/proc/self/maps` 算出的地址 |
| `len == 0` | 长度非法（多半来自被污染的 rlimit/参数） | 已修 `getrlimit`，看是否消失 |
| `flags` 含未知位 | 我们把 flags 传错了 | 查拦截路径 |

**若 `getrlimit` 修复直接消掉这条 `[fail]`，且 guest 开始出现 `clone`** →
线程创建恢复 → 目标 `dalvikvm -cp /rom/hello.dex Hello` 有望跑通。

## 七、方法论（本轮）

| 教训 | 体现 |
|---|---|
| **"唯一失败项"就是最高优先线索** | 全链只此一条 `[fail]`，直接顺着它找到真 bug |
| **检索实现要同时搜宏名与字面量** | `case 163:` vs `case VM_NR_getrlimit:` —— 本轮因此误判过一次 |
| **平台期望值要与真实平台对齐** | `RLIMIT_STACK` 回"无限"在 Linux 上合法，但**Android 是 8MB**，与 ART 的假设不符 |
