## 二、新案：liblog 的 logd FATAL（fd 所有权案）

**死亡序列**（全部符号化定罪）：
```
liblog __android_log_assert("Assertion failed: %s")   ← liblog+0xC2B8（TEXT 段实测）
  → libbase LogMessage(FATAL)                          ← libbase+0x63c8
  → art::Runtime::Abort                                ← sig#0 = libart+0xc861f4 = Abort+0x334
  → abort() → SIGABRT → debuggerd_handler
    → "libc: Fatal signal 6..."（stderr tee 抓到）
    → clone(转储子进程) → prctl(PR_SET_PTRACER,ANY/0) ×2
    → （转储流程跑完，最终按 abort 语义正常死亡）
```

**根因（本轮最硬的一条）**：ptrace 后端下，**被拦截的 syscall 其实会先原生执行**
（arm64 在 entry 停点就锁定了 syscall 号，tracer 改 x8 只改了一个普通寄存器），
引擎只是在 exit 覆盖返回值。而 socket(198) 的处理是 **引擎在 tracer 进程里
原生 socket()**——返回的 fd 属于 tracer，**guest 的 fd 表里根本没有**→
guest 后续 connect → EBADF → liblog logd 写失败 → FATAL → abort。
（[fail] nr=167 -22 是**误报**：fail_watch 读的是覆盖前的内核值——引擎实际
返回了 0，debuggerd 管线是走通了的。）

**修复**：socket(198)/connect(203) 移出拦截名单 → **guest 原生 socket/connect**：
fd 就在 guest 里，connect 到宿主 /dev/socket/logd（App 权限足够）→
liblog 正常工作，日志还顺路进宿主 logcat（调试福利）。

## 三、附带发现（下轮处理）

1. **被拦截 syscall 的原生副作用**是架构事实：openat 会先打开宿主真文件再被
   覆盖成合成 fd → **真实 fd 泄漏**（每次几十个，fd 上限 32768 暂无虞）——
   记入路线图（长期：openat 改"纯合成不透传"需要 arm64 换号机制，需评估）；
2. `/system/etc/public.libraries.txt` 缺失 → libnativeloader LOG(ERROR)（非致命，
   运行继续）——后续可合成该文件；
3. fail_watch 对被拦截 syscall 读的是覆盖前的值 → [fail] 会误报——观测噪音，
   非功能问题。
