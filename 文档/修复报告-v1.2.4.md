# TwinVM v1.2.4 —— si_value=NULL（裸 abort）→ 栈扫描回溯

> 输入：v1.2.3 真机日志（5736 行）。Abort message 探针打了个空——但空得有信息量。

## 1. v1.2.3 判读

- `[sig] 收到信号 6（code=-1 发送方…）` 正常打印 ✓（SI_QUEUE 分支进了）；
- **Abort message 行没出现** = `si_value.sival_ptr < 0x1000` = **NULL**：
  bionic abort() 无条件用 rt_tgsigqueueinfo 发信（si_code=SI_QUEUE），
  消息指针为 NULL 当没有 set_abort_message——**这是一次"裸 abort"**
  （典型来源：未捕获 C++ 异常 / Runtime::Abort 无消息路径 / 某些 CHECK）；
- Fatal signal 行的线程名是 "twinvm-selftest"——prctl(PR_GET_NAME) 透传
  返回真线程名（fork 自示踪线程的名，无关紧要）；
- abort 前最后序列：libartbased 三路 ENOENT（不致命）→ prctl(GET_DUMPABLE)
  → PR_SET_VMA ×4 → uname → **cmdline ×2** → **cache-info.xml ENOENT** →
  `ioctl(38, 0xc018aa3f)`（0xaa=uffd 家族——CMC GC 的 userfaultfd！）→
  socket(AF_UNIX) → ABORT。这一段是 dex 加载（OatFileAssistant）+ GC 基础
  设施（uffd）混合现场。

## 2. FP 链为什么靠不住

abort() 的帧指针链打出来的 ret 全是垃圾值（v1.2.2/v1.2.3 两轮实锤）——
libc abort 内部 raise/tgkill 折返后 x29 已不可信。但**调用者的返回地址
还在栈上**。

## 3. v1.2.4：栈扫描回溯

致命信号停点时：
1. 读 `/proc/<tid>/maps`（真 maps，guest 自己的地址空间），收集全部
   `r-xp` 段（同名段合并，记 base=fileoff 换算）；
2. `process_vm_readv` 读 `[sp, sp+8192)`；
3. 每 8 字节筛：落在任一可执行段 → 打印 `sp+0x偏移  地址  模块+0x文件偏移`。

输出形如：`[sig] sp+0x18 0x723b1a2b4c /apex/.../libart.so +0x1234`——
**abort 调用者模块直接现形**（裸 abort 的"无消息"也被栈回溯兜住）。
另：Abort message=NULL 的分支现在显式打一行（不再静默）。

## 4. 验证

- `make -C core test` 5/5 PASS；`checkrom --strict` PASS；ROM md5 未变（fa88cc28）；
- APK SIGN_OK / versionCode=154；包内 .so 含 `sp+0x%` 探针 ✓；包内 ROM ✓。

## 5. 下一轮判据（真机跑 v1.2.4）

```
[sig] （Abort message=NULL——裸 abort 无消息，靠栈扫描回溯）
[sig] ★ 栈扫描回溯（sp=0x…，筛 N 个可执行段）：
[sig]   sp+0x…  0x…  /apex/com.android.art/lib64/libart.so +0x…   ← ★ 调用者
```

拿到"libart+偏移"清单后本地符号化 → 凶手函数名 → 动刀。

## 6. 本轮教训（第十二类：**观测分支要打"为什么没打"**）

> v1.2.3 的 si_value 探针静默跳过 NULL——多等一轮才发现是裸 abort。
> 以后每个条件分支都要有 else 打点（哪怕一行），观测代码的静默
> 就是下一轮的盲区。
