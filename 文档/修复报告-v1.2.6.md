# TwinVM v1.2.6 —— 结案：ioctl(真 fd) 被吃成 ENOTTY，art 的 uffd 握手 FATAL

> 输入：v1.2.5 真机日志（5772 行）+ 系统 logcat（9999 行）。栈扫描 v2 开工，
> 一次抓满证据链，全案告破。

## 1. 定罪过程（三步，全部实证）

### ① 栈扫描 + 原始栈 dump（v1.2.5 新探针首次全功能运行）
- 栈上唯一干净代码指针：`0x72319252b0` ×3 → 落在 libart.so 的 mmap-fill
  区（fd=10000=libart，fill at=0x723130d000 off=0x400000）→ 文件偏移
  **0xA182B0**；
- 栈上还有 linker64 的格式串 **"dlopen calling constructors: …"** +
  "\nfalse"——出事时 linker 正在跑构造函数链。

### ② 符号化 + 反汇编
```
libart.so +0xA182B0 = _GLOBAL__sub_I_mark_compact.cc + 0
```
即 **mark_compact.cc（CMC 垃圾回收器）的静态构造器**。其调用序：
`__cxa_atexit → __cxx_global_var_init.1/.10 → ShouldUseUserfaultfd() →
IsKernelVersionAtLeast(5,7)` ——与死前 syscall 序完美对应：
uname（内核版本检查）→ cmdline ×2（FetchCmdlineGcType）→
GetProperty（属性缺省）→ **ioctl(37, 0xc018aa3f)**。

### ③ KernelSupportsUffd 反汇编（最后一块拼图）
```asm
syscall(282, 0x80001)        ; 建 userfaultfd——282 不在拦截名单 → 真 fd=37 ✓
mov w1,#0xaa3f / movk #0xc018 ; ioctl 请求=0xc018aa3f（ColorOS 的 uffd API 握手，
                              ; movz/movk 拼出来——字面量搜不到的原因）
ioctl(fd, 0xc018aa3f, &api)  ; ← 被 tvm_virt_nr 拦下，引擎回 ENOTTY
cbnz w0 → LOG(FATAL)          ; android::base::LogMessage(severity=6, userfaultfd.cc:145)
                              ; 消息走 logd socket（我们看不到）→ 无遗言 abort
```

## 2. 根因（一句话）

**ptrace 后端迁移时丢了旧 BPF 的"真 fd ioctl 原生放行"语义**——引擎对一切
非 binder 的 ioctl 回 ENOTTY，art 的 uffd 握手失败被判"内核异常"FATAL。
（教训八"物理执行域"的 ioctl 实例：同一个 case，BPF 时代=放行，ptrace
时代=拦截。）

## 3. v1.2.6 修复

tracer entry 停点：`nr==29 且 fd∈[3,10000)` → 不改写、原生执行（子进程内核
对真 uffd 握手，结果直接写回 guest 内存），日志 `[ioctl] fd=N 真直通`。
fd 0/1/2（console）仍 ENOTTY（bionic 非 tty 语义）；虚拟 fd 仍走引擎（binder）。

## 4. logcat 侧发现（附带）

- guest 自身无 tombstone（被我们 trace 着，crash_dump 无法 attach——符合预期）；
- **扫雷探针每次运行生成 ~34 个系统 tombstone**（SYS_SECCOMP 死）——无害但
  玷污 DropBox，后续版本可把 sweep 降为手动开关；
- 无 SELinux avc denied。

`make -C core test` 5/5 PASS；checkrom PASS；APK 156 SIGN_OK；包内 ROM fa88cc28 ✓。
