# TwinVM v1.2.69 —— 🏁 五版灵异终局定罪：Android 16 cgroup freezer

> v1.2.68 [beat] 判定：**B（循环死）**——stress 后连无条件心跳都停。
> 三版取证链（[alrm]/[chk]/[beat]）把"死"钉在 stress 后数秒内，且无声无息。

## 全案串珠（终于全部对上了）

| 版本 | 现象 | 当时以为 |
|------|------|---------|
| v1.2.61 | 主线程 38s 后死 | "主线程死因不明" |
| v1.2.62~64 | tracer 各版正常但 graceful 不响 | 轮询/掩码/替换失败 |
| v1.2.66~68 | t-watch/[chk]/[beat] 逐一证明：**一切正常直到"输出停止后数秒"→ 全家静默** | 各种猜测 |
| **v1.2.69** | **真凶：无 WakeLock 的 App 在空闲后被系统冻结**（cgroup freezer——Android 16 对后台/空闲 App 的进程级冻结：不杀、只停） | |

**为什么每次都死在 stress 之后**：guest 输出停止 → UI 的 400ms 刷新无新内容
→ 数秒后系统判定 App 空闲 → 冻结整个进程（guest+tracer+主线程全部挂起）。
**为什么无声无息**：冻结不杀线程、不产生日志——只是不再调度。
**为什么 TA 手动停止后能导出日志**：UI 恢复前台 → 解冻 → 文件都在。
**为什么 v1.2.61 主线程先死**：主线程与 tracer 同批冻结，只是观测通道不同。
（也解释了为什么 Rom/引擎侧怎么修都没用——问题根本不在引擎里！）

## 修复（v1.2.69：运行期持 PARTIAL_WAKE_LOCK）

- 运行按钮按下：`mRunLock.acquire(10min)`（CPU 保持调度，10 分钟防泄漏保底）；
- 收场（stage0 返回/异常）：`mRunLock.release()`；
- Manifest 声明 WAKE_LOCK 权限。

引擎侧零改动——v1.2.66 的 graceful 判据链本来就是对的，
只是从未获得过"活着跑到 8 秒"的机会。
