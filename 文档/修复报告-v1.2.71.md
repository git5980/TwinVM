# TwinVM v1.2.71 —— setitimer 可用性自检（EINTR 永不命中的最后嫌疑）

> v1.2.70 真机：FGS 持有下依旧 stress 后全停——且 **47 停点的死法高度
> 规律**（每版都停在 nr=167 PR_GET_DUMPABLE 附近）。

## 本轮关键认知修正

回看 v1.2.55~70 **所有**真机日志：stress 后都是 47~51 停点、
以 nr=96(set_tid_address) 新线程出生 + nr=98 futex 收尾——**这是 ART
Shutdown 的标准收尾舞步，然后 guest 在 futex 死等**（正常：等线程退出）。

所以真相可能比"冻结"更简单：**guest 没死，是 tracer 在 futex 静默期
没有任何唤醒源**——SIGALRM（唯一唤醒源）从未响过。沙箱验证
setitimer→ALRM→EINTR 全链正常；**真机上 [alrm] 就绪声明打了但 EINTR
零命中**——最大嫌疑：**App seccomp 对 setitimer 返回 ENOSYS**
（此前从未检查过返回值！——v1.2.63"替换静默失败"同款低级错误的又一变体）。

## v1.2.71（自检 + 自适应兜底）

- 首次调用 setitimer 后**检查返回值**并打日志：
  `[alrm] setitimer 可用（SIGALRM 打断 waitpid）` 或
  `[alrm] setitimer 被拒→WNOHANG 轮询兜底`
- 被拒时：全程 WNOHANG+20ms 轮询（静默期驱动 graceful；忙时立即返回，
  吞吐影响仅在静默期）。

## 验证

沙箱 alrmtest 全链 ✓；make test 5/5；APK **221/1.2.71 SIGN_OK**。

## 下轮判据（一行定生死）

```
[alrm] setitimer 可用 → 之后 [alrm] EINTR 命中 → [t-watch] → [graceful] ✓
[alrm] setitimer 被拒 → 轮询兜底直接驱动 [t-watch]/[graceful] ✓
```
两种读数都能让 graceful 落地——除非 setitimer "成功但不投递信号"（真机
seccomp 假成功），那是最坏情况，下轮日志见分晓。
