# TwinVM v1.2.72 —— 🏁 终极真凶：信号投递目标被主线程抢收

> v1.2.71 真机判决：**setitimer 可用**（返回值 0 ✓）——但 EINTR 依旧零命中。
> 沙箱全链正常 vs 真机永不响——矛盾指向投递环节。

## 定罪（教科书级信号陷阱）

Linux 信号投递目标 = **任一未屏蔽该信号的线程**（内核自选，通常主线程优先）。

旧代码时序：
1. 主线程创建 tracer 前屏蔽 SIGALRM（2614，含在 chld_m）；
2. tracer 出生继承屏蔽 → v1.2.66 给 tracer 自行 UNBLOCK ✓；
3. **但主线程在 fork 完成后恢复 old_m（fork 前的干净掩码）→ 主线程
   变回不屏蔽 ALRM**（2642 恢复整个旧掩码——v1.2.63 加的"屏蔽 ALRM"
   被这次恢复抹掉了）；
4. → 主线程和 tracer 都 unblocked → **内核把每个 SIGALRM 都投给主线程**
   （空 handler 吃掉）→ **tracer 的阻塞 waitpid 从未被信号打断**。

完美解释全部五版（v1.2.66~71）：
- setitimer"可用"却零 EINTR ✓（信号发了，但打错人）
- 主线程"38s 死亡"假象 ✓（它吃信号的 handler 空转，观测通道停是别的原因）
- 沙箱全链正常 ✓（测试程序单线程，没有"别的线程"抢收）

## 修复（v1.2.72：一行）

主线程恢复掩码时**强制带上 ALRM 屏蔽**（`rm = old_m; sigaddset(&rm, SIGALRM)`）
——全进程只剩 tracer 一个投递目标，信号必达。
