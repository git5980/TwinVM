# TwinVM v1.2.8 —— stat 真身直读：startstack=0 之死（教训五第四击）

> 输入：v1.2.7 真机日志（6161 行）。三判据全中（maps 真身 204KB、cpu 0-7、
> ioctl 直通），但 guest 死于**下一层**——而且死因文案直接打出来了。

## 1. v1.2.7 判读

```
openat("/proc/self/maps")  -> [synth 204799B]      ✓ 真身直读生效
openat("/sys/devices/system/cpu/possible") -> [合成 0-7] ✓
openat("/proc/self/stat")  -> [synth 138B, startstack=0x0]   ★ 病灶
… ~40 万字节 maps 长读（数十次 4KB read）…
libc: stack not found in /proc/self/maps        ★ 死因原文（tee 首次抓到）
```

bionic `__find_main_stack_limits()`：从 stat 第 28 字段取 startstack → 到
maps 找包含区间。**startstack=0** → 找不到 → fatal。

根因（教训五第四击）：旧 stat 合成的 `g_guest_stack_base` 由**子进程**的
loader 设置，父进程（syscall 处理方）恒零——与 maps 同病。

## 2. v1.2.8（一处）

stat 分支改为**真身直读** `/proc/<pid>/stat`（读失败退回旧合成）：startstack/
startcode/starttime 等字段天然正确，且天然落在真身 maps 的区间内（fork 源
线程的栈在子进程真实存在）。与 maps 同一哲学：**guest 有真 pid，能直读的
proc 文件绝不手工合成**。

## 3. 验证

- `make -C core test` 5/5 PASS（maptest 断言随真身语义更新：startstack 非零）；
- `checkrom --strict` PASS；ROM md5 未变（fa88cc28）；
- APK SIGN_OK / versionCode=158；包内 ROM ✓。

## 4. 下一轮判据（真机跑 v1.2.8）

```
openat("/proc/self/stat") -> fd=… [真身 ~1xxB, startstack=0x7…（真值）]
"stack not found" 不再出现

```
