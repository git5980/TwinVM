# TwinVM v1.2.89 —— 🏁 终解：v1.2.76 速率判据的"自杀性副作用"

> TA 最后机会局。放弃单点猜测，做时间账，铁证闭环。

## 破案（一笔时间账）

```
观测：循环期 mprotect 每对间隔恰好 40ms（25 对/秒）
v1.2.76 我写的慢轮询 sleep = 20ms
每对 mprotect = 2 个停点（entry+exit）× 20ms 轮询延迟 = 40ms  ← 完美吻合
```

**真凶是自己**：v1.2.76 设"≥100 停点/s 才算忙，否则 20ms 慢轮询"——
本意抓 futex 死锁，但 **ART 构造期（libart 298 个构造/heap 逐页初始化）
的真实停点速率只有 ~50/s**（大量纯用户态计算）：

```
50/s < 100 → 被判"静默" → 每停点 20ms 节流 → 启动拖慢 4~10 倍
→ 90s 兜底把它当死锁收尸
```

**没有死循环，没有重跑**——是健康的 ART 初始化被我自己的代码节流成了
"看起来像死循环"。（v1.2.75 风暴期 39044/s > 100 → 满速 ✓，所以风暴
快、构造慢——历史日志两个速率档的真相。）

九版侦查全部贡献了排除法：close/uffd/EINVAL/fd 截断全修对了（都是真实
bug 但都不是主犯），帧链/探针把"正在干活"钉死（无 futex WAIT、构造 ra
推进），最后时间账锁死真凶。

## 修复（v1.2.89：两个数字）

```
忙阈值：100 → 32 停点/s（ART 构造 50/s 恢复满速；futex 死锁 0/s 照走慢轮询）
慢轮询：20ms → 5ms（真死锁兜底灵敏度 ×4）
```

自洽性：三级 graceful 判据原样（≥8 停点/s 不杀/8s 死锁快收/90s 兜底）；
修复后 ART 构造期全速 → 90s 兜底前必然跑完。
