# 修复报告 · v17 图形族（ColorSpace → Canvas → 首帧地基）

日期：2026-10-31　版本：hotfix-10311250　目标：M3-c「让 Activity 真正活」

---

## 一、问题

设备（OnePlus PKR110 / Android 16）容器C 跑 `TwinVM-M2-DemoApp`，
`onCreate` 在 `setContentView` 构建 View 树时中断：

```
No implementation found for long android.graphics.ColorSpace$Rgb$Native.nativeCreate(
    float,float,float,float,float,float,float,float[])
  (tried Java_android_graphics_ColorSpace_00024Rgb_00024Native_nativeCreate ...)
Landroid/graphics/ColorSpace; failed initialization: java.lang.UnsatisfiedLinkError ...
  at android.graphics.ColorSpace$Rgb$Native.nativeCreate(Native Method)
  at android.graphics.ColorSpace$Rgb.<init>(ColorSpace.java:3154)
  at android.graphics.ColorSpace$Rgb.<init>(ColorSpace.java:2912)
  at android.graphics.ColorSpace.<clinit>(ColorSpace.java:1603)
M3-Bootstrap: onCreate 段异常（继续）: ... ← onCreate
```

（设备日志 `logs/twinvm-live-c.log`，原始行 16374–16421）

后果：`ColorSpace` 类初始化失败（`<clinit>` 抛错后类进入 erroneous 状态），
后续 `ColorStateList`/`TextPaint`/`TextView` 全部连坐；生命周期只剩
onStart/onResume/onPause/onStop 四段（4/5），界面自然出不来。

## 二、根因

AOSP `framework/base/graphics/java/android/graphics/ColorSpace.java`：

- `Rgb.<init>`（:3138 起）在 `mTransferParameters != null` 时调用
  `Native.nativeCreate(7×float, float[])`（:3154）；
- `Rgb.Native`（:2683）只声明两个 native：
  ```java
  static native long nativeGetNativeFinalizer();
  static native long nativeCreate(float a, ..., float g, float[] xyz);
  ```
- `ColorSpace.<clinit>`（:1603）第一件事就是构造 sRGB `Rgb`，必然踩到 nativeCreate；
- `NoImagePreloadHolder.sRegistry = new NativeAllocationRegistry(..., Native.nativeGetNativeFinalizer(), 0)`
  在首次 `registerNativeAllocation` 时也会调用另一个 native。

对照 libcore（ROM 内 `framework.dex` 实测，`tools/dexnative.py` 导出）：

```
Landroid/graphics/ColorSpace$Rgb$Native;  nativeCreate             (FFFFFFF[F)J
Landroid/graphics/ColorSpace$Rgb$Native;  nativeGetNativeFinalizer ()J
```

`libtvmbridge.so` 的 JNI 注册表（19 张表）里**没有这个类**——ColorOS 的
framework 比通用 core-patch 新，绘制系统 native 面比桥里已铺的大一圈。
这不是 ROM 缺陷，而是桥的覆盖缺口。

## 三、修复内容

### 3.1 ColorSpace（直接解锁 onCreate）

`src/bootstrap/tvmbridge.c` 新增 `kColorSpace`：

| Java native | 描述符（ROM 实测） | 桩语义 |
| --- | --- | --- |
| `nativeCreate` | `(FFFFFFF[F)J` | 返回稳定非 0 句柄 `1`（SkColorSpace* 只作不透明 token，后续 Skia 全桩，不解引用） |
| `nativeGetNativeFinalizer` | `()J` | 返回**真实 no-op C 函数地址**（见 3.3） |

### 3.2 绘制族一次铺完（防下一站打地鼠）

用 `tools/gen_registry.py` 从 ROM `framework.dex` **实测 native 描述符**生成
`src/bootstrap/gen_registry.h`，整族注册（而非照 AOSP 猜）：

| 类 | 条数 | 说明 |
| --- | --- | --- |
| `android.graphics.BaseCanvas` | 34 | 全部 nDraw*（含 ColorOS 专有 nDrawSmoothRoundRect/16、nPunchHole） |
| `android.graphics.Canvas` | 33 | nInitRaster/nSave*/clip/matrix/quickReject |
| `android.graphics.Matrix` | 40 | 变换族 |
| `android.graphics.Matrix$ExtraNatives` | 2 | nCreate / nGetNativeFinalizer |
| `android.graphics.Path` | 47 | 路径构建/变换 |
| `android.graphics.Paint` | 90 | 替换旧表（旧表多处描述符与 ROM 不符，见 3.4） |
| `android.graphics.RenderNode` | 94 | 替换旧表（nResetPivot 等 ROM 为 `Z` 返回等） |

合计新增/替换 **342** 条，全部按 ROM dex 描述符逐字生成，**零猜测**。

桩按返回类型分族（`tvm_stub_void/false/int/one/float/double/null`），
变参 C 函数在 AArch64 JNI 调用约定下安全（被调方不读参数；返回宽度按族匹配）。

### 3.3 finalizer 从"伪地址"改为"真实 no-op 函数"

旧实现（Theme/Paint/Typeface/Binder 等）返回 `0xdeadbeef` 或 `1` 作为
`NativeAllocationRegistry` 的 freeFunction。GC 真回调时会跳到非法地址（SEGV 隐患）。
新增：

```c
static void tvm_noop_free(void* p) { (void)p; }
static jlong tvm_finalizer_addr(void) { return (jlong)(intptr_t)&tvm_noop_free; }
```

所有 `*GetNativeFinalizer` / `*GetFinalizer` 桩统一返回它（含 ColorSpace）。

### 3.4 清理 25 条僵尸登记

`tools/audit_bridge.py` 对照 ROM dex 发现旧表有 25 条描述符在 ROM 里根本不存在
（如 `SystemProperties.native_get(String)`、`Trace.nativeAsyncTraceEnd(J)V`、
`MessageQueue.nativePollOnce(JII)V`、`AssetManager.nativeAddAssetPath` 等）。
这些条目本来注册就失败（异常被清掉），删除后：

- 审计：**僵尸/错位 0 条**
- 宿主 JVM 注册实测：**437 ok / 0 fail**

（未补齐的 112 条是这些旧类里"ROM 有、桥没有"的方法，属既有缺口，不是本次卡点；
见第八节。）

### 3.5 注册过程可观测

`JNI_OnLoad` 现在打印每张新表的注册结果，guest stdout 直接落 live 日志：

```
[bridge] JNI 注册完成: N ok / M fail（19 张表）
[bridge] class[i] FindClass FAILED（跳过）      # 类找不到会显式报
[bridge]   reg FAIL <method>                    # 新族签名错位会逐条报
```

这样下一次真机日志能直接判断"桥是否生效"，不必再靠猜。

## 八、预期下一站（若 onCreate 通过）

1. **TextView 构造/测量**：`Paint` 读写值现在恒 0（`nGetTextSize` 等），首帧尺寸会是 0；
   需要给 Paint 加最小状态（textSize/color/flags），或在 Java 侧用壳直供。
2. **PhoneWindow/DecorView 壳链**：v94b 用 Unsafe 造壳，`setContentView` 的
   `addView`/`requestApplyInsets` 可能触 `mDecor` 空字段；日志若见 NPE 按栈补字段。
3. **Bitmap/Canvas 真句柄**：`Bitmap.nativeCreate` 返回 Java Bitmap 对象，不能简单给 1；
   若首帧走 `Bitmap.createBitmap`，需要 JNI `AllocObject` + 字段填充（下一族）。
4. **文字排版**：`Paint.nGetTextAdvances`/`nGetFontMetricsInt` 返回 0 会让文本宽高为 0，
   要按 Minikin 语义给"每字符固定宽高"的近似值。
5. **ViewRootImpl**：`WindowManager.addView` 目前是 Proxy 返回 null —— 首帧要显式
   反射驱动 `ViewRootImpl`（measure/layout/draw）或提供最小 WindowSession 壳。
