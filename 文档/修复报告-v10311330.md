## 二、根因

日志 `M3-CL: java.lang.BootClassLoader@…`：Bootstrap 被加载进 **BootClassLoader**。
之前的 `DexFile.loadClass("…MainActivity", BootClassLoader)` 只是把主类"硬定义"进
BootCL，而 BootCL 的 dex 路径里**没有 APK**——所以主类能构造，主类里引用的
`MainActivity$1` 在解析时找不到 → `NoClassDefFoundError`。

ATM 问题是执行顺序：`manualAttach` 先 attachBaseContext（内部 v94b 会建 View，
触发 Activity 主题初始化 → ATM），而此时 v35/v89 的代理还没装。

## 三、v19 修复

### 3.1 APK 进真 classloader

- 从 `System.getProperty("java.class.path")` 取 `*.apk` 路径（默认
  `/data/app/TwinVM-M2-DemoApp.apk`）；
- `new dalvik.system.DexClassLoader(apkPath, null, null, Bootstrap.class.getClassLoader())`
  → 设置线程上下文 loader；
- 业务主类改用 `Class.forName(cls, true, apkLoader)` 装载，主类与内部类共享
  同一条 dex 路径；
- 诊断用的 `DexFile.loadClass` 改载 `CliMain`，不再提前污染业务主类；
- 兜底：若 DexClassLoader 失败/装不上，用 `DexFile.entries()` 把
  `cls` 与所有 `cls$*` 内部类逐个 `loadClass(…, BootCL)` 预定义（沿用已验证的 DexFile 通路）。

### 3.2 ATM 早预填

新增 `prefillAtmEarly()`：在 `manualAttach` 一开始就把
`ActivityTaskManager` 的 `Singleton.mInstance` 填成 `IActivityTaskManager` Proxy
（复用 v89 语义：所有方法 `deepStub`）。这样 v94b 构造 FrameLayout(act) 时
ColorOS 的 `onApplyThemeResource → setTaskDescription → ATM` 整链短路。

### 3.3 预期

- `M3-apk: DexClassLoader ✓` / `M3-apk: DexFile 兜底预定义 N 个类`；
- `M3-man: v19 ATM 早预填 ✓`；
- `M3-man: v94b PhoneWindow 壳链 ✓`；
- `M3-Bootstrap: onCreate 完成`（进入 setContentView）。
