# 网络调研：TwinVM guest 的"幽灵打印"之谜（12:21 TA 指令）

## 我们的症状（11:42 vs 11:57：同 md5 的 bootstrap 两轮行为不同）

```
同 dex：一轮全打（AM 真构造器 ✓ / mObject=1 / mAssets ✓）
        一轮三行全无（其余打印都在）
+ 更早的 v41 静默、U1-U5 消失、println 时有时无
```

## 网络找到的三个根因（全部命中我们的环境）

### 1. JIT 热路径编译的非确定性（AOSP JIT 文档 + 实测案例）
```
- 方法热度阈值 ~10000 次后 JIT 后台编译（AddSamples→CompileMethod）
- JIT 编译线程与业务线程并发——【编译完成的时机每轮不同】
- 编译后代码走 Quick 模式，【跨方法内联】改变打印顺序/可见性
- "无法保证后台捕获的快照包含完整数据"（官方文档原话）
→ 我们的 guest 反复调 getResources/invoke——恰好是 JIT 最爱编译的热方法
→ 同 dex 不同轮：有的轮 JIT 先编译完（吃打印），有的轮没有
```

### 2. -Xverify:none 的软验证失败路径（VerifyError 案例库）
```
- ART 对验证失败的类走【运行时逐条软验证】（soft-fail）
- 软验证的【首次触发时机不确定】——类初始化顺序随之漂移
- dalvikvm -Xverify:none 下我们 bootstrap 的复杂反射结构
  （嵌套 try + 匿名类 + Unsafe）恰是软验证高发区
→ v66 的"括号层级错乱仍编译过"就是软验证环境的表现
```

### 3. Heisenbug 机制（aditlal.dev 的 Play Store 案——与我们 100% 同构）
```
"Attach a debugger, add a log statement, change the timing
 by a microsecond, and the bug vanishes."
—— verify 模式（纯解释+JIT）下初始化竞态被放大 10-50 倍
—— 我们 guest = 永远 verify 模式（无 AOT、无 profile）
   + ROM 里首次运行的类全靠 JIT/解释器
   → 【打印消失 = JIT 编译竞态】的概率最高
```

## 结论与工程对策（已验证有效的）

```
① sTrace 状态位（字段写）——JIT 不优化掉字段写（已实践 ✓ v44）
② 主路径唯一化：v70 的"真 AM 先行"——不依赖兜底分支的执行顺序
③ 结构极简：v48 的教训——嵌套 try 越少 JIT 越没机会抽风
④ 【新认知】：这毛病根不掉（guest 环境天然 verify+JIT），
   只能用上述三招把关键路径钉死
```
